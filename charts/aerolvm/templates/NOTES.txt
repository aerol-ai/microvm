{{- if and .Release.IsUpgrade $enterprise }}

Enterprise mode, like API tokens, reaches only pods made after it was turned
on. Turn it on in an upgrade of its own, after any version upgrade has
finished (the AerolCluster's RUNNING column shows the new version): a pod
made again mid-rollout keeps its old version, which cannot start in
enterprise mode. If this upgrade turned it on, first move every tool that
uses the admin token over the network to an API token or SSO: on a new pod
the admin token works only from inside the pod. The operator makes its own API token on a
server for its calls. Then replace the running pods in the same order: the
gateway pods one at a time, then the server pods one at a time, each after the
last one's replacement says Serving, then the workers by replacing their
machines. Do it soon: the edge's settings already point at the new pods'
private socket, so an old pod whose edge restarts answers the API with 502.
To turn enterprise mode off later, replace the pods in the same order after
that upgrade too, the server pods at the least: the operator stops renewing
its own API token, and once that expires (within 30 days) it can reach no
server still in enterprise mode.
{{- end }}

when sandboxd serves; `aerolvm health` (the CLI) reports the same through the API.

The worker pod runs privileged: label the namespace for it
(pod-security.kubernetes.io/enforce=privileged); `aerolvm k8s verify` checks the label.

Upgrading: a chart upgrade never restarts the worker pod, which would end every
sandbox. To move sandboxd to a new image, change the agent container in place;
only it restarts, and the sandboxes keep running:

   kubectl -n {{ .Release.Namespace }} set image pod/{{ include "aerolvm.name" . }}-0 agent=<image>
