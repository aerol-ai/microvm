A snapshot is a saved copy of a sandbox's files and installed software, stored as an image with a short name. You start new sandboxes from it the same way you start them from `ubuntu:22.04`. Use snapshots to skip slow setup steps, like installing packages, every time you create a sandbox.

Snapshots work with standard container sandboxes, the default kind. V8 isolate sandboxes do not support them.

<Aside title="Using Firecracker?">
Firecracker sandboxes use [Firecracker templates](/firecracker-templates/) instead. A template builds the virtual machine's disk ahead of time and saves a paused copy of its memory. New sandboxes then start in under 100 ms. Templates and snapshots are separate features and cannot stand in for each other.
</Aside>

There are three ways to make a snapshot:

- **Save a running sandbox.** `createSnapshot` saves the sandbox's files and installed packages as a new image.
- **Name an existing image.** `registerSnapshot` with `image` gives an image from a registry, like `python:3.12-slim`, a short name everyone can use.
- **Build from a Dockerfile.** `registerSnapshot` with `dockerfileContent` has the server build the image for you.

Either way, you use a snapshot by passing its name as the `image` when you create a sandbox.

## Save a running sandbox as a snapshot

Set up a sandbox the way you want it, then save it. The original sandbox keeps running, and the snapshot does not depend on it.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({ image: "ubuntu:22.04" });
    await sandbox.exec("apt-get update && apt-get install -y python3-pip");

    const snapshot = await sandbox.createSnapshot("py-ready");
    console.log(snapshot.name, snapshot.image);
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox = client.create(image="ubuntu:22.04")
    sandbox.exec("apt-get update && apt-get install -y python3-pip")

    snapshot = sandbox.create_snapshot("py-ready")
    print(snapshot["name"], snapshot["image"])
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    sandbox, err := client.Create(ctx, sdktypes.CreateSandboxOptions{Image: "ubuntu:22.04"})
    if err != nil {
        log.Fatal(err)
    }
    if _, err := sandbox.ExecCommand(ctx, "apt-get update && apt-get install -y python3-pip"); err != nil {
        log.Fatal(err)
    }

    snapshot, err := sandbox.CreateSnapshot(ctx, "py-ready")
    if err != nil {
        log.Fatal(err)
    }
    fmt.Println(snapshot.Name, snapshot.Image)
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let sandbox = client.create(CreateOptions {
        image: "ubuntu:22.04".into(),
        ..Default::default()
    })?;
    sandbox.exec("apt-get update && apt-get install -y python3-pip")?;

    let snapshot = sandbox.create_snapshot("py-ready")?;
    println!("{} {}", snapshot.name, snapshot.image);
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    Sandbox sandbox = client.create(new CreateOptions().setImage("ubuntu:22.04"));
    sandbox.exec("apt-get update && apt-get install -y python3-pip");

    SandboxSnapshot snapshot = sandbox.createSnapshot("py-ready");
    System.out.println(snapshot.name + " " + snapshot.image);
    ```
  </TabItem>
</Tabs>

Snapshot names are unique across the whole server. If you save again after changes, use a new name, like `py-ready-2026-05`. Calling `createSnapshot` again with the same name on the **same** sandbox is safe: it returns the snapshot you already have. The same name on a **different** sandbox fails with `snapshot name already in use`.

## Start a sandbox from a snapshot

Pass the snapshot's name where you would normally pass an image.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({ image: "py-ready" });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox = client.create(image="py-ready")
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    sandbox, err := client.Create(ctx, sdktypes.CreateSandboxOptions{Image: "py-ready"})
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let sandbox = client.create(CreateOptions {
        image: "py-ready".into(),
        ..Default::default()
    })?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    Sandbox sandbox = client.create(new CreateOptions().setImage("py-ready"));
    ```
  </TabItem>
</Tabs>

The server swaps the name for the real image before it creates the sandbox. If a name could also be an image from a registry, the snapshot wins. That rarely happens, because snapshot names are short words, not registry paths. Afterward, the sandbox's `image` field shows the real image, not the snapshot name.

The new sandbox does not copy the snapshot's CPU, memory or disk hints. It gets the normal defaults unless you set `cpu`, `memoryMB` and `diskGB` yourself.

## Give an existing image a snapshot name

If the image is already in a registry, you do not need to build or save anything. `registerSnapshot` just records a name that points at it. The server does not download the image until the first sandbox uses it.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    await client.registerSnapshot({
      name: "py-base",
      image: "python:3.12-slim",
      cpu: 2,
      memoryMB: 4096,
      diskGB: 10,
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    client.register_snapshot({
        "name": "py-base",
        "image": "python:3.12-slim",
        "cpu": 2,
        "memoryMB": 4096,
        "diskGB": 10,
    })
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    if _, err := client.RegisterSnapshot(ctx, sdktypes.RegisterSnapshotOptions{
        Name:     "py-base",
        Image:    "python:3.12-slim",
        CPU:      2,
        MemoryMB: 4096,
        DiskGB:   10,
    }); err != nil {
        log.Fatal(err)
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::RegisterSnapshotOptions;

    client.register_snapshot(RegisterSnapshotOptions {
        name: "py-base".into(),
        image: Some("python:3.12-slim".into()),
        cpu: Some(2.0),
        memory_mb: Some(4096),
        disk_gb: Some(10),
        ..Default::default()
    })?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    client.registerSnapshot(new RegisterSnapshotOptions()
        .setName("py-base")
        .setImage("python:3.12-slim")
        .setCpu(2.0)
        .setMemoryMb(4096)
        .setDiskGb(10));
    ```
  </TabItem>
</Tabs>

The `cpu`, `memoryMB` and `diskGB` values are hints. The server stores them and returns them with the snapshot, so your own app can show sensible defaults. They are not applied to new sandboxes.

Registering the same name with the same image again is safe and returns the existing snapshot. The same name with a different image fails with `snapshot name already in use`.

## Build a snapshot from a Dockerfile

If the image does not exist yet, send a Dockerfile. The server builds it and points the snapshot at the result.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    await client.registerSnapshot({
      name: "data-tools",
      dockerfileContent: [
        "FROM python:3.12-slim",
        "RUN pip install --no-cache-dir pandas duckdb polars",
      ].join("\n"),
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    client.register_snapshot({
        "name": "data-tools",
        "dockerfileContent": (
            "FROM python:3.12-slim\n"
            "RUN pip install --no-cache-dir pandas duckdb polars"
        ),
    })
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    if _, err := client.RegisterSnapshot(ctx, sdktypes.RegisterSnapshotOptions{
        Name: "data-tools",
        DockerfileContent: "FROM python:3.12-slim\n" +
            "RUN pip install --no-cache-dir pandas duckdb polars",
    }); err != nil {
        log.Fatal(err)
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    client.register_snapshot(RegisterSnapshotOptions {
        name: "data-tools".into(),
        dockerfile_content: Some(
            "FROM python:3.12-slim\nRUN pip install --no-cache-dir pandas duckdb polars".into(),
        ),
        ..Default::default()
    })?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    client.registerSnapshot(new RegisterSnapshotOptions()
        .setName("data-tools")
        .setDockerfileContent(
            "FROM python:3.12-slim\n" +
            "RUN pip install --no-cache-dir pandas duckdb polars"));
    ```
  </TabItem>
</Tabs>

Good to know:

- **Pass one or the other.** `image` and `dockerfileContent` cannot be used together.
- **A lone `FROM` line is fast.** If the Dockerfile only names a base image, the server registers that image without running a build.
- **Builds are cached.** The server names the built image after a hash of the Dockerfile. Registering the same Dockerfile again reuses the earlier build.
- **There is a builder helper.** Each SDK can also turn its `Image` builder object into a Dockerfile for you, with `registerSnapshotFromImage` (Python `register_snapshot_from_image`, Go `RegisterSnapshotFromImage`, Rust `register_snapshot_from_image`).

## What a snapshot keeps

A snapshot saves the sandbox's image, not the running state around it.

| Saved | Not saved |
|---|---|
| Files and installed packages | Attached cloud storage (it lives outside the sandbox; see [Attach cloud storage](/external-storage/)) |
| The image's start command and working folder | Running programs, open terminal sessions, anything in memory |
| The OS user and the image's own environment variables | Network rules, exposed ports and public URLs |
| Environment variables set with `env` at create time | |
| CPU, memory and disk hints, when you set them | |

<Aside type="caution">
Saving a sandbox also saves the environment variables you passed in `env`. A sandbox started from that snapshot can read them, even though its own `env` is empty. We confirmed this on a server that runs containers on Docker. Do not snapshot a sandbox whose `env` holds secrets you would not share with every user of the snapshot.
</Aside>

To keep data next to an image, write it to [attached cloud storage](/external-storage/) instead. Declare the same storage when you create the new sandbox. The data then lives on its own, apart from any one sandbox.

## Ideas for using snapshots

- **One base image per kind of work.** Register `py-base`, `node-base` or `cuda-base` once when you deploy. Then create every sandbox from it. It is faster than running `apt-get install` in each sandbox, and you update versions in one place.
- **A shared starting point.** Set up a sandbox once (clone a repo, build it, load test data), then save it. Start one sandbox per user from that snapshot. Each user gets a fresh copy of the same starting point.
- **Snapshots that survive a failed server.** In a cluster, combine snapshot pushing with `failover.policy = "recreate"`. See [Share snapshots across a cluster](#share-snapshots-across-a-cluster) below.

## For server operators

### Share snapshots across a cluster

On a single server, a snapshot lives on that server, which runs every sandbox. In a cluster, a saved snapshot exists only on the node that made it. Without help, sandboxes from that snapshot can only run on that node, and if the node fails, the snapshot is gone.

AerolVM can push snapshots in the background to AOCR (the Aerol OCI Registry, a shared image store) so any node can pull them. Turning this on does not slow down `createSnapshot`. The call still returns right away, and a background job pushes the image. Once the push finishes, any node can start sandboxes from it. Together with `failover.policy = "recreate"` (see [Durability and failover](/durability/)), sandboxes made from snapshots survive the loss of their node. Without the push, that recreate is refused, because no other node can reach the image.

You turn this on for the whole server. There is no SDK option, because it is an operations choice, not a per-call one.

| Setting | What it does | Default |
|---|---|---|
| `SB_SNAPSHOT_PUSH_ENABLED` | Turns the whole feature on. When `false`, snapshots stay on their own node, as before. | `false` |
| `SB_AUTO_IMPORT_CLUSTER_ID` | Your cluster's folder in AOCR (`cluster/<id>/snapshots/<name>:latest`). Shared with the auto-import setup. Required when push is on. | None |
| `SB_AUTO_IMPORT_CLUSTER_PAT_PATH` | File holding the token used as the registry password. Read again on every push, so you rotate it by writing the file. Required when push is on. | None |
| `SB_MIRROR_PUSH_HOST` | Where to push, for example `aocr.aerol.ai`. | `SB_IMAGE_DISTRIBUTION_AOCR_HOST` |
| `SB_SNAPSHOT_PUSH_RECONCILE_INTERVAL` | How often the background job runs. | `5m` |
| `SB_SNAPSHOT_PUSH_MAX_IN_FLIGHT` | How many pushes one run may start. | `2` |
| `SB_SNAPSHOT_PUSH_TAG_SUFFIX` | Optional retention suffix added to the pushed tag (`latest<suffix>`), like `--ttl-7d` or `--idle-30d`. Empty pushes a plain `latest` tag that AOCR keeps forever, which is right for failover snapshots. Short-lived clusters can set a short TTL so their snapshots clean themselves up. Push and pull use the same suffix. | Empty |

The server tracks a push state for each snapshot (`push_state` in the API, `PushState` in the Go SDK):

| Push state | What it means |
|---|---|
| `active` | No push was needed, or the push finished. |
| `pending`, `pushing` | Waiting for, or in, the background job. |
| `error` | The last push failed. `push_error` says why, and the job tries again next run. |

A failed push does no harm: the snapshot still works on the node that made it. Snapshots made before you turned the feature on stay `active`; the server does not push them after the fact.
