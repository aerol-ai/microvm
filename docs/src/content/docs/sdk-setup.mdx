An SDK is a library that lets your code talk to the AerolVM server. There is one for TypeScript, Python, Go, Rust and Java. They all do the same things, so you can pick whichever language you already use.

## Tell the SDK where your server is

Every SDK needs two things:

| Setting | What it is | Default |
|---|---|---|
| `SB_API_URL` | The address of your AerolVM server. | `http://127.0.0.1:21212` |
| `SB_PAT_TOKEN` | The secret token you chose when you installed the server. | None. You must set it, or `SB_API_TOKEN`. |
| `SB_API_TOKEN` | The same as `SB_PAT_TOKEN`, for any credential: the server token, your own API token (`avm_…`), or a sign-in token from `aerolvm auth token`. `SB_PAT_TOKEN` wins if both are set. | None |
| `SB_TEAM` | With [access control](/enterprise/sso/) on, the team to act for when your credential belongs to several. | None: your first team |

The easiest way is to set them in your terminal before you run your code:

```bash
export SB_API_URL=http://localhost:21212
export SB_PAT_TOKEN=your-secret-pat
```

You can also pass them in code. Code values win over the terminal settings.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

    ```ts
    import { MicroVM } from "@aerol-ai/aerolvm-sdk";

    const client = new MicroVM({
      apiUrl: "http://localhost:21212",
      patToken: "your-secret-pat",
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    from microvm import MicroVM

    client = MicroVM(
        api_url="http://localhost:21212",
        pat_token="your-secret-pat",

    ```
  </TabItem>
  <TabItem label="Go">

    ```go
    }
    ```

## Connect through a company network

Some company networks put a proxy between your code and the server. The proxy may check TLS with its own certificate authority (CA), ask for a client certificate, or need an extra header. Each SDK can handle this:

| SDK | Trust another CA | Send a client certificate | Add headers |
|---|---|---|---|
| TypeScript | Start Node with `NODE_EXTRA_CA_CERTS` | Pass a `fetch` that uses an undici `Agent` with `connect: { cert, key }` | Pass a `fetch` that adds them |
| Python | `ca_file=` | `client_cert=` | `headers=` |
| Go | `HTTPClient` with `tls.Config.RootCAs` | `HTTPClient` with `tls.Config.Certificates` | `HTTPClient` with a `RoundTripper` that adds them |
| Rust | Add the CA to the system's list | Not yet | Not yet |
| Java | `setHttpClient` with an `SSLContext` | `setHttpClient` with an `SSLContext` | Not yet |

In Python, `ca_file` replaces the system's CA list for this client, like `verify=` does in the `requests` library. `client_cert` takes one PEM file that holds the certificate and its key, or a pair of files `(cert_file, key_file)`. `headers` go on every request and on every live stream. They cannot replace the headers the SDK or HTTP sets itself: `Authorization`, the team header, `Content-Type`, `Idempotency-Key`, `Host`, `Content-Length` and `Transfer-Encoding`. A file that cannot be read fails when you make the client, not on the first call.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    // Run with: NODE_EXTRA_CA_CERTS=/etc/ssl/company-ca.pem node app.js
    const client = new MicroVM({
      fetch: (input, init) => {
        const headers = new Headers(init?.headers);
        headers.set("X-Proxy-Auth", process.env.PROXY_TOKEN ?? "");
        return fetch(input, { ...init, headers });
      },
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import os

    from microvm import MicroVM

    client = MicroVM(
        ca_file="/etc/ssl/company-ca.pem",
        client_cert=("/etc/ssl/me.pem", "/etc/ssl/me.key"),
        headers={"X-Proxy-Auth": os.environ["PROXY_TOKEN"]},
    )
    ```
  </TabItem>
  <TabItem label="Go">
    ```go

    if err != nil {
        log.Fatal(err)
    }
    roots := x509.NewCertPool()
    roots.AppendCertsFromPEM(caPEM)
    cert, err := tls.LoadX509KeyPair("/etc/ssl/me.pem", "/etc/ssl/me.key")
    if err != nil {
        log.Fatal(err)
    }
    client, err := microvm.NewClientWithConfig(&sdktypes.MicroVMConfig{
        HTTPClient: &http.Client{Transport: &http.Transport{
            TLSClientConfig: &tls.Config{RootCAs: roots, Certificates: []tls.Certificate{cert}},
        }},
    })
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust

    // it (on Linux, for example, with update-ca-certificates).
    // Client certificates and extra headers are not supported yet.
    let client = Client::new(None, None)?;
    ```
  </TabItem>
  <TabItem label="Java">

## Run many calls at the same time

An agent often runs many sandboxes at once. Each SDK lets you send calls side by side, in the way that is normal for its language:

- **TypeScript:** every call returns a promise. Use `Promise.all`.
- **Python:** use `AsyncMicroVM` with `asyncio`. It has every call `MicroVM` has, as coroutines, and runs the same request code, so the two always act the same. Close it with `async with`. Callbacks from live streams run on the event loop. The plain `MicroVM` also works from threads.
- **Go:** the client is safe to share between goroutines.
- **Rust:** the client blocks, so run calls on threads. Clone the client for each thread.
- **Java:** the client is safe to share between threads. Run calls on an `ExecutorService`.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandboxes = await Promise.all(
      ["a", "b", "c"].map((name) => client.getOrCreate(name, { image: "python:3.12" })),
    );
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import asyncio

    from microvm import AsyncMicroVM


    async def main():
        async with AsyncMicroVM() as client:
            results = await asyncio.gather(
                *(client.get_or_create(name, image="python:3.12") for name in ["a", "b", "c"])
            )
            for sandbox, created in results:
                print(sandbox.id, created)


    asyncio.run(main())
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    var wg sync.WaitGroup
    for _, name := range []string{"a", "b", "c"} {
        wg.Add(1)
        go func() {
            defer wg.Done()
            if _, _, err := client.GetOrCreate(ctx, name, sdktypes.CreateSandboxOptions{Image: "python:3.12"}); err != nil {
                log.Print(err)
            }
        }()
    }
    wg.Wait()
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust

        for name in ["a", "b", "c"] {
            let client = client.clone();
            scope.spawn(move || {
                client.get_or_create(
                    name,
                    CreateOptions {
                        image: "python:3.12".to_string(),
                        ..Default::default()
                    },
                )
            });
        }
    });
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecutorService pool = Executors.newFixedThreadPool(3);
    List<Future<GetOrCreateResult>> calls = new ArrayList<>();
    for (String name : List.of("a", "b", "c")) {
        calls.add(pool.submit(() -> client.getOrCreate(name, new CreateOptions().setImage("python:3.12"))));
    }
    for (Future<GetOrCreateResult> call : calls) {
        System.out.println(call.get().getSandbox().id);
    }
    ```
  </TabItem>

## When the server is busy

A busy server can turn a request away and say when to try again. It answers `503` when it is overloaded, and `429` when your code sends more than its fair share. Both answers can carry a `Retry-After` header: the number of seconds to wait, or a date and time.

Every SDK retries these for you, up to 3 times:

- It waits as long as `Retry-After` asks, never less.
- It adds up to a fifth more, at random, so many clients do not all come back at the same moment.
- It never waits more than 30 seconds for one retry. A longer ask is cut to 30 seconds.
- Without a `Retry-After`, it waits a short time that doubles on each try: about 200 ms, then 400 ms, then 800 ms.

To change the 30-second limit, set the retry option `maxRetryAfterMs` (`MaxRetryAfterMs` in Go, `max_retry_after_ms` in Rust). Set it to `0` to ignore `Retry-After` and always use the short waits.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    import { MicroVM } from "@aerol-ai/aerolvm-sdk";

    const controller = new AbortController();
    const client = new MicroVM({
      retry: { maxRetryAfterMs: 10_000 },
      // Optional: lets you stop this client's requests and waits.
      signal: controller.signal,
    });

    // Later, to stop everything this client is doing:
    controller.abort();
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    from microvm import MicroVM

    client = MicroVM(config={"retry": {"maxRetryAfterMs": 10000}})
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    maxWait := 10000
    client, err := microvm.NewClientWithConfig(&sdktypes.MicroVMConfig{
        Retry: &sdktypes.RetryConfig{MaxRetryAfterMs: &maxWait},
    })
    if err != nil {
        log.Fatal(err)
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::{ApiVersion, Client, ClientConfig, RetryConfig};

    let client = Client::with_config(
        ClientConfig {
            retry: Some(RetryConfig {
                max_retry_after_ms: Some(10_000),
                ..Default::default()
            }),
            ..Default::default()
        },
        ApiVersion::V1,
    )?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    import ai.aerol.microvm.MicroVMClient;
    import ai.aerol.microvm.MicroVMConfig;
    import ai.aerol.microvm.model.RetryConfig;

    MicroVMClient client = new MicroVMClient(
        new MicroVMConfig()
            .setRetry(new RetryConfig().setMaxRetryAfterMs(10_000))
    );
    ```
  </TabItem>
</Tabs>

Each SDK stops a wait early in its own way:

| SDK | How to stop waiting |
|---|---|
| TypeScript | Pass `signal` to `MicroVM`, or to one call (see below). Aborting it ends the request and any wait. |
| Python | Pass `timeout=` to one call (see below). A signal handler that raises, such as Ctrl-C, also ends the wait. |
| Go | Cancel the `ctx` you pass, or give it a deadline. |
| Rust | The client blocks, so a wait cannot be stopped. Lower `max_retry_after_ms` to keep waits short. |
| Java | Interrupt the thread, for example with `Future.cancel(true)`. |

### Give one call a time limit

Sometimes one call must not take long, while others may. Each SDK lets you limit a single call:

- **TypeScript:** every call takes an optional last argument, `{ signal }`. Use `AbortSignal.timeout(ms)` for a time limit. The call fails with the signal's reason, a `TimeoutError`.
- **Python:** every call takes `timeout=`, in seconds. The call fails with `MicroVMTimeoutError`. Its `status_code` is `0`, which tells it apart from a `504` sent by the server.
- **Go:** give the call a `ctx` with a deadline.
- **Java:** run the call on another thread and stop waiting with `Future.get(timeout)`.
- **Rust:** there is no time limit for one call yet.

The limit covers the whole call: every automatic retry and every wait between retries. A call that does more than one request, such as `getOrCreate`, gets one limit for all of them. For a call that opens a stream, such as running a command with live output or watching files, the limit covers opening the stream, not how long it runs.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.get("sb-1234", undefined, {
      signal: AbortSignal.timeout(5_000),
    });
    const result = await sandbox.exec("make test", { signal: AbortSignal.timeout(60_000) });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    from microvm import MicroVMTimeoutError

    try:
        sandbox = client.get("sb-1234", timeout=5)
        result = sandbox.exec("make test", timeout=60)
    except MicroVMTimeoutError:
        print("too slow; try again later")
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    callCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    sandbox, err := client.Get(callCtx, "sb-1234")
    if errors.Is(err, context.DeadlineExceeded) {
        log.Print("too slow; try again later")
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    // The Rust client blocks and has no time limit for one call yet.
    // Keep retry waits short instead:
    let client = Client::with_config(
        ClientConfig {
            retry: Some(RetryConfig {
                max_retry_after_ms: Some(5_000),
                ..Default::default()
            }),
            ..Default::default()
        },
        ApiVersion::V1,
    )?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecutorService pool = Executors.newCachedThreadPool();
    Future<Sandbox> call = pool.submit(() -> client.get("sb-1234"));
    try {
        Sandbox sandbox = call.get(5, TimeUnit.SECONDS);
    } catch (TimeoutException e) {
        call.cancel(true); // stops the request and any retry wait
        System.out.println("too slow; try again later");
    }
    ```
  </TabItem>
</Tabs>

## When a request fails

When the server says no, every SDK gives you an error that holds:

- **The status**, the HTTP number, such as `422` or `503`.
- **The code**, a short name such as `overloaded`. The server sends one for errors your code can act on.
- **The message**, words for a person to read.
- **The wait**, how long the server's `Retry-After` asked you to wait, when it sent one.

Use the code, not the message, to decide what your program does next. A code stays the same from one release to the next. A message can change.

Not every error has a code. Many errors are only meant for a person to read. An error page from a proxy in front of the server has no code either. For that page, the SDK makes the message from the status. The Rust SDK uses the page's text instead.

| SDK | Error type | Status | Code (when none) | Wait |
|---|---|---|---|---|
| TypeScript | `MicroVMApiError` | `status` | `code` (`undefined`) | `retryAfterMs` |
| Python | `MicroVMHTTPError` | `status_code` | `code` (`""`) | `retry_after`, in seconds |
| Go | `*microvm.APIError` | `StatusCode` | `Code` (`""`) | `RetryAfter` |
| Rust | `Error::Api(ApiError)` | `status()` | `code()` (`None`) | `retry_after()` |
| Java | `MicroVMApiException` | `getStatusCode()` | `getCode()` (`null`) | `getRetryAfter()` |

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    import { MicroVM, MicroVMApiError } from "@aerol-ai/aerolvm-sdk";

    const client = new MicroVM();

    try {
      const sandbox = await client.create({ image: "ubuntu:22.04" });
      console.log(`Created ${sandbox.id}`);
    } catch (err) {
      if (!(err instanceof MicroVMApiError)) throw err;
      console.error(`status ${err.status}, code ${err.code ?? "none"}: ${err.message}`);
      if (err.retryAfterMs !== undefined) {
        console.error(`The server asked to wait ${err.retryAfterMs} ms.`);
      }
    }
    ```
  </TabItem>
  <TabItem label="Python">
    ```python

            print(f"The server asked to wait {err.retry_after} seconds.")
    ```
  </TabItem>
  <TabItem label="Go">

  <TabItem label="Rust">

### Catch one kind of error

Some statuses come up often, so each SDK gives them their own error type. You can catch just the case you care about, such as "this sandbox does not exist", without checking numbers. Each one is a kind of the error above, so code that catches the general error still catches all of them.

| Status | What it means | TypeScript | Python | Go (`errors.Is`) | Rust | Java |
|---|---|---|---|---|---|---|
| `404` | The thing you named does not exist, or is not yours. | `MicroVMNotFoundError` | `MicroVMNotFoundError` | `microvm.ErrNotFound` | `is_not_found()` | `MicroVMNotFoundException` |
| `409` | It clashes with what is there now, such as a name you already use. | `MicroVMConflictError` | `MicroVMConflictError` | `microvm.ErrConflict` | `is_conflict()` | `MicroVMConflictException` |
| `503` | The server is full or busy. The SDK already tried again. | `MicroVMCapacityError` | `MicroVMCapacityError` | `microvm.ErrCapacity` | `is_capacity()` | `MicroVMCapacityException` |
| `408`, `504` | The server, or a proxy in front of it, stopped waiting. | `MicroVMTimeoutError` | `MicroVMTimeoutError` | `microvm.ErrTimeout` | `is_timeout()` | `MicroVMTimeoutException` |
| `401`, `403` | The token is missing, wrong or expired (`401`), or it may not do this (`403`). | `MicroVMAuthError` | `MicroVMAuthError` | `microvm.ErrAuth` | `is_auth()` | `MicroVMAuthException` |

Other statuses, such as `422` or `500`, use the general error type.

A few details:

- **Python:** `MicroVMTimeoutError` is also a built-in `TimeoutError`, so `except TimeoutError` catches it. A `TimeoutError` is an `OSError`, so code that catches `OSError` around a call now also catches a `408` or `504` answer.
- **Rust:** the checks are methods on both `ApiError` and `Error`. `Error::is_timeout()` is also true when the HTTP client itself stopped waiting. `Error::Api(_)` still matches every HTTP error.
- **TypeScript:** the error's `name` stays `"MicroVMApiError"`, so code that checks the name still works. Use `instanceof` to tell the types apart.
- **Go:** a `ctx` that runs out of time gives `context.DeadlineExceeded`, not `ErrTimeout`.

    ```ts
    const client = new MicroVM();

      await client.destroy("sb-1234");
    } catch (err) {

      console.log("Already gone.");
    }
    ```

    ```go
    case errors.Is(err, microvm.ErrNotFound):

    case err != nil:
        log.Fatal(err)
    }
    ```
  </TabItem>

### Error codes

Some codes you may see:

| Code | Status | What it means | What to do |
|---|---|---|---|
| `overloaded` | `503` | The node is running as many of this kind of request as it allows. | The SDK already tried again. Wait, then try later. |
| `rate_limited` | `429` | Your account or team sent more than its share of this kind of request. | Send fewer requests at once. |
| `egress_floor_not_ready` | `503` | The node has not yet set up the rules that keep sandboxes away from cloud metadata and blocked addresses. | Try again after the wait. The node fixes this by itself. |
| `node_guard_not_ready` | `503` | The node has not yet set up the rules that keep sandboxes away from the node's own services. | Try again after the wait. |
| `key_store_unavailable` | `503` | The server could not reach the key store that protects sandbox secrets. | Try again after the wait. |
| `key_revoked` | `503` | The key that protects sandbox secrets was turned off or deleted in the key store. | Ask the key's owner to restore it. |
| `network_policy_unenforced` | `501` | This node cannot enforce the network rules you asked for. | Drop the rules, or ask the operator to turn on the host firewall. |
| `idempotency_key_reused` | `422` | The create's idempotency key was already used with other options. | Send the first options again, or use a new key. See [Retry a create safely](/sandboxes/#retry-a-create-safely). |

In Rust SDK 0.8.0, `Error::Api` holds an `ApiError` instead of the text `"<status>: <message>"`. Errors the SDK finds itself, such as a missing argument, moved to `Error::Client`. Code that read the old text as a `String` no longer compiles, so the compiler shows each place to update.
