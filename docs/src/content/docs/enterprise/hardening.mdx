The defaults are set for getting started, not for hostile code. Pick a posture first, then work through the checklists. What no setting can fix is on [Responsibility and limits](/enterprise/responsibility/).

## Pick a posture

| | Your own code | Code from your users | Hostile code, many tenants |
|---|---|---|---|
| Runtime | Container | gVisor | Firecracker |
| Network | A deny list, or open | An allow list of site names | Block everything, or a short allow list |
| Server default | Open | `default_policy: allowlist` | `default_policy: block_all`, plus `deny_cidrs` and the control-port guard |
| User in the image | Root is fine | Non-root | Non-root |
| Mounts | As needed | Read-only where possible | None |
| API keys | Variables | Inject rules | Inject rules, or none |
| Timers | Optional | Stop when idle | Stop when idle, and a maximum age |

## A hardened sandbox

This sandbox runs in gVisor, has no network and firm limits, stops when idle and is deleted after 4 hours:

## Checklist for each sandbox

1. **Pick the runtime** from the posture table: `runtime: "gvisor"` or `"firecracker"`. See [Sandboxes](/sandboxes/).
2. **Close the network,** or open only what the code needs: `networkBlockAll: true`, or `networkAllowOut` with site names. Avoid deny lists for untrusted code, because they allow everything you did not list. See [Network access](/network-access/).
3. **Use a non-root image.** Setting a user at create time does not change the user yet, so set it in the image:

   ```dockerfile
   FROM python:3.12
   RUN useradd --create-home app
   USER app
   ```

4. **Mount as little as you can,** with `readOnly: true` on every mount that only reads. See [External storage](/external-storage/).
5. **Pin the image by digest** (`image@sha256:...`) after you check its signature in your build pipeline.
6. **Keep API keys out** with an inject rule instead of a plain variable. See [Keep an API key out of the sandbox](/advanced-network-rules/#keep-an-api-key-out-of-the-sandbox).
7. **Set limits and timers:** `cpu`, `memoryMB` and `diskGB`, plus `stopIfIdleFor` and `destroyAtAge`. See [Lifecycle](/lifecycle/).
8. **Cap traffic** with byte limits if the code moves data. See [Limit egress and ingress](/network-usage/).

## Checklist for each server

1. **Start every sandbox closed.** Point `SB_EGRESS_OPERATOR_FILE` at a policy file like this one:

   ```yaml
   version: 1
   default_policy:
     mode: block_all                    # creates that set no policy get no network
   deny_cidrs: [169.254.169.254/32]     # the cloud metadata service; add your private ranges
   node_control_port_guard: true        # no sandbox can reach AerolVM's own ports
   ```

   Do not add the ranges the server gives its own sandboxes to `deny_cidrs`. Test a sandbox after each change. See [Private networks](/advanced-network-rules/#private-networks).
2. **Protect the API token.** The installer prints it once. Keep it in a secret manager.
3. **Use a domain, not an IP address,** so Caddy (the web server in front of AerolVM) serves HTTPS.
4. **Keep the API port private.** On a single server in domain mode, set `SB_API_HOST=127.0.0.1` so only Caddy reaches port `21212`.
5. **Firewall the server.** Open `80` and `443`. Open `22000` to `23000` only if you share TCP ports, and `2220` only if you use SSH. Keep `21212` and `7000` to `7002` private.
6. **Turn off what you do not use:** `SB_ENABLE_SSH_GATEWAY=false`, and leave Firecracker, WebAssembly and V8 isolates off unless you need them. `SB_HOST_RUNTIMES` lists the container runtimes the server may run.
7. **Keep the safety settings on.** Leave `SB_CONTAINER_PRIVILEGED` off. It also turns off name allow lists. Never set `SB_RESOURCE_LIMITS_DISABLED`.
8. **Send the audit log off the server** with `SB_AUDIT_EXPORT_BACKEND` set to `webhook` or `s3`. See [Evidence for your audit](/enterprise/audit-evidence/).
9. **Verify each download** against `checksums.txt` and its signed build provenance. See [Release verification](https://github.com/aerol-ai/microvm/blob/main/RELEASE-VERIFICATION.md).
10. **Stay on the newest release line.** Security fixes land there only.

## Checklist for a cluster

1. **Keep the cluster's signing key off the servers.** Each new server makes its own key and asks to be signed. Node certificates last 90 days, and bundled alerts warn before one expires.
2. **Keep the gossip key on.** Never set `SB_CLUSTER_INSECURE_GOSSIP`.
3. **Use AWS KMS for secret copies:** `SB_SECRET_PROVIDER=awskms` with `SB_SECRET_PROVIDER_STRICT_BOOT=true`, so a server with a broken KMS setup refuses to start. See [Secrets providers](/cluster-secrets/).
4. **Keep the cluster ports on a private network** that the internet cannot reach.
