You run programs in a sandbox the way you would in a terminal. You send a command, and you get back what it printed. There are two ways to do it:

- **`exec`** runs a command, waits for it to finish, and returns all of its output at once. Use it for short commands like `ls`, `pip install` or `python script.py`.
- **`execStream`** hands you the output while the command is still running, and lets you type into it. Use it for long builds, live logs and interactive programs.

## Run a command

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const result = await sandbox.exec("echo hello");
    console.log(result.stdout);   // hello
    console.log(result.exitCode); // 0
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    result = sandbox.exec("echo hello")
    print(result["stdout"])    # hello
    print(result["exitCode"])  # 0
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    result, err := sandbox.ExecCommand(ctx, "echo hello")
    if err != nil {
        log.Fatal(err)
    }
    fmt.Print(result.Stdout)     // hello
    fmt.Println(result.ExitCode) // 0
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let result = sandbox.exec("echo hello")?;
    print!("{}", result.stdout);      // hello
    println!("{}", result.exit_code); // 0
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecResult result = sandbox.exec("echo hello");
    System.out.print(result.stdout);     // hello
    System.out.println(result.exitCode); // 0
    ```
  </TabItem>
</Tabs>

The command runs in a shell (`/bin/sh`), so pipes (`|`), `&&` and variables like `$HOME` all work. The call returns when the command exits.

## What you get back

| What | TypeScript and Python | Go | Rust | Java |
|---|---|---|---|---|
| What the command printed | `stdout` | `Stdout` | `stdout` | `stdout` |
| Error messages it printed | `stderr` | `Stderr` | `stderr` | `stderr` |
| Exit code | `exitCode` | `ExitCode` | `exit_code` | `exitCode` |
| How long it ran, in milliseconds | `durationMS` | `DurationMS` | `duration_ms` | `durationMs` |
| Whether the time limit stopped it | `timedOut` | `TimedOut` | `timed_out` | `timedOut` |
| Whether output was cut ([details](#limit-how-much-output-you-get-back)) | `stdoutTruncated`, `stderrTruncated` | `StdoutTruncated`, `StderrTruncated` | `stdout_truncated`, `stderr_truncated` | `stdoutTruncated`, `stderrTruncated` |
| The signal that stopped it, if any | `signal` | `Signal` | `signal` | `signal` |

In Python the result is a dictionary, so you read `result["stdout"]`. An exit code of `0` means the command worked. Any other number means it failed.

### When a signal stops the command

A signal is a message from the system that stops a program, for example when it crashes or runs out of time. Then the exit code is `-1`, and `signal` names the signal, like `SIGKILL`. When the command ends on its own, `signal` is empty (`None` in Rust, `null` in Java, `undefined` in TypeScript). Sandboxes created before this field existed never set it.

A shell reports the same thing differently: as exit code 128 plus the signal's number. To compare with a script that checks for, say, `137`, use this table:

| `signal` | Number | A shell's exit code | Common cause |
|---|---|---|---|
| `SIGINT` | 2 | 130 | Ctrl-C |
| `SIGKILL` | 9 | 137 | The time limit ran out, or the system ran out of memory |
| `SIGSEGV` | 11 | 139 | The program crashed |
| `SIGTERM` | 15 | 143 | Something asked it to stop |

You always see `signal` with [`argv`](#pass-arguments-without-a-shell). With `command`, a shell sits between the sandbox and your program. You see `signal` when the shell itself is stopped, for example by the time limit. Some shells also run the last program of a command in their own place, and then you see its signal too. But if the shell keeps running after your program is killed, the shell exits with 128 plus the number, and `signal` is empty.

## Check whether a command worked

A command that fails does not raise an error in your code. Check the exit code yourself.

<Tabs syncKey="lang">

    ```ts
    const result = await sandbox.exec("ls /does-not-exist");
    if (result.exitCode !== 0) {
      console.log(`failed (exit code ${result.exitCode}): ${result.stderr}`);
    }
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    result = sandbox.exec("ls /does-not-exist")
    if result["exitCode"] != 0:
        print(f"failed (exit code {result['exitCode']}): {result['stderr']}")
    ```
  </TabItem>
  <TabItem label="Go">

  </TabItem>
  <TabItem label="Rust">

  </TabItem>
  <TabItem label="Java">


The SDK raises an error only when the command cannot start at all. For example, the command is empty or its working directory does not exist.

## Set the folder, variables and time limit

Pass an options object instead of a string to choose where the command runs, add environment variables, or set a time limit.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const result = await sandbox.exec({
      command: "echo $GREETING from $(pwd)",
      workDir: "/tmp",
      env: { GREETING: "hello" },
      timeoutSeconds: 30,
    });
    console.log(result.stdout); // hello from /tmp
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    result = sandbox.exec({
        "command": "echo $GREETING from $(pwd)",
        "workDir": "/tmp",
        "env": {"GREETING": "hello"},
        "timeoutSeconds": 30,
    })
    print(result["stdout"])  # hello from /tmp
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    result, err := sandbox.Exec(ctx, sdktypes.ExecRequest{
        Command:        "echo $GREETING from $(pwd)",
        WorkDir:        "/tmp",
        Env:            map[string]string{"GREETING": "hello"},
        TimeoutSeconds: 30,
    })
    if err != nil {
        log.Fatal(err)
    }
    fmt.Print(result.Stdout) // hello from /tmp
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::ExecRequest;
    use std::collections::HashMap;

    let result = sandbox.exec(ExecRequest {
        command: "echo $GREETING from $(pwd)".into(),
        work_dir: Some("/tmp".into()),
        env: Some(HashMap::from([("GREETING".to_string(), "hello".to_string())])),
        timeout_seconds: Some(30),
        ..Default::default()
    })?;
    print!("{}", result.stdout); // hello from /tmp
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecResult result = sandbox.exec(new ExecRequest()
        .setCommand("echo $GREETING from $(pwd)")
        .setWorkDir("/tmp")
        .setEnv(Map.of("GREETING", "hello"))
        .setTimeoutSeconds(30));
    System.out.print(result.stdout); // hello from /tmp
    ```
  </TabItem>
</Tabs>

| Option | What it does | Default |
|---|---|---|
| `workDir` | The folder the command starts in. It must already exist. | The image's working folder, often `/` |
| `env` | Extra environment variables for this one command. They are added to the sandbox's own variables. | None |
| `timeoutSeconds` | The longest the command may run before it is stopped. | 300 (5 minutes) |
| `argv` | A program and its arguments as a list, instead of `command`. See [Pass arguments without a shell](#pass-arguments-without-a-shell). | None |
| `maxStdoutBytes`, `maxStderrBytes` | Keep only the start of the output. See [Limit how much output you get back](#limit-how-much-output-you-get-back). | No limit (64 MiB at most) |

The tabs above show how each language spells these names. Python also accepts `workdir` and `timeout_seconds`.

When the time limit runs out, the whole command stops, including anything it started in the background. The result has exit code `-1`, `signal` is `SIGKILL`, and `timedOut` is `true` (`timed_out` in Rust; sandboxes created before these fields existed never set them).

<Aside type="caution" title="A program that leaves its process group keeps running">
The time limit stops every program in the command's process group. A program that starts a new group of its own, as daemons do, is not stopped. To stop such a program on time too, put `timeout` in the command itself: `timeout 30 npm test` stops after 30 seconds and exits with code `124`.
</Aside>

## Pass arguments without a shell

`command` is one string, and a shell reads it. So spaces, quotes, `$` and `;` in it have special meanings. If an argument comes from somewhere you do not control, like a file name or a user's message, you have to quote it just right, or the shell may split it or even run part of it as a second command.

Use `argv` instead. It is a list: the program first, then each argument. Each one reaches the program exactly as you wrote it.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const result = await sandbox.exec({ argv: ["echo", "it's $5; really"] });
    console.log(result.stdout); // it's $5; really
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    result = sandbox.exec({"argv": ["echo", "it's $5; really"]})
    print(result["stdout"])  # it's $5; really
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    result, err := sandbox.Exec(ctx, sdktypes.ExecRequest{
        Argv: []string{"echo", "it's $5; really"},
    })
    if err != nil {
        log.Fatal(err)
    }
    fmt.Print(result.Stdout) // it's $5; really
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::ExecRequest;

    let result = sandbox.exec(ExecRequest {
        argv: Some(vec!["echo".into(), "it's $5; really".into()]),
        ..Default::default()
    })?;
    print!("{}", result.stdout); // it's $5; really
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecResult result = sandbox.exec(new ExecRequest()
        .setArgv(List.of("echo", "it's $5; really")));
    System.out.print(result.stdout); // it's $5; really
    ```
  </TabItem>
</Tabs>

- Set `command` or `argv`, not both.
- `argv` finds programs the same way `command` does. It uses the same `PATH`, including folders the image's login setup adds, such as conda's.
- Shell features like pipes (`|`), `&&` and `*` do nothing in `argv`. They are passed to the program as plain text.
- If the program does not exist, the exit code is `127` and `stderr` says `not found`, as in a shell.
- `argv` also works in images that have no shell at all, such as "distroless" images, where `command` cannot run. The sandbox then looks the program up on the image's `PATH`.
- `execStream` takes `argv` too.
- A sandbox started before `argv` existed runs an older agent. The SDK checks first and raises the same error as for [output limits](#limit-how-much-output-you-get-back), without running anything.

## Limit how much output you get back

Some commands print far more than you want to read, like a long build log or `cat` on a big file. Set `maxStdoutBytes` and `maxStderrBytes` to keep only the start of each stream. The sandbox reads the rest and throws it away, so the command does not slow down or get stuck. The result tells you whether anything was cut.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const result = await sandbox.exec({
      command: "cat /var/log/build.log",
      maxStdoutBytes: 64_000,
      maxStderrBytes: 16_000,
    });
    if (result.stdoutTruncated) {
      console.log("The log is longer. This is only the start of it.");
    }
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    result = sandbox.exec({
        "command": "cat /var/log/build.log",
        "maxStdoutBytes": 64_000,
        "maxStderrBytes": 16_000,
    })
    if result["stdoutTruncated"]:
        print("The log is longer. This is only the start of it.")
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    result, err := sandbox.Exec(ctx, sdktypes.ExecRequest{
        Command:        "cat /var/log/build.log",
        MaxStdoutBytes: 64_000,
        MaxStderrBytes: 16_000,
    })
    if err != nil {
        log.Fatal(err)
    }
    if result.StdoutTruncated {
        fmt.Println("The log is longer. This is only the start of it.")
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::ExecRequest;

    let result = sandbox.exec(ExecRequest {
        command: "cat /var/log/build.log".into(),
        max_stdout_bytes: Some(64_000),
        max_stderr_bytes: Some(16_000),
        ..Default::default()
    })?;
    if result.stdout_truncated {
        println!("The log is longer. This is only the start of it.");
    }
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecResult result = sandbox.exec(new ExecRequest()
        .setCommand("cat /var/log/build.log")
        .setMaxStdoutBytes(64_000L)
        .setMaxStderrBytes(16_000L));
    if (result.stdoutTruncated) {
        System.out.println("The log is longer. This is only the start of it.");
    }
    ```
  </TabItem>
</Tabs>

- The limits count bytes, not characters. A cut never splits a character in two, so you can get a few bytes less than the limit.
- Leave a limit out, or set it to `0`, for no limit of your own. Even then, a sandbox keeps at most 64 MiB of each stream, and the flag tells you when that cut the output.
- The exit code is the command's own. Cutting its output does not change it.
- Output that a background job prints after `exec` returns is dropped, as always, and does not count as cut.
- A sandbox started before these limits existed runs an older agent that would ignore them and send all the output. So the SDK checks first, and if the agent is too old, it raises an error and does not run the command. The error is `MicroVMUnsupportedFeatureError` in TypeScript and Python, `ErrUnsupportedFeature` in Go, `Error::UnsupportedFeature` in Rust and `MicroVMUnsupportedFeatureException` in Java. Restart the sandbox, or re-create its Firecracker template, to get the current agent.

## Watch output while a command runs

`execStream` returns a handle right away. Your callbacks get each piece of output as the command prints it. Wait on the handle to get the exit code.

This example runs `npm install` in a Node.js sandbox that has a project in `/workspace`.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const handle = sandbox.execStream({
      command: "npm install",
      workdir: "/workspace",
      onStdout: (chunk) => process.stdout.write(chunk),
      onStderr: (chunk) => process.stderr.write(chunk),
    });

    const { code } = await handle.done;
    console.log(`exited with ${code}`);
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import sys

    handle = sandbox.exec_stream({
        "command": "npm install",
        "workdir": "/workspace",
        "onStdout": lambda chunk: sys.stdout.buffer.write(chunk),
        "onStderr": lambda chunk: sys.stderr.buffer.write(chunk),
    })

    print(handle.wait())  # {'code': 0}
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    handle, err := sandbox.ExecStream(ctx, sdktypes.ExecStreamOptions{
        Command:  "npm install",
        Workdir:  "/workspace",
        OnStdout: func(chunk []byte) { os.Stdout.Write(chunk) },
        OnStderr: func(chunk []byte) { os.Stderr.Write(chunk) },
    })
    if err != nil {
        log.Fatal(err)
    }

    exit, err := handle.Wait()
    if err != nil {
        log.Fatal(err)
    }
    fmt.Println("exited with", exit.Code)
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::ExecStreamOptions;
    use std::sync::Arc;

    let handle = sandbox.exec_stream(ExecStreamOptions {
        command: "npm install".into(),
        workdir: Some("/workspace".into()),
        on_stdout: Some(Arc::new(|chunk| print!("{}", String::from_utf8_lossy(&chunk)))),
        on_stderr: Some(Arc::new(|chunk| eprint!("{}", String::from_utf8_lossy(&chunk)))),
        ..Default::default()
    })?;

    let exit = handle.wait()?;
    println!("exited with {}", exit.code);
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecStreamHandle handle = sandbox.execStream(new ExecStreamOptions()
        .setCommand("npm install")
        .setWorkDir("/workspace")
        .setOnStdout(chunk -> System.out.print(new String(chunk, StandardCharsets.UTF_8)))
        .setOnStderr(chunk -> System.err.print(new String(chunk, StandardCharsets.UTF_8))));

    ExecExitInfo exit = handle.waitForExit();
    System.out.println("exited with " + exit.code);
    ```
  </TabItem>
</Tabs>

Output arrives as raw bytes, in the pieces the command happened to print. A piece can end in the middle of a line.

| Option | What it does |
|---|---|
| `command` | The shell command to run. Required, unless you set `argv`. |
| `argv` | A program and its arguments as a list, run without a shell. See [Pass arguments without a shell](#pass-arguments-without-a-shell). |
| `workdir` | The folder to start in. Note the spelling: `workdir` here, but `workDir` for `exec` in TypeScript and Python. |
| `env` | Extra environment variables for this command. |
| `onStdout`, `onStderr` | Called with each piece of output and error output. |
| `onError` | Called with a message if the stream reports an error. |
| `tty`, `cols`, `rows` | Run the command in a terminal of this size. See [Run an interactive program](#run-an-interactive-program). |

The exit info has a `code`, and a `signal` name when a signal stopped the command. `execStream` has no time limit option. To stop a command, [send it a signal](#stop-a-command).

## Send input to a command

`write` sends text to the command's input (stdin), as if you typed it. `close` ends the input, like pressing Ctrl-D. The command then keeps running until it exits on its own.

<Aside type="note" title="In a terminal, send Ctrl-D instead of close">
With `tty: true`, `close` does nothing: a terminal has no separate input to end. Instead, `write` Ctrl-D (the byte `\x04`) at the start of a line. The program reads it as the end of its input, as it would from a keyboard.
</Aside>

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const handle = sandbox.execStream({
      command: "wc -l",
      onStdout: (chunk) => process.stdout.write(chunk),
    });

    handle.write("one\ntwo\nthree\n");
    handle.close();
    await handle.done; // wc prints 3
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import sys

    handle = sandbox.exec_stream({
        "command": "wc -l",
        "onStdout": lambda chunk: sys.stdout.buffer.write(chunk),
    })

    handle.write("one\ntwo\nthree\n")
    handle.close()
    handle.wait()  # wc prints 3
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    handle, err := sandbox.ExecStream(ctx, sdktypes.ExecStreamOptions{
        Command:  "wc -l",
        OnStdout: func(chunk []byte) { os.Stdout.Write(chunk) },
    })
    if err != nil {
        log.Fatal(err)
    }

    handle.WriteString("one\ntwo\nthree\n")
    handle.Close()
    handle.Wait() // wc prints 3
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::ExecStreamOptions;
    use std::sync::Arc;

    let handle = sandbox.exec_stream(ExecStreamOptions {
        command: "wc -l".into(),
        on_stdout: Some(Arc::new(|chunk| print!("{}", String::from_utf8_lossy(&chunk)))),
        ..Default::default()
    })?;

    handle.write_string("one\ntwo\nthree\n")?;
    handle.close()?;
    handle.wait()?; // wc prints 3
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecStreamHandle handle = sandbox.execStream(new ExecStreamOptions()
        .setCommand("wc -l")
        .setOnStdout(chunk -> System.out.print(new String(chunk, StandardCharsets.UTF_8))));

    handle.write("one\ntwo\nthree\n");
    handle.close();
    handle.waitForExit(); // wc prints 3
    ```
  </TabItem>
</Tabs>

## Run an interactive program

Programs like `bash`, `vim`, `top` and the Python prompt expect a terminal. Set `tty` to true to give the command one. This is a pseudo-terminal (PTY): a fake terminal that makes the program act as if a person is typing at it.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const handle = sandbox.execStream({
      command: "bash",
      tty: true,
      cols: process.stdout.columns,
      rows: process.stdout.rows,
      onStdout: (chunk) => process.stdout.write(chunk),
    });

    // Pass every key you press straight to the sandbox.
    process.stdin.setRawMode?.(true);
    process.stdin.on("data", (chunk) => handle.write(chunk));

    // Keep the remote terminal the same size as yours.
    process.stdout.on("resize", () => {
      handle.resize(process.stdout.columns, process.stdout.rows);
    });

    await handle.done;
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import sys

    handle = sandbox.exec_stream({
        "command": "bash",
        "tty": True,
        "cols": 120,
        "rows": 40,
        "onStdout": lambda chunk: sys.stdout.buffer.write(chunk),
    })

    handle.write("echo hello\n")
    handle.write("exit\n")
    print(handle.wait())
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    handle, err := sandbox.ExecStream(ctx, sdktypes.ExecStreamOptions{
        Command:  "bash",
        TTY:      true,
        Cols:     120,
        Rows:     40,
        OnStdout: func(chunk []byte) { os.Stdout.Write(chunk) },
    })
    if err != nil {
        log.Fatal(err)
    }

    handle.WriteString("echo hello\n")
    handle.WriteString("exit\n")
    exit, err := handle.Wait()
    fmt.Println(exit.Code, err)
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::ExecStreamOptions;
    use std::sync::Arc;

    let handle = sandbox.exec_stream(ExecStreamOptions {
        command: "bash".into(),
        tty: true,
        cols: Some(120),
        rows: Some(40),
        on_stdout: Some(Arc::new(|chunk| print!("{}", String::from_utf8_lossy(&chunk)))),
        ..Default::default()
    })?;

    handle.write_string("echo hello\n")?;
    handle.write_string("exit\n")?;
    println!("{:?}", handle.wait()?);
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    ExecStreamHandle handle = sandbox.execStream(new ExecStreamOptions()
        .setCommand("bash")
        .setTty(true)
        .setCols(120)
        .setRows(40)
        .setOnStdout(chunk -> System.out.print(new String(chunk, StandardCharsets.UTF_8))));

    handle.write("echo hello\n");
    handle.write("exit\n");
    ExecExitInfo exit = handle.waitForExit();
    System.out.println(exit.code);
    ```
  </TabItem>
</Tabs>

In a terminal, normal output and error output arrive mixed together, so only `onStdout` is called. Call `resize(cols, rows)` on the handle when your window changes size, so programs like `vim` redraw to fit.

## Stop a command

Send the command a signal: a short message from the system that asks a program to stop. It goes to the command and to every program the command started.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    handle.signal("INT"); // same as pressing Ctrl-C
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    handle.signal("INT")  # same as pressing Ctrl-C
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    handle.Signal("INT") // same as pressing Ctrl-C
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    handle.signal("INT")?; // same as pressing Ctrl-C
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    handle.signal("INT"); // same as pressing Ctrl-C
    ```
  </TabItem>
</Tabs>

| Signal | What it does |
|---|---|
| `INT` | Interrupts the command, like Ctrl-C. |
| `TERM` | Asks the command to stop and clean up. |
| `KILL` | Stops the command at once. It cannot refuse. |
| `HUP` | Tells the command its terminal closed. |
| `QUIT` | Like Ctrl-\. Many programs stop and print debug details. |

A command stopped by a signal reports exit code `-1` and the signal's name, for example `interrupt`.

## If the connection drops

A streamed command lives only as long as its connection. If the connection closes before the command exits, the sandbox stops the command and everything it started. This covers your program exiting, the network failing, or a proxy cutting the link. Nothing is left running with no one to read its output.

A command that prints nothing for a long time is not treated as dropped. The sandbox checks every open stream every 30 seconds, which also stops proxies from closing quiet connections. Every SDK answers those checks for you. If no answer arrives for 90 seconds, the connection counts as dropped.

For work that must keep going after you disconnect, such as a dev server or a long build, use a [terminal session](/sessions/). Sessions keep running, and they replay their recent output when you reconnect.

## Which one to use

| You want to | Use |
|---|---|
| Run a short command and read the result: `ls`, `git status`, a test script | `exec` |
| See output as it happens: `npm install`, `make`, a training run | `execStream` |
| Run something interactive: `bash`, `python`, `vim` | `execStream` with `tty: true` |
| Handle very large output without holding it all in memory | `execStream` |
| Keep a program running after you disconnect | A [terminal session](/sessions/) |

## Good to know

- **Background jobs do not hold up `exec`.** If your command starts something with `&`, `exec` returns soon after the command itself ends (within about a second), and the background program keeps running. Output it prints after `exec` returns is dropped. To watch a long-running program's output, start it in a [terminal session](/sessions/) instead. A sandbox keeps the output of up to 256 such programs open; past that, a new one's output is closed, so it may stop the next time it prints.
- **`exec` keeps the output in memory** until the command ends, up to 64 MiB of each stream. For commands that print a lot, [set a limit](#limit-how-much-output-you-get-back) or use `execStream`.
- **If the sandbox stops while a command runs**, the call fails within seconds instead of waiting. This covers a sandbox that crashes, is stopped or is deleted. The error is HTTP 409 with `sandbox is not running`. A crashed Firecracker sandbox can take up to 30 seconds to notice, and that call fails with HTTP 502. The command may have done part of its work, so the SDKs do not send it again. A command that is still running is never cut off, however long it stays quiet.
- **WebAssembly sandboxes** support `exec`, but not `execStream` or terminals. What a command does there depends on the module. See [WebAssembly (WASM)](/wasm-sandbox/).
- **V8 isolate sandboxes** have no shell. There, `exec` calls the isolate's request handler, and the command is the URL path to request. See [V8 isolate](/isolate-sandbox/).

## For server operators

Two settings limit how much output `exec` returns, for every caller. Both are off by default.

| Variable | What it does |
|---|---|
| `SB_EXEC_OUTPUT_DEFAULT_BYTES` | The limit for each stream when a call sets none. |
| `SB_EXEC_OUTPUT_MAX_BYTES` | The largest limit a call may ask for. A larger one, or none, is lowered to it. |

The server applies them before the command reaches the sandbox, so they work on every runtime and on sandboxes that are already running. They cover `exec` from the AerolVM SDKs and the Daytona SDK's `process.executeCommand`, not `execStream` or sessions. A sandbox started before the limits existed ignores them. In a cluster, set the same values on every node. With a maximum set, an `exec` request bigger than 8 MiB is refused with HTTP 413. Linux limits a command and its variables to a few MiB, so no real command is that big.
