A **cluster** is a group of AerolVM servers that work together as one system. Each server in the group is called a **node**. The cluster spreads sandboxes across its nodes, so you can run more of them at once. It keeps working if one node goes down.

One server is fine for development and light production use (see [Install on a server](/getting-started/single-node-setup/)). You need a cluster when:

- one server cannot fit all your sandboxes,
- the system must keep running when a server fails, or
- you want public web traffic to land on different machines than the sandboxes.

You can build a cluster in two ways. Neither needs a copy of the AerolVM repository.

| | One command per machine | Terraform on AWS |
|---|---|---|
| Where | Any Linux machines: any cloud, or your own hardware | AWS |
| What you run | The installer on each machine | `terraform apply`, once |
| Who makes the machines | You | Terraform |
| Good for | Any setup, and for learning how a cluster fits together | A repeatable AWS cluster you keep in code |

Both join nodes the same way: each new machine runs one line with a **join token**, a short secret that lets one machine in. After that, you run the cluster from your own computer with the [`aerolvm` CLI](/cli/#run-a-cluster).

## Node roles

Each node has a role: the jobs it does.

| Role | Votes on cluster decisions | Runs sandboxes | Takes public traffic |
|---|---|---|---|
| `mixed` | Yes | Yes | Yes |
| `server` | Yes | No | No |
| `worker` | No | Yes | No |
| `ingress` | No | No | Yes |
| `server,worker` | Yes | Yes | No |
| `server,ingress` | Yes | No | Yes |
| `worker,ingress` | No | Yes | Yes |

Nodes with `server` in their role (or `mixed`) keep the cluster's shared record of which sandbox runs on which node. They agree on every change with a method called **Raft**. A change only goes through when a majority of these voting nodes is online. That majority is called a **quorum**.

With 3 voting nodes you can lose 1. With 5 you can lose 2. Always use an odd number of voting nodes: 3, 5 or 7. The [Glossary](/cluster-glossary/) has the full table.

Mixed and combined roles are only for clusters of 10 nodes or fewer. Bigger clusters need separate `server`, `worker` and `ingress` nodes. See [Ingress nodes](/cluster-ingress/).

How big to make each node:

- **Server nodes** do little work. 2 CPUs and 2 to 4 GB of memory is enough.
- **Worker nodes** run the sandboxes, so they need more memory and disk. Size them for your workload.
- **Ingress nodes** pass network traffic along. 2 CPUs and 4 GB of memory is a good start.

## Before you start

You need:

- **Linux machines** with Ubuntu 22.04 or newer, one per node.
- **A private network between them**, with these ports open. Keep them closed to the internet.

| Port | Open it | What it carries |
|---|---|---|
| `7000` TCP | Between server nodes | Raft: the servers' votes |
| `7001` TCP and UDP | Between all nodes | Gossip: how nodes find each other |
| `7002` TCP | Between all nodes | Calls from node to node, over mutual TLS |
| `7003` TCP | From every node to the server nodes | Joins: a new machine asks to join here |
| `443` TCP | From the internet to ingress nodes | HTTPS for the API and sandbox links |

- **A domain on Cloudflare** and a Cloudflare API token with the `Zone:DNS:Edit` and `Zone:Read` permissions, for HTTPS. [Install on a server](/getting-started/single-node-setup/#step-3-create-a-cloudflare-api-token) shows how to make the token.
- **The `aerolvm` CLI** on your computer. See [Install the CLI](/cli/#install).

## Build a cluster with one command per machine

### Step 1: Start the cluster on the first server

Log in to the machine that will be the first server. Make a secret admin token for the cluster. Your apps send it with every request, like a password:

```bash
openssl rand -hex 32
```

Then install AerolVM and start the cluster in one command. Put your own values in place of the examples:

```bash
curl -fsSL https://aerolvm.aerol.ai | sudo bash -s -- \
    --domain cluster.example.com \
    --pat-token your-secret-pat \
    --dns-provider cloudflare \
    --dns-api-token your-cloudflare-api-token \
    init --role server
```

Everything before `init` is an [installer option](/getting-started/installer-options/). Everything after it goes to `sandboxd init`, which:

1. makes the cluster's certificate authority (the key that signs every node's certificate), the gossip key and the key that encrypts stored secrets,
2. starts the cluster with this machine as its first server and leader,
3. makes a join token for a worker, and prints the line that adds one, and
4. writes the cluster's admin login to `/etc/sandboxd/admin-context.json`.

`--role` must include `server`. `mixed` is the default. To use your own tokens instead of the one `init` makes, pass `--token worker=<token>:0`, `--token ingress=<token>:0` or `--token server=<token>:24h`.

<Aside type="tip">
Not sure the machine is ready? `sudo sandboxd preflight` checks it first and prints a fix for each problem: disk space, the ports, cgroup v2, and `/dev/kvm` for Firecracker. `init` and `join` run the same checks, and stop before they change anything if one fails.
</Aside>

### Step 2: Log in from your computer

Copy the admin login to your computer and import it:

```bash
ssh ubuntu@<first-server-ip> sudo cat /etc/sandboxd/admin-context.json > admin-context.json
aerolvm config import admin-context.json --use
aerolvm get nodes
```

The file holds the admin token, so keep it private. `aerolvm get nodes` lists one node: the first server, `Ready,Leader`.

### Step 3: Add the other machines

For each new machine, make a join command on your computer:

```bash
aerolvm join-command --role server     # for a server
aerolvm join-command --role worker     # for a worker (the default)
aerolvm join-command --role ingress    # for an ingress node
```

Each prints one line, like this:

```
curl -fsSL https://aerolvm.aerol.ai | sudo bash -s -- join https://10.0.1.5:7003 --token <token> --ca-cert-hash sha256:<hash>
```

Log in to the new machine and run that line. It installs AerolVM, checks that it is talking to your cluster (the `--ca-cert-hash` pins the cluster's certificate authority), gets the node a signed certificate, and joins. It also brings the admin token, so you never pass it again. When it ends, the node is a member. You never copy keys or certificates by hand.

If your cluster has a domain, give every machine the same domain options as the first server, so it serves and names sandbox links under your domain. Put them before the word `join`:

```bash
curl -fsSL https://aerolvm.aerol.ai | sudo bash -s -- \
    --domain cluster.example.com \
    --dns-provider cloudflare \
    --dns-api-token your-cloudflare-api-token \
    join https://10.0.1.5:7003 --token <token> --ca-cert-hash sha256:<hash>
```

Then point your domain at the ingress nodes: an `A` record for `cluster.example.com` and one for `*.cluster.example.com`, each to every ingress node's public IP address, or to a load balancer in front of them. Turn Cloudflare's proxy off for both (**DNS only**).

A join token works for one machine and lasts 2 hours, unless you say otherwise. `--reusable` lets many machines use one token. `--ttl 0` never expires, for worker and ingress nodes that an autoscaler adds. A server token lasts at most 24 hours. See [Keep join tokens safe](#keep-join-tokens-safe).

A join that fails part way is safe to run again: the same machine gets the same answer.

### Step 4: Check the cluster

```bash
aerolvm get nodes
```

Every node should show `Ready`, one server `Ready,Leader`. To check that your code can reach the cluster, point an SDK at `https://cluster.example.com`. See [SDK setup](/sdk-setup/).

## Build a cluster on AWS with Terraform

**Terraform** creates cloud machines from config files. AerolVM ships a Terraform module that creates the whole cluster on AWS: the network, the machines, the firewall rules and the DNS records in Cloudflare. Each machine installs AerolVM and joins with one line, by itself. You use the module by its address on GitHub, so you need no copy of the repository.

You need:

- **Terraform 1.5 or newer.** [Download it here](https://developer.hashicorp.com/terraform/install).
- **An AWS account** that can create EC2 instances (cloud servers), VPCs (private networks), IAM roles, S3 buckets and security groups, and AWS credentials on your computer.
- **A Cloudflare account** that manages your domain, plus an API token with the `Zone:DNS:Edit` and `Zone:Read` permissions.
- **An EC2 key pair** in your region, for SSH to the nodes.

### Step 1: Make a folder

Make an empty folder for your cluster. Copy these three files into it from [`Terraform/examples/from-url`](https://github.com/aerol-ai/microvm/tree/main/Terraform/examples/from-url):

```
my-cluster/
  main.tf
  config/cluster.yml
  config/secrets.example.yml
```

`main.tf` uses the module by its address, pinned to a release:

```hcl
module "aerolvm" {
  source = "git::https://github.com/aerol-ai/microvm//Terraform?ref=v0.7.0"

  cluster_name        = "aerolvm"
  aws_region          = "us-east-1"
  config_dir          = "${path.module}/config"
  admin_allowed_cidrs = ["203.0.113.0/24"]
  ssh_key_name        = "my-key"

  nodes = {
    server-1  = { role = "server", seed = true }
    server-2  = { role = "server" }
    server-3  = { role = "server" }
    ingress-1 = { role = "ingress" }
    worker-1  = { role = "worker", instance_type = "c6i.xlarge", volume_size_gb = 200 }
  }
}
```

`admin_allowed_cidrs` is required. It decides who outside AWS can reach SSH and the API: set it to your own IP ranges. Every other setting the module takes is listed in its [`variables.tf`](https://github.com/aerol-ai/microvm/blob/main/Terraform/variables.tf), and goes in the same block.

`main.tf` also says where Terraform keeps its **state**, the file that records what it made. Use a backend such as S3 with encryption on. The state holds your join tokens and admin token, so keep it as private as the admin token.

### Step 2: Add your secrets

```bash
cp config/secrets.example.yml config/secrets.yml
```

Open `config/secrets.yml` and fill in two values:

```yaml
cluster:
  pat_token: ""     # the cluster's admin token: openssl rand -hex 32
cloudflare:
  api_token: ""     # Cloudflare API token with Zone:DNS:Edit and Zone:Read
```

Every node and every SDK client uses the admin token. Never commit this file to Git.

### Step 3: Set your domain

Open `config/cluster.yml` and change the `ingress` section. Ingress means traffic coming in from the internet.

```yaml
ingress:
  domain_name: "cluster.example.com"   # your domain
  acme_email:  "you@example.com"        # your email, for certificate expiry notices
```

Each sandbox gets its own address under this domain, for example `abc123.cluster.example.com`. Terraform creates the DNS records for you.

### Step 4: Choose your servers

Each entry in `nodes` is one machine. Exactly one must have `seed = true`: the seed starts the cluster, and the others join it. The seed's role must include `server` (or be `mixed`).

The smallest cluster that is ready for production is three `mixed` nodes. With three, you can lose one and the cluster keeps running:

```hcl
nodes = {
  node1 = { role = "mixed", seed = true }
  node2 = { role = "mixed" }
  node3 = { role = "mixed" }
}
```

A larger cluster with separate roles:

```hcl
nodes = {
  srv1 = { role = "server", seed = true, instance_type = "t3.small" }
  srv2 = { role = "server",              instance_type = "t3.small" }
  srv3 = { role = "server",              instance_type = "t3.small" }
  wrk1 = { role = "worker",              instance_type = "t3.large", volume_size_gb = 200 }
  wrk2 = { role = "worker",              instance_type = "t3.large", volume_size_gb = 200 }
  ing1 = { role = "ingress",             instance_type = "t3.medium" }
  ing2 = { role = "ingress",             instance_type = "t3.medium" }
}
```

How the machines join: the module makes one join token per role. The seed runs the installer with `init` and registers all three. Every other machine runs the installer with `join` and its role's token. The worker and ingress tokens never expire, so a worker you add to `nodes` weeks later still joins. The server token lasts 24 hours. Worker and ingress machines never get the admin token, not even in their user data; see [Keep join tokens safe](#keep-join-tokens-safe).

### Step 5: Turn on gVisor (optional)

gVisor adds an extra wall around each container. It puts its own small kernel (the core of an operating system) between the sandbox and the server. If code in a sandbox attacks a kernel bug, it hits gVisor instead of the real kernel.

gVisor works on any normal EC2 instance type. It needs no special hardware.

To turn it on for a worker node, add `with_gvisor = true`:

```hcl
nodes = {
  srv1 = { role = "server", seed = true, instance_type = "t3.small" }
  wrk1 = { role = "worker", with_gvisor = true, instance_type = "t3.large" }
  wrk2 = { role = "worker", with_gvisor = true, instance_type = "t3.large" }
  ing1 = { role = "ingress",                    instance_type = "t3.medium" }
}
```

After you deploy, create sandboxes with `runtime: "gvisor"` to use it. The runtime is the kind of wall a sandbox runs inside. The cluster sends those sandboxes only to nodes that have gVisor. See [gVisor](/gvisor-sandbox/).

### Step 6: Turn on Firecracker (optional)

Firecracker runs each sandbox in its own microVM: a small, fast virtual machine that boots in under 100 ms. This is the strongest wall AerolVM offers. Each sandbox has its own kernel, so a bug in one cannot reach the server or other sandboxes.

<Aside type="caution" title="Firecracker needs bare-metal AWS instances">
Firecracker needs direct access to the chip's virtualization feature (the `/dev/kvm` device). Normal EC2 types (`t3`, `c6i`, `m5`, `r5` and so on) are virtual machines themselves, so they do not have it. You must use **bare-metal** types: the `*.metal` sizes.

- Compute: `c5.metal`, `c5n.metal`, `c6i.metal`, `c7g.metal`
- General purpose: `m5.metal`, `m5zn.metal`, `m6i.metal`
- Storage and memory: `i3.metal`, `r5.metal`

Bare-metal instances cost more. Use them only for the worker nodes that run Firecracker. If a node has no `/dev/kvm`, its setup stops with a message and the node does not join.

All nodes in one cluster must use the same kind of CPU. `c7g.metal` is an ARM (Graviton) machine, so every other node in that cluster must be ARM too, such as `t4g`. Terraform refuses a cluster that mixes ARM and x86.
</Aside>

To turn it on, set `with_firecracker = true` on worker nodes and pick a bare-metal `instance_type`:

```hcl
nodes = {
  srv1 = { role = "server", seed = true, instance_type = "t3.small" }
  wrk1 = { role = "worker", with_firecracker = true, instance_type = "c5.metal" }
  wrk2 = { role = "worker", with_firecracker = true, instance_type = "c5.metal" }
  ing1 = { role = "ingress",                         instance_type = "t3.medium" }
}
```

You only set `with_firecracker` on nodes whose role includes `worker` (or `mixed`). Terraform refuses it anywhere else.

By default, setup downloads the official Firecracker release and a matching Linux kernel for the microVMs. To use your own files instead, add a `firecracker` block to the module block with their download addresses:

```hcl
firecracker = {
  binary_url        = "https://example.com/firecracker"
  jailer_url        = "https://example.com/jailer"
  kernel_url        = "https://example.com/vmlinux"
  kernel_config_url = "https://example.com/vmlinux.config"
  kernel_path       = "/var/lib/sandboxd/firecracker/vmlinux"
}
```

Good to know:

- If `kernel_config_url` is empty, setup tries `kernel_url` with `.config` added to the end.
- The kernel config must turn on `CONFIG_VMGENID=y`. If it does not, setup stops.
- If your server image already has the files, set `auto_install_artifacts = false` and leave the URLs empty. The kernel must be at `kernel_path`, with its config next to it (by default `/var/lib/sandboxd/firecracker/vmlinux.config`).
- The default download comes from GitHub only. So that a GitHub outage cannot stop a new server, set the Terraform variable `download_mirror = "https://aerolvm-downloads.s3.us-east-1.amazonaws.com"`. Then every file the server setup downloads (Firecracker, the scripts, and the network plugins and BuildKit on containerd servers) falls back to the [download mirror](/getting-started/installer-options/#where-downloads-come-from) when GitHub fails. You can instead point `binary_url` and `jailer_url` at the mirror's copies: `https://aerolvm-downloads.s3.us-east-1.amazonaws.com/deps/firecracker/v1.15.1/firecracker-v1.15.1-x86_64` and `.../jailer-v1.15.1-x86_64` (`aarch64` on Arm servers). Either way, set it when you create the cluster: changing it later replaces every server on the next `terraform apply`.

After you deploy, turn a container image into a Firecracker template, then create sandboxes with the `firecracker` runtime. See [Firecracker templates](/firecracker-templates/).

### Step 7: Turn on V8 isolates (optional)

The V8 isolate runtime runs small JavaScript or TypeScript web handlers (`fetch` handlers). It uses Cloudflare's `workerd` program, the same model as Cloudflare Workers. It is off by default.

Add `with_isolate = true` to a worker. Setup then installs a fixed, checksum-verified version of `workerd` and sets `SB_ENABLE_ISOLATE=true`:

```hcl
nodes = {
  srv1 = { role = "server", seed = true, instance_type = "t3.small" }
  wrk1 = { role = "worker", with_isolate = true, instance_type = "t3.large" }
  wrk2 = { role = "worker", with_isolate = true, instance_type = "t3.large" }
  ing1 = { role = "ingress",                     instance_type = "t3.medium" }
}
```

To turn it on for every node, set `default_with_isolate = true` in the module block instead.

After you deploy, upload your JavaScript bundle (`POST /v1/js-bundles`). Then create a sandbox with `runtime: "isolate"` and a `module_ref` that points at the bundle. Some cluster rules:

- A bundle lives only on the one worker that received the upload.
- Listing bundles from any node shows every bundle in the cluster.
- If that worker is gone, upload the bundle again. The API tells you with the error code `artifact_node_unavailable`.

See [V8 isolate](/isolate-sandbox/) for outbound traffic, cluster behavior and current limits.

### Step 8: Turn on GPUs (optional)

AerolVM can give sandboxes direct use of a physical GPU. Both NVIDIA and AMD GPUs work. GPU workers sit next to normal workers. The cluster sends GPU sandboxes only to nodes with a matching GPU.

GPU sandboxes cannot also use gVisor. You can still have GPU nodes and gVisor nodes in the same cluster. Each one just takes different sandboxes.

#### NVIDIA GPUs

Set `with_nvidia_gpu = true` on worker nodes that have an NVIDIA GPU. Setup installs the NVIDIA Container Toolkit, which lets containers use the GPU.

The NVIDIA driver itself must already be on the machine (the `nvidia-smi` command must work). Pick an `ami_id` (server image) that includes it.

Common NVIDIA instance types on AWS:

| Instance | GPU |
|---|---|
| `g4dn.xlarge` | NVIDIA T4 |
| `g5.xlarge` | NVIDIA A10G |
| `p3.2xlarge` | NVIDIA V100 |

```hcl
nodes = {
  srv1 = { role = "server", seed = true,  instance_type = "t3.small" }
  wrk1 = { role = "worker",               instance_type = "t3.large" }
  wrk2 = { role = "worker", with_nvidia_gpu = true, instance_type = "g5.xlarge",
            volume_size_gb = 500, tags = { gpu = "nvidia-a10g" } }
  ing1 = { role = "ingress",              instance_type = "t3.medium" }
}
```

The optional `tags` field adds AWS tags to the instance. They help you find it in the AWS console. Sandboxes do not pick a GPU by these tags. They ask for a GPU maker (`nvidia` or `amd`), and the cluster finds a node that has one.

#### AMD GPUs

Set `with_amd_gpu = true` on worker nodes with AMD GPUs that support ROCm (AMD's GPU software). This only works on `x86_64` instances. The GPU must already be visible to the operating system (`/dev/kfd` must exist).

```hcl
wrk3 = { role = "worker", with_amd_gpu = true, instance_type = "g4ad.xlarge",
          volume_size_gb = 300 }
```

After you deploy, see [GPU](/gpu-sandboxes/) to create GPU sandboxes.

### Step 9: Deploy

From your folder:

```bash
terraform init
terraform apply -var 'admin_allowed_cidrs=["203.0.113.0/24"]' -var ssh_key_name=my-key
```

`init` downloads the module and Terraform's plugins. `apply` shows a plan of everything it will create. Read it, then type `yes`. This usually takes 3 to 5 minutes. (The example `main.tf` takes your IP ranges and key pair name as `-var` options. You can write them into the module block instead.)

When `apply` finishes, Terraform prints each node's public IP address, and the seed's SSH command as `ssh_command_seed`.

Each node then sets itself up. Watch one node's setup log to see when it is done:

```bash
ssh ubuntu@<node-ip> sudo tail -f /var/log/aerolvm-bootstrap.log
```

The seed's log ends with `seed started the cluster with sandboxd init`. Every other node waits for the seed, then its log says `joined the cluster with sandboxd join`.

### Step 10: Check that every node joined

Log in with the cluster's address and the admin token from `config/secrets.yml`, then list the nodes:

```bash
aerolvm login https://cluster.example.com
aerolvm get nodes
```

Every node should show `Ready`, and one server `Ready,Leader`. The built-in [Dashboard](/dashboard/) shows the same nodes in a browser.

To check that your code can reach the cluster, point an SDK at `https://cluster.example.com`. See [SDK setup](/sdk-setup/).

### Terraform from a copy of the repository

The repository still runs the same module from a checkout: `scripts/terraform.sh init` and `scripts/terraform.sh apply` read `config/terraform.tfvars`, `config/cluster.yml` and `config/secrets.yml` at its top. A cluster built that way before the module moved keeps every machine: run `scripts/terraform.sh init` once, and the next plan moves each resource into the module without changing it. That cluster keeps the old way of joining. Do not set `one_line_join = true` on it: changing how nodes join changes every machine's setup script, and Terraform then replaces every machine. The [Terraform README](https://github.com/aerol-ai/microvm/blob/main/Terraform/README.md) has the details.

### Put a load balancer in front

By default, Terraform gives your domain one DNS record for each ingress node. This is called DNS round-robin: each client picks one of the nodes. It costs nothing, but it has a weak spot.

Say the AerolVM server on one node stops: it crashed, or you are restarting or upgrading it. Caddy, the web server in front of it on the same node, keeps running. A client sent to that node still connects, so it does not try another node. It gets error `502` until the server is back. With three ingress nodes, about one call in three fails for that whole time.

A **load balancer** fixes this. It sits in front of the ingress nodes and checks each one every 5 seconds. After two failed checks, about 10 seconds after the server stops, it sends no new connections to that node. After two passed checks, it sends them again.

| | DNS round-robin (`none`, the default) | Load balancer (`nlb`) |
|---|---|---|
| The AerolVM server stops on one node | Its share of calls get `502` until it is back | Calls to it fail for about 10 seconds, then none do |
| What your domain points at | Every ingress node | The load balancer's one fixed IP address |
| Raw TCP port addresses | `tcp://cluster.example.com:22017` | `tcp://tcp.cluster.example.com:22017` |
| Extra AWS cost | None | One Network Load Balancer and one Elastic IP |

Use the load balancer for production. A bank or anyone with an uptime promise should turn it on. Add this line to the module block, then run `terraform apply`:

```hcl
api_load_balancer = "nlb"
```

<Aside type="caution" title="Choose it when you create the cluster">
The setting changes the setup script of every node. On a running cluster, Terraform then replaces every node, and the sandboxes on them are lost. Turn it on before the first `apply`.
</Aside>

What it sets up:

- **An AWS Network Load Balancer that passes connections through.** It does not open them. Caddy on each node still holds your certificates, and [TLS ports](/tcp-vs-tls-ports/) keep working.
- **The caller's real IP address reaches AerolVM.** Audit records and limits see the client, not the load balancer.
- **Ports 80, 443 and the SSH gateway (2220) go through it.** Raw TCP ports do not: an AWS Network Load Balancer takes at most 50 ports, and the pool is about 1,000. So raw TCP goes straight to the nodes under `tcp.<your domain>`, which keeps one DNS record per node. These connections do not pass through the AerolVM server, so they keep working while it restarts.
- **A health check that follows a user's path.** Each ingress node answers the check on port `21280` (change it with `api_lb_health_check_port`). The check goes through Caddy on port 443 to the AerolVM server, so it fails when any part of that path is down. Only the load balancer can reach this port.
- **Open connections stay open.** When a node leaves, only new connections go elsewhere. A connection to a sandbox's port is relayed by Caddy, not by the AerolVM server, so it keeps working while the server restarts.

Your domain stops pointing at the nodes, but they keep their public IP addresses and still answer on them. `admin_allowed_cidrs` works as before.

## Grow the cluster

**By hand:** run `aerolvm join-command` with the new machine's role, and run the line it prints on the machine. See [Step 3](#step-3-add-the-other-machines).

**With Terraform:** add a worker or ingress node to `nodes` and run `terraform apply`. It joins with the module's token for its role, which never expires.

A **server** added later is different: the module's server token lasts 24 hours, so it no longer works. Add the machine with `blank = true`, which leaves it as plain Ubuntu, then join it by hand:

```hcl
srv4 = { role = "server", blank = true, instance_type = "t3.small" }
```

```bash
aerolvm join-command --role server
ssh ubuntu@<srv4-ip>
```

On the machine, run the printed line, with your domain options before the word `join` as in [Step 3](#step-3-add-the-other-machines).

## Take a node out

```bash
aerolvm drain wrk-2 --timeout 30m
aerolvm delete node wrk-2
```

`drain` stops new sandboxes landing on the node, then waits until it runs none. Add `--delete-sandboxes` to destroy what is left instead. `delete node` removes it from the cluster. From then on, every other node refuses it, until the machine joins again with a new token. To reuse the machine, run `sudo sandboxd reset --yes` on it first.

With Terraform, drain and delete the node first, then remove it from `nodes` and run `terraform apply`.

To take a server out, keep a majority of the voting servers up: with three servers, take out one at a time, and add its replacement before the next.

## Upgrade a cluster

From your computer:

```bash
aerolvm upgrade plan v0.7.0
aerolvm upgrade apply v0.7.0 --wait
```

`plan` changes nothing. It prints each node's role and version, whether the jump is allowed, the order the nodes go in, and what restarts on each. `apply` checks every file against the release's checksums and hands the upgrade to the cluster's leader, so it goes on even if your computer goes to sleep. The order is:

1. Every node downloads and checks the new files first. If one cannot, nothing restarts.
2. The servers, one at a time. The leader hands its job to another server and goes last.
3. The ingress nodes, one at a time.
4. The workers, in batches: 10% of them at a time (at least 1), or what `--batch` says. Each batch stops taking new sandboxes before it restarts.

Each node keeps its old files, backs up its database, and goes back to the old files if the new ones do not come up healthy. The rollout stops at the first failure. [`aerolvm upgrade`](/cli/#upgrade-the-cluster) lists `status`, `stop`, `resume`, `rollback` and the canary pause. The [cluster upgrades runbook](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/cluster-upgrades.md) says what to do when a node fails.

### What running sandboxes see

The AerolVM server on each node stops for a few seconds while it swaps its files. What that means for the sandboxes on the node:

| Sandbox | During the upgrade |
|---|---|
| Containers: Docker, containerd and gVisor | Keep running. The new server picks them up again. |
| Firecracker | Keep running. Their VMs run outside the server's own service. |
| Attached cloud storage | Keeps working. Its helpers run outside the server's own service. |
| WebAssembly (WASM) | **Do not survive.** They stop when the server restarts and lose what they held in memory. Start or recreate them after. |
| V8 isolate | **Do not survive.** They are gone after the server restarts. Create them again after. |

A node with WASM or V8 isolate sandboxes that must not stop: drain it first with `aerolvm drain`, or plan for those sandboxes to be recreated.

The toolbox inside a running sandbox stays the old one. New sandboxes get the new one.

### Nodes with no internet access

Pull the release into one file on a machine that has internet, carry it over, and upgrade from it:

```bash
aerolvm release pull v0.7.0 -o aerolvm-v0.7.0.tgz
aerolvm upgrade apply v0.7.0 --from aerolvm-v0.7.0.tgz --wait
```

`release pull` checks every file against the release's checksums as it downloads. `apply` checks them again before it sends anything. The servers hand the files on to the other nodes, so the nodes need no internet access.

### The first upgrade from an older release

Servers on a release older than `aerolvm upgrade` cannot run it. Upgrade those once with the installer instead, one node at a time: servers first, then ingress nodes, then workers. On each node, run:

```bash
curl -fsSL https://aerolvm.aerol.ai | sudo bash
```

The installer keeps the node's settings and token. Wait until `aerolvm get nodes` shows that node `Ready` on the new version before the next one. After this first hop, use `aerolvm upgrade` for every later release.

## Bring an older cluster onto one-line joins

A cluster first built with `cluster-init.sh` keeps its certificate authority key on its first server only, and its nodes have no record that lets them renew their own certificates. After the first upgrade above, run this once:

1. On the first server (the seed): `sudo sandboxd adopt`. It takes the key from `/etc/sandboxd/cluster-ca/ca.key` and records every node as admitted.
2. On every other server: `sudo sandboxd adopt`. Each one gets the key from the seed over the cluster's mutual TLS.
3. Workers and ingress nodes need nothing.

From then on, `aerolvm join-command` works, and every node renews its own certificate before it ends. `adopt` is safe to run again.

If the seed is gone, run `sudo sandboxd adopt --ca-key <file>` with a saved copy of its `ca.key`, such as one from a `sandboxd backup` archive. Without any copy, the cluster cannot sign new certificates.

## Keep join tokens safe

A join token can make a node. What the node gets depends on the token's role:

| Role | What the new node gets |
|---|---|
| `server` | The admin token, the key that signs every node's certificate, the gossip key, and the key that opens stored secrets (unless [key custody](/enterprise/key-custody/) is wrapped). |
| `worker`, `ingress` | The gossip key, the key that opens stored secrets (unless key custody is wrapped), and its own certificate. **Not** the admin token: it gets the admin token's SHA-256 hash instead. |

A worker or ingress node does not need the admin token. It talks to the other nodes with its own certificate, and it checks the admin token you send it against the hash. So a worker or ingress token that leaks lets someone add a worker until you revoke it. It never gives them the admin token, a server token or the certificate key: a server refuses to make a server token, hand out the certificate key, or run `adopt` for a caller whose certificate names a worker or ingress node.

A server token gives everything, so treat it like the admin token:

- **Keep lifetimes short.** The default is 2 hours. A server token lasts at most 24 hours.
- **Keep never-expiring tokens (`--ttl 0`) for workers and ingress nodes,** such as the ones an autoscaler or Terraform adds. In [enterprise mode](/enterprise/enterprise-mode/) they also need wrapped key custody.
- **Revoke what you no longer need:** `aerolvm get jointokens`, then `aerolvm delete jointoken <id>`.
- **Keep Terraform's state private.** It holds the module's three join tokens and the admin token. The user data of a worker or ingress machine holds only its own join token, never the admin token.

Every join, and every refused one, is written to the audit log.

### The token on a worker or ingress node

On a worker or ingress node, `SB_PAT_TOKEN` in `/etc/sandboxd/sandboxd.env` is a random token of that node's own, and `/etc/sandboxd/cluster.env` holds the admin token's hash as `SB_PAT_TOKEN_SHA256`. The node's own token works only for tools on that machine that call `http://127.0.0.1:21212` directly, such as `sandboxd reset`. It is refused from anywhere else, through Caddy, and on every other node.

Some things to know:

- **Upgrades.** While any node still runs an older release, joins hand the admin token to every role, as before. Nodes that already hold it keep working. To take it off such a node once the whole cluster runs this release, run its join line again: the node swaps the admin token for a token of its own and the hash.
- **Rotating the admin token.** On worker and ingress nodes, update the hash instead of the token. Get the new hash with `printf %s "$NEW_TOKEN" | sha256sum`, set `SB_PAT_TOKEN_SHA256=<new hash>,<old hash>` in `/etc/sandboxd/cluster.env`, and restart the node. When every client uses the new token, remove the old hash and restart again.
- **The hash is only as strong as the admin token.** Use a random admin token of at least 32 bytes (`openssl rand -hex 32`).

## Tear down

**By hand:** on each machine, run `sudo sandboxd reset --yes` to take it out of the cluster, then [uninstall](/getting-started/single-node-setup/) AerolVM or delete the machine.

**With Terraform:** from your folder, run:

```bash
terraform destroy
```

<Aside type="caution">
This deletes every EC2 instance, VPC and S3 bucket in the cluster, and every running sandbox. You cannot undo it.
</Aside>

## Good to know

- **Lock down SSH and the API.** With Terraform, `admin_allowed_cidrs` decides who outside the VPC can reach SSH (port 22) and the API (port 21212). A world-open range (`0.0.0.0/0`) is refused unless you also set `allow_admin_from_anywhere = true`.
- **Keep `config/secrets.yml` private.** It holds your admin token and your Cloudflare token.
- **Node names are limited.** Each name in `nodes` must start with a letter or number. It may use only letters, numbers, dots, underscores and hyphens, up to 128 characters.
- **Label nodes to choose where sandboxes run.** Set `SB_NODE_ZONE` and `SB_NODE_LABELS` on a node, and a create can ask for them. See [Choose where a sandbox runs](/engineering-placement-failover/#choose-where-a-sandbox-runs).
- **Certificates renew themselves.** Each node's certificate lasts 90 days and is renewed at two thirds of its life. A node whose certificate has already ended cannot renew it: join it again with a new token.
