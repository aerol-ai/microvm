The **dashboard** is a web page for operators. It shows the health of a node, the nodes in your cluster, where each sandbox runs, and the server's counters.

`sandboxd` is the AerolVM program on each node. It serves the dashboard itself. There is nothing to install. If `sandboxd` runs, the dashboard is there.

## Words to know

| Word | What it means |
|---|---|
| **Node** | One machine that runs `sandboxd`. A one-server install has one node. |
| **Admin token** | The password in `SB_PAT_TOKEN`. It can do everything. The dashboard calls it "Server token". |
| **API token** | A token that starts with `avm_`. You make one with `aerolvm token create`. Each one has a role. |
| **Role** | What a person or token is allowed to do: `admin`, `viewer`, `runner` or `auditor`. |
| **Company sign-in** | Signing in with your work account. It needs [access control](/enterprise/sso/) on. The page also calls it SSO (single sign-on). |
| **Sign-in provider** | The service that holds your work accounts, such as Okta, Entra ID or Google. |
| **API domain** | The domain name your apps use to reach AerolVM, set in `SB_DOMAIN`. In a cluster, it is the cluster address. |

## Open the dashboard

Add `/ui` to the node's address, on the API port. The API port is `21212`, unless you changed `SB_API_PORT`.

```text
http://<node-address>:21212/ui
```

On your own computer, open `http://localhost:21212/ui`.

`sandboxd` also prints the address when it starts. Look for these lines in its log:

```text
time=... level=INFO msg="starting sandboxd" version=... addr=0.0.0.0:21212
time=... level=INFO msg="dashboard available" url=http://0.0.0.0:21212/ui
```

| Where `sandboxd` runs | Where its log is |
|---|---|
| macOS | The file `~/.aerolvm/logs/sandboxd.log`. |
| Linux | Run `journalctl -u sandboxd` to read it. |

When your install has an API domain, the dashboard is also at `https://<api-domain>/ui`. Company sign-in needs this HTTPS address. Does it answer "not found"? Then your install is older than this address. Run the [installer](/getting-started/installer-options/#upgrade-an-install) again to add it.

### Open it on a remote node

On a remote node, use an **SSH tunnel**. It is a private link from your computer to the node, through SSH. Your token then never crosses the open internet. Keep this command running:

```bash title="On your computer"
ssh -L 21212:127.0.0.1:21212 <user>@<node-ip>
```

Then open `http://localhost:21212/ui` in your browser. Type `localhost`, not `127.0.0.1`. Company sign-in sends the address you opened to your sign-in provider. Your operator registered the `localhost` address there.

Every node serves the dashboard: server, worker, ingress and mixed nodes. The node list and the sandbox list show the whole cluster. It does not matter which node you open.

## Sign in

The sign-in box has one button for each company sign-in your operator set up. Each button says **Sign in with ...**, such as "Sign in with Acme Okta". Google shows its own button. Below the buttons, **Use an API token instead** opens a token field. With no company sign-in set up, you see only the token field.

| To sign in with | Do this |
|---|---|
| A token | Paste the admin token, or an API token (`avm_…`). Click **Sign in**. |
| Your company account | Click your provider's button. Sign in there. You come back to the dashboard, signed in. |

The page keeps your sign-in in the tab's `sessionStorage`. That is browser memory that lasts only while the tab is open. The page never writes it to `localStorage` or to disk. It sends it only to the AerolVM server. Closing the tab clears it. So does **Sign out**.

If the token is wrong, the form says so and asks you to sign in again. A wrong token changes nothing on the server.

### Company sign-in needs HTTPS

The sign-in buttons appear only on an HTTPS page, or on `localhost`. An SSH tunnel counts as `localhost`.

On plain HTTP from another computer, the box says "SSO sign-in needs a secure connection". It links to your server's HTTPS address. A token still works there. The page warns you that the token crosses the network unencrypted.

### Who sees the console

The **console** is the main view: health, nodes, sandboxes and metrics. Almost every panel needs the `admin` role. After you sign in:

| You are | You see |
|---|---|
| An `admin`, or the admin token | The console. |
| Another role: `viewer`, `runner` or `auditor` | A short "Signed in as ..." screen. It shows your name, role and team. It also shows two commands to run in a terminal: `aerolvm login <this server>` and `aerolvm list`. |
| A person no access rule matches | "You're signed in, but you don't have access here." It lists up to 50 of the groups your sign-in carried. Tell your admin which group to add. |

An Entra ID sign-in can carry too many groups to list. The screen then asks your admin to bind an Entra app role instead.

The header shows who you are. A person sees their name and an `admin` badge. The admin token shows "Server token" with an `operator` badge. With access control on, that badge has a warning color. The reason: actions taken with the admin token are recorded as the server, not as a person.

### Staying signed in, and signing out

- **A company sign-in lasts as long as your provider allows.** That is often about one hour.
- **The page renews it 2 minutes before it ends.** Google renews it in place. Every other provider reloads the page through the provider. You come back to the same view.
- **A failed renewal changes nothing while your sign-in still works.** The page keeps using your sign-in. It tries again when the sign-in ends.
- **When your sign-in has ended,** a banner says "Your sign-in expired". It has a **Sign in again** button. Your view stays.
- **Sign out** clears the tab. It also stops Google from signing you straight back in. It does not sign you out of your company account. Other company apps work the same way.
- **Use a different account** asks your provider to let you pick another account.

## What the page shows

Each part of the page reads one API endpoint that already exists. The dashboard adds no logic of its own. It shows only what the API returns.

| Part | Endpoint | What it shows |
|---|---|---|
| **Summary tiles** | `GET /v1/cluster/members` | The number of nodes, and how many are drained or stale. The number of sandboxes. How much CPU, memory and disk the cluster has given out. |
| **Health** | `GET /health` | The overall status. Whether Docker, Caddy, Firecracker and the SSH gateway work. (Caddy is the web server in front of AerolVM.) The server version, and the number of live sandboxes. |
| **Nodes** | `GET /v1/cluster/leader` and `GET /v1/cluster/members` | The leader and the number of members. The **leader** is the node that writes down each cluster change. Then one row per node: name, IP, status, role, sandbox count, and the CPU, memory, disk and GPU in use. |
| **Placements** | `GET /v1/cluster/sandbox-index`, one page at a time | One row per sandbox in the cluster: ID, owner node, state, runtime status, version, and when it was made and last changed. |
| **Metrics** | `GET /v1/metrics` | A chosen set of the server's `aerolvm_*` counters. Examples: how long the cluster takes to save a change, forwarded requests, and worker health. Open **Show raw /v1/metrics** to see all of them. |

What a node's status means:

| Status | What it means |
|---|---|
| `active` | The node is up and takes work. |
| `dead` | The node does not answer. |
| `stale` | The node is up. But its last report of free CPU and memory is old. |
| `drained` | The node gets no new sandboxes. See [Actions](#actions-you-can-take). |

A **placement** is the cluster's record of which node owns a sandbox. What a placement's state means:

| State | What it means |
|---|---|
| `placed` | The sandbox has an owner node. |
| `reserved` | A node is being set up for the sandbox. The create is not done yet. |
| `orphaned` | The owner node died, so no node serves the sandbox. |

The runtime column tells you whether the sandbox runs. For sandboxes on the node you opened, it shows `started` or `stopped`. For sandboxes on other nodes, it shows `remote`.

The page refreshes every 5 seconds while you look at it. It pauses while the tab is hidden. So it makes no API calls in the background. The header also has a **Refresh** button and an **auto-refresh** switch.

## Actions you can take

The console has seven buttons for operators. Only admins and the admin token reach the console. So only they see the buttons. Each button asks you to confirm first. The confirm box shows the API call the button makes. Each button calls one existing API endpoint.

| Button | Where | Endpoint | What it does |
|---|---|---|---|
| **Drain** | Nodes, on each row | `POST /v1/cluster/nodes/{id}/drain` | The node gets no new sandboxes. Its running sandboxes keep running. Safe to run again. |
| **Uncordon** | Nodes, on drained rows | `POST /v1/cluster/nodes/{id}/uncordon` | Undoes a drain. The node can get new sandboxes again. Safe to run again. |
| **Start** | Placements, on stopped sandboxes | `POST /v1/sandboxes/{id}/start` | Starts the sandbox again. |
| **Stop** | Placements, on started sandboxes | `POST /v1/sandboxes/{id}/stop` | Stops the sandbox. |
| **Delete** | Placements, on sandboxes that are not orphaned | `DELETE /v1/sandboxes/{id}` | Deletes the sandbox. |
| **Reclaim local** | Placements, on orphaned rows | `POST /v1/cluster/orphans/{id}/reclaim-local` | Fixes a false alarm. The cluster marked a node dead, but it was not. This works only on the node that used to own the sandbox, so open the dashboard on that node. That node must still have the sandbox's local record. |
| **Force delete** | Placements, on orphaned rows | `DELETE /v1/cluster/orphans/{id}` | Removes the cluster's placement record of an orphan. Use it when the old owner node will not come back. It deletes no sandbox on any node, because no owner is left to act. |

There are no buttons to create or resize sandboxes. Use the [SDKs](/sdk-setup/) or the [aerolvm CLI](/cli/) for that. They use the same login and the same checks as everything else.

## Security

- **The page itself (`GET /ui`) needs no login.** It is plain HTML and JavaScript. It holds no passwords and no server data. You sign in before the page calls any API that needs a login. A normal login page works the same way.
- **`GET /health` needs no login either.** Load balancers call it to check that a node is up. It reports only the node's own health.
- **Every other call the page makes needs your token.** That includes `GET /v1/...`, `GET /v1/metrics` and the buttons. The page sends the token as `Authorization: Bearer <token>`. The server checks it like any SDK call, with the same role checks.
- **`/v1/metrics` needs a role bound to every team.** Its counters show how the whole system runs: lease state, queue lengths and secret decrypt failures.
- **The page never calls `/debug/vars`.** Caddy does not forward it from your API domain. It stays `admin`-only, on each node's own port.
- **Company sign-in happens between your browser and your provider.** The server holds no client secret and keeps no session. The browser keeps only the provider's sign-in token, never a refresh token.
- **The page sends a strict Content-Security-Policy.** That is a browser rule that lists what the page is allowed to load and call. It allows only the page's own script, Google's sign-in script, and your providers' addresses. No other site can show the page inside a frame.

Whatever protects the API port also protects the dashboard: HTTPS, a login proxy in front, or an IP allow list. To keep the dashboard on a trusted network, limit who can reach that port.

## Use it with several nodes

You do not need one dashboard per node. The Nodes and Placements lists show the whole cluster, from any node you open. Every button except **Reclaim local** reaches the right node, from any node.

The Metrics panel is different. It shows only the counters of the node you opened. To compare nodes side by side, open one tab per node.

## Collect metrics with Prometheus

**Prometheus** is a monitoring tool. It reads numbers from your servers on a schedule. Each read is called a **scrape**.

Each node serves its `aerolvm_*` counters at `GET /v1/metrics`, in Prometheus's text format. That endpoint needs a token too.

Like the Metrics panel, this is per node. Add every server, worker, ingress and mixed node to Prometheus:

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: sandboxd
    metrics_path: /v1/metrics
    bearer_token: "<a viewer API token on every team, or SB_PAT_TOKEN>"
    static_configs:
      - targets:
          - server-1.example.com:21212
          - worker-1.example.com:21212
```

With [access control](/enterprise/sso/) on, give Prometheus a `viewer` API token for every team. Do not give it the admin token. Make the token like this:

```bash title="On your computer"
aerolvm token create --name prometheus --role viewer --team '*' --expires-in 90d
```

This token cannot create, run or delete anything. It is read-only, but not metrics-only. It can also read every team's sandbox details and audit records.

A node's copy of the token list can be out of date. The node then refuses API tokens with `503`. `/v1/metrics` is the one exception, so Prometheus keeps working.

Good first alerts to set up:

- `aerolvm_raft_apply_errors_total`: errors while the cluster saves a change.
- `aerolvm_ingress_route_desired_revision - aerolvm_ingress_route_applied_revision`: how far behind the ingress routes are.
- `aerolvm_create_queue_depth`: how many creates are in progress right now.
- `aerolvm_worker_lease_max_age_nanos`: how long ago the cluster last heard from the quietest worker.
- `aerolvm_image_pull_backoff_rejects_total`: image pulls refused because the last pull of that image failed.
- The `aerolvm_host_pressure_*` gauges: how much CPU, memory, disk and GPU each node has given out, and how much it has.

### Sandbox lifecycle metrics

These counters show what happens to sandboxes over time. Each one has a `key` label with a short, fixed list of values. None of them has a label per sandbox.

| Metric | `key` values | What it counts |
|---|---|---|
| `aerolvm_sandbox_stops_total` | `user_stop`, `idle`, `max_age`, `out_of_memory`, `disk_limit`, `crashed`, `program_exited`, `reconcile` | Sandboxes that stopped, by their [stop reason](/lifecycle/#why-a-sandbox-stopped). |
| `aerolvm_sandbox_starts_total` | `requested`, `restarted`, `failover` | Sandboxes that started again. `requested` is a call, including a wake. `restarted` is `restartOnFailure`. `failover` is a sandbox rebuilt after its node failed. |
| `aerolvm_sandbox_expired_total` | `idle`, `max_age`, `program_exited` | Sandboxes a lifecycle timer deleted, by the timer. `destroyAt` counts as `max_age`. `destroyAfterExitFor` counts as `program_exited`. |
| `aerolvm_sandbox_finished_total` | `success`, `failure` | Main programs that ended, by whether the exit code was `0`. A sandbox that goes down with another exit code counts as a `crashed` stop instead. So `failure` counts only programs watched for [`destroyAfterExitFor`](/lifecycle/#delete-when-the-program-ends). Those end while the sandbox keeps running. |
| `aerolvm_create_latency_by_start_seconds_bucket` | `warm`, `cold` (`key2` is the bucket) | How long successful creates took. `warm` means a warm pool, a parked container or a running V8-isolate group served the create. |

Do `crashed` or `out_of_memory` stops rise together with `restarted` starts? Then sandboxes crash again and again. The D2 Capability Matrix dashboard in [`setup/grafana`](https://github.com/aerol-ai/microvm/tree/main/setup/grafana) has a panel with all four counters.

`aerolvm_sandbox_events_dropped_total` has no labels. It counts runtime events that `sandboxd` dropped. A sandbox can hold at most 64 waiting events. That limit is reached only while a long step, such as a restart, holds the sandbox. `sandboxd` then drops that sandbox's oldest waiting event. Other sandboxes' events keep moving. The next reconcile pass reads the runtime and fixes the sandbox's status. A value above `0` means one sandbox sent a flood of events. The log names that sandbox.

## Profile the server with pprof

**pprof** is Go's built-in profiler. It shows where `sandboxd` spends its CPU time and what holds its memory. It also shows what each **goroutine** does. A goroutine is one task that a Go program runs side by side with others.

pprof is off by default. To turn it on, set `SB_ENABLE_PPROF=true`, then restart `sandboxd`. On Linux, the setting goes in `/etc/sandboxd/sandboxd.env`:

```bash title="On a node"
sudo systemctl restart sandboxd
```

The profiler then answers under `/debug/pprof/`, on each node's own API port (`21212` by default).

- **Only admins can read it.** Use the admin token, or an API token with the `admin` role. A request with no token gets `401`. Any other token gets `403`.
- **It is per node.** Caddy does not forward `/debug/` from your API domain. So open each node's own port, the same way as `/debug/vars`.
- **Turn it off when you are done.** Set `SB_ENABLE_PPROF=false`, and restart `sandboxd`. A profile shows the server's goroutines, memory and command line. Taking a profile also costs CPU while it runs.

Download a profile with your admin token. Then open the file with `go tool pprof`.

| Path | What you get |
|---|---|
| `/debug/pprof/` | A list of every profile. |
| `/debug/pprof/profile?seconds=30` | 30 seconds of CPU time. |
| `/debug/pprof/heap` | What holds the memory. |
| `/debug/pprof/goroutine?debug=2` | Every goroutine, as text. |

## Send metrics and traces with OpenTelemetry

**OpenTelemetry** (OTEL) is a standard way to send metrics and traces to a **collector**, a program that gathers them. A **trace** is a timed record of one request. Each timed step in it is a **span**.

Prometheus pulls numbers from the node. OpenTelemetry pushes them from the node, over OTLP/HTTP. OTLP is OpenTelemetry's own format.

| Setting | What it does | Default |
|---|---|---|
| `SB_OTEL_METRICS_ENABLED` | Sends metrics. | `false` |
| `SB_OTEL_METRICS_ENDPOINT` | Where to send metrics. Setting it also turns metrics on. If it is empty, `sandboxd` reads `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`. | empty |
| `SB_OTEL_METRICS_INTERVAL` | How often to send metrics. It must be above `0`. | `30s` |
| `SB_OTEL_TRACES_ENABLED` | Sends traces. | `false` |
| `SB_OTEL_TRACES_ENDPOINT` | Where to send traces. Setting it also turns traces on. If it is empty, `sandboxd` reads `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`. | empty |
| `SB_OTEL_TRACES_SAMPLE_RATIO` | The share of traces to keep, from `0` to `1`. | `0.05` |
| `OTEL_SERVICE_NAME` | The service name on every metric and span. | `sandboxd` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | The standard OpenTelemetry address. Setting it turns on both metrics and traces. | empty |

While metrics or traces are on, a value outside these limits stops `sandboxd` from starting. A sample setup:

```bash title="In the node's settings"
SB_OTEL_METRICS_ENDPOINT=http://otel-collector:4318/v1/metrics
SB_OTEL_METRICS_INTERVAL=30s
SB_OTEL_TRACES_ENDPOINT=http://otel-collector:4318/v1/traces
SB_OTEL_TRACES_SAMPLE_RATIO=0.05
OTEL_SERVICE_NAME=sandboxd
```

What `sandboxd` sends:

- **Metrics:** the same `aerolvm_*` counters, as `aerolvm.expvar.int64` and `aerolvm.expvar.float64`. The counter's own name is in the `metric` attribute. Map keys are in `key`, `key2` and so on.
- **Traces:** one span per API request. `sandboxd` reads the W3C trace context your app sends. W3C trace context is the standard header that carries a trace ID. So `sandboxd`'s spans join your app's traces. Each span is tagged with `http.route`, the status code, node ID, node role, service name and server version.

By default, `sandboxd` keeps 5% (`0.05`) of the traces it starts itself. A trace that comes from your app follows your app's choice. So a large cluster can send traces, and a burst of requests does not flood your collector.

### Traces reach the sandbox's helper program

`toolboxd` is the **helper program** inside a sandbox. It runs commands, files and terminals for the server. Calls reach it from the AerolVM API and from the Daytona, E2B and Runloop APIs.

- **Every call the server passes to `toolboxd` carries a W3C `traceparent` header.** With tracing on, it names the server's own span for the request. With tracing off, it is your app's trace context, passed on unchanged.
- **`toolboxd` writes one log line per such request** to the sandbox's output. The line has the `trace_id`, the method and the path. It never has the query. So you can find `toolboxd`'s side of a slow or failed call by its trace ID.
- **Only `traceparent` and `tracestate` go into the sandbox.** `baggage`, the free-form data your app attached, never does.
- **WASM and V8-isolate sandboxes have no helper program inside.** For those, the server's span is the only record.

## Grafana dashboards, alerts and runbooks

**Grafana** is a tool that draws charts from Prometheus numbers. The repository has ready-made files you can load:

- **Grafana dashboard:** [`setup/grafana/sandboxd-slo-dashboard.json`](https://github.com/aerol-ai/microvm/blob/main/setup/grafana/sandboxd-slo-dashboard.json). It shows create queue depth, create time, worker pressure, and how long ago each worker last reported. It shows ingress route lag and ingress shard health. It shows errors while the cluster saves a change, and the size of the cluster's saved records. It shows Caddy errors, and errors when a node passes a request on to another node. It also tracks secret decrypt health and image-pull storms. More dashboards are in the same folder.
- **Prometheus alert rules:** [`setup/prometheus/sandboxd-alerts.yml`](https://github.com/aerol-ai/microvm/blob/main/setup/prometheus/sandboxd-alerts.yml). They cover the health of the cluster's records, workers that stopped reporting, create backlog and worker pressure. They cover ingress route lag, Caddy errors, forwarding errors, image-pull storms and secret decrypt failures. They also cover identity and access: the admin token used from outside, a stale token list, and failing key fetches.
- **Alertmanager example:** [`setup/alertmanager/sandboxd-alertmanager-example.yml`](https://github.com/aerol-ai/microvm/blob/main/setup/alertmanager/sandboxd-alertmanager-example.yml). Alertmanager sends Prometheus alerts to people. This file shows how to route them.

Each alert links to a step-by-step runbook. See [Runbooks](/operational-runbooks/) for the full list.

## Set up sign-in for the dashboard

This section is for the person who runs the server. Company sign-in on the dashboard needs two things:

- [Access control](/enterprise/sso/) on.
- An **identity file** with a dashboard app for each provider you want as a button. The identity file lists your sign-in providers. [SSO](/enterprise/sso/) shows its format.

The steps below use your provider's own words. Pick the options with those names.

1. **Register a dashboard app at your provider.** Make it a single-page app. It is a public client, with no secret. It uses the authorization code flow with PKCE.
2. **Register the addresses.** Register `https://<api-domain>/ui` as its **redirect URI**: the address the provider sends you back to. Register `https://<api-domain>` as an **allowed origin**: an address the provider accepts browser calls from.
3. **Register the SSH tunnel addresses too, if people use one.** Add `http://localhost:21212/ui` as a redirect URI, and `http://localhost:21212` as an allowed origin. Without that origin, the page cannot finish the sign-in. It says "didn't sign you in (network_error)".
4. **Use `localhost`, not `127.0.0.1`.** Tell people to open the tunnel at `http://localhost:21212/ui`. A provider refuses a redirect URI it does not know. So a tab opened at `127.0.0.1` gets an "invalid redirect_uri" error.
5. **Put the groups claim in the ID token.** The **ID token** is the signed note from your provider that says who you are. The groups claim is the list of your groups in it. The dashboard asks for the scopes `openid email profile`. It adds `groups` when your provider lists that scope, as Dex does.
6. **Add the app's client ID to the identity file.** Put it in the issuer's `audiences`, and in `clients.dashboard`. Set `display_name` to the button's label.

Which providers get a button:

- Only issuers with `clients.dashboard` get a button. The buttons follow the order of the identity file.
- Workload issuers, such as GitHub Actions, get no button.
- Only the first Google issuer gets a button. Google allows one sign-in client per page.

What to set at each provider:

| Provider | What to set |
|---|---|
| Okta | A Single-Page app with Authorization Code and PKCE. Add `https://<api-domain>` as a Trusted Origin for CORS. Add a groups claim to the ID token. |
| Entra ID | An app registration with the "Single-page application" platform and the `/ui` redirect URI. Above 200 groups, Entra leaves the groups out. So bind on app roles. |
| Keycloak | A public client with the standard flow and PKCE (`S256`). Set Web origins to `https://<api-domain>`. For an SSH tunnel, add `http://localhost:21212` too. Add a Group Membership mapper to the ID token. Turn its **Full group path** off. With it on (the default), groups arrive as `/platform-admins`, and no group rule matches. |
| Google | Use `kind: google`. Make a "Web application" client. Add `https://<api-domain>` as an authorized JavaScript origin. Google uses its own sign-in button and pop-up. |
| Authentik | Share one application with the CLI. Use a Public OAuth2/OpenID provider with an RSA signing key. Add `https://<api-domain>/ui` as a Strict redirect URI. Authentik then allows browser calls from that address. The `profile` scope already puts `groups` in the ID token. |
| Zitadel | A User Agent app with PKCE, in the CLI app's project, with no other apps in it. Zitadel's own roles claim is an object the server cannot read. So add a flat `groups` claim with an Action. [SSO](/enterprise/sso/#zitadel-roles-as-groups) shows how. |
| Dex | A static client with `public: true` and the `/ui` redirect URI. Set `web.allowedOrigins` to `https://<api-domain>`. Quiet renewal needs Dex's experimental sessions (`DEX_SESSIONS_ENABLED=true`). Without them, people sign in again when the ID token expires. [SSO](/enterprise/sso/#dex) has the details. |

Authentik, Zitadel and Dex have not been tested against a live provider yet. [SSO](/enterprise/sso/#step-3-register-the-apps-at-your-provider) has the full steps for every provider.

How the sign-in works:

- **The browser talks to your provider directly.** It reads the provider's discovery document. It trades the sign-in code for a token. So your provider must allow browser calls from your dashboard's address. (Providers call this CORS.) Its token endpoint must also be on the same address as its issuer URL. The page's Content-Security-Policy allows only those addresses.
- **AerolVM's discovery document** is at `https://<api-domain>/.well-known/aerolvm-auth`. It lists the buttons, and the dashboard's HTTPS address (`ui_url`, from `SB_DOMAIN`). The page reads it to draw the sign-in box.
