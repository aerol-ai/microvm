[Install on a server](/getting-started/single-node-setup/) uses only the options most people need. This page lists the rest. Add any of them to the install command from that guide.

To see every option, run:

```bash
curl -fsSL https://aerolvm.aerol.ai | bash -s -- --help
```

## Main options

| Option | What it does | Default |
|---|---|---|
| `--domain <domain>` | The base domain for the API and sandbox links. | None. Without it the server uses [IP mode](#try-it-without-a-domain). |
| `--pat-token <token>` | The secret token your apps send with every request. | A random token, printed once. A new run keeps it. |
| `--dns-provider cloudflare` | The DNS provider used to get certificates. | None. Required with `--domain`. |
| `--dns-api-token <token>` | Your Cloudflare API token. | None. Required with `--domain`. |
| `--acme-email <email>` | Your email address, registered with Let's Encrypt as the contact for your certificates. | None |
| `--public-host <host-or-ip>` | The public address to use when you have no domain. | The server's first IP address |
| `--version <tag>` | The release to install, such as `v0.6.4`. | `latest` |
| `--idle-timeout-min <minutes>` | Stops running sandboxes after this many idle minutes. It skips sandboxes that set their own lifecycle. | `0` (off) |
| `--node-name <name>` | A friendly name for this server, shown in the cluster table of the [dashboard](/dashboard/). | Empty |
| `--no-start` | Installs and enables everything but leaves the server stopped. You rarely need it: `init` and `join` (below) do this for you, and start the server once it has the cluster's settings and keys. Not with `--local`. | Off: the server starts |

## Start or join a cluster

Two words end the installer's options: `init` and `join`. Everything after the word goes to `sandboxd init` or `sandboxd join`, which run once the install is done.

```bash
# The first node of a new cluster
curl -fsSL https://aerolvm.aerol.ai | sudo bash -s -- --domain cluster.example.com --pat-token your-secret-pat \
    --dns-provider cloudflare --dns-api-token your-cloudflare-api-token init

# Every other machine: set CLOUDFLARE_API_TOKEN, then paste the join command `aerolvm join-command` prints
export CLOUDFLARE_API_TOKEN=your-cloudflare-api-token
curl -fsSL https://aerolvm.aerol.ai | sudo bash -s -- --domain cluster.example.com \
    --dns-provider cloudflare --dns-api-token "$CLOUDFLARE_API_TOKEN" \
    join https://10.0.1.5:7003 --token <token> --ca-cert-hash sha256:<hash>
```

The join command that `aerolvm join-command` prints already carries the cluster's domain options, before the word `join`. Linux only. [Build a cluster](/cluster/create/) walks through it. `sudo sandboxd init --help` and `sudo sandboxd join --help` list every option.

## Upgrade an install

On a server whose release has `aerolvm upgrade` (v0.7.0 and later), upgrade from your computer:

```bash
aerolvm upgrade plan v0.7.0
aerolvm upgrade apply v0.7.0 --wait
```

It checks the files against the release's checksums, backs up the database, keeps the old files, and goes back to them if the new server does not come up. On a cluster it upgrades every node in a safe order; see [Upgrade a cluster](/cluster/upgrade/).

On an older release, or for a one-off, run the installer again with no options. It upgrades AerolVM to the newest release and keeps your settings:

```bash
curl -fsSL https://aerolvm.aerol.ai | sudo bash
```

- **The installer remembers your options.** Each run saves every option except secrets in `/etc/sandboxd/node.json`, which only root can read. Secrets, such as your token and your Cloudflare token, stay in the settings files the installer wrote. A new run reads them back, so your apps keep working with the same token.
- **Older servers work too.** On a server set up before `node.json` existed, the first new run reads the settings back from those files once, then writes `node.json`.
- **It starts the new version.** If the run installed a new release, or changed a setting, and the server is running, the installer restarts the server. It waits until the server answers, and only then starts Caddy.
- **It swaps the programs safely.** When the installed server has `sandboxd upgrade node`, the installer hands the swap to it, the same way `aerolvm upgrade` does: a database backup, the old files kept, and the old files back if the new server does not start.
- **Sandboxes keep running.** Containers, Firecracker VMs, WebAssembly and V8 isolate sandboxes keep running while the server restarts. The new server picks them up again.
- **Check the version** with `sudo sandboxd version`. It shows the release and never starts a second server.

## Change an install

Run the installer again with only the options you want to change. Options you pass win over the saved ones. Options you leave out keep their saved values.

- To install one release instead of the newest, add `--version v0.6.4`. The installer does not save it, so the next plain run goes back to the newest release.
- To turn a saved switch off, such as `--with-gvisor`, set it to `false` in `/etc/sandboxd/node.json`, then run the installer again.

This works on Linux. On macOS, a new run keeps your token, but pass your other options again.

<Aside type="caution">
Each run still rewrites the settings file, `/etc/sandboxd/sandboxd.env`, from the saved options. Settings you added to that file by hand are lost, such as `SB_IDENTITY_ENABLED`, `SB_ENTERPRISE_MODE` or the audit witness settings. Keep them in a file of your own instead (see below).
</Aside>

### Keep your own settings

The installer never touches a second settings file that you load with a systemd drop-in. Put the settings you add by hand in `/etc/sandboxd/local.env`, one `NAME=value` per line, and load it once:

```bash
sudo mkdir -p /etc/systemd/system/sandboxd.service.d
printf '[Service]\nEnvironmentFile=/etc/sandboxd/local.env\n' | sudo tee /etc/systemd/system/sandboxd.service.d/local.conf
sudo systemctl daemon-reload
sudo systemctl restart sandboxd
```

When a setting is in both files, the one in `local.env` wins. Do this before you run the installer again, so the restart it does already has your settings.

## Add more kinds of sandbox

A plain container is the default. You can add stronger walls between the sandbox and the server.

| Kind | How to turn it on | Notes |
|---|---|---|
| Containers on Docker | On by default | Works with the most images. |
| Containers on containerd | `--with-containerd-engine` | Runs containers through containerd (the engine Docker itself is built on) instead of Docker. Needs containerd's socket at `/run/containerd/containerd.sock`. |
| Image builds without root | `--buildkit-rootless` | Runs BuildKit as a normal user instead of root, and keeps it away from containerd. Needs the containerd engine. `--no-buildkit-rootless` goes back. |
| [gVisor](/gvisor-sandbox/) | `--with-gvisor` | Adds a user-space kernel: a layer that handles the sandbox's requests to the operating system, so they never reach the server's kernel directly. |
| [V8 isolate](/isolate-sandbox/) | `--with-isolate` | Installs Cloudflare's `workerd` and turns on JavaScript isolates. Off by default. |
| [Firecracker](/firecracker-sandbox/) | `--with-firecracker` | Each sandbox is a small virtual machine with its own Linux kernel. Needs `/dev/kvm`, which usually means a bare-metal server. See [Turn on Firecracker](#turn-on-firecracker). |
| [WebAssembly (WASM)](/wasm-sandbox/) | No flag. Set `SB_ENABLE_WASM=true`. | Runs WASI modules (WebAssembly programs with file and clock access). See [Turn on WebAssembly](#turn-on-webassembly). |
| Kata Containers | Not available | Create requests fail with `runtime not yet implemented on this build`. |

For example, this installs the server with gVisor:

```bash
curl -fsSL https://aerolvm.aerol.ai | sudo bash -s -- \
    --domain sandbox.example.com \
    --pat-token your-secret-pat \
    --dns-provider cloudflare \
    --dns-api-token your-cloudflare-api-token \
    --with-gvisor
```

<Aside type="caution" title="gVisor limits">
gVisor cannot run privileged containers, and it ignores the sandbox disk limit (`disk_gb`). It needs cgroup v2 (the Linux feature that limits CPU and memory) and systemd. Ubuntu 22.04 and newer have both. GPUs do not work with gVisor.
</Aside>

## Add GPU support

Add the flag for your GPU to the install command.

| GPU | Installer flag | What you need first |
|---|---|---|
| NVIDIA | `--with-nvidia-gpu` | NVIDIA drivers, with a working `nvidia-smi`. The flag installs the NVIDIA Container Toolkit and restarts Docker. |
| AMD | `--with-amd-gpu` | An `x86_64` server with the `amdgpu` kernel module loaded, so `/dev/kfd` exists. The flag installs AMD ROCm. |
| Apple Silicon | No flag | Works only in a [local install on a Mac](/getting-started/local-setup/), through Docker Desktop. |

A sandbox cannot use a GPU and gVisor at the same time. To create a sandbox with a GPU, see [GPU](/gpu-sandboxes/).

## Try it without a domain

You can install without `--domain` to try AerolVM on a bare IP address. The installer calls this IP mode.

```bash
curl -fsSL https://aerolvm.aerol.ai | sudo bash -s -- \
    --public-host 203.0.113.42 \
    --pat-token your-secret-pat
```

- The API is at `http://203.0.113.42:21212`. Open port `21212`, and port `80` for sandbox links.
- Sandbox links use paths instead of subdomains: `http://203.0.113.42/<sandbox-id>/` and `http://203.0.113.42/<sandbox-id>/proxy/<port>/`.
- [TLS ports](/tcp-vs-tls-ports/) (encrypted ports that share port `443`) need a domain. Use [TCP ports](/tcp-ports/) instead.

<Aside type="caution">
IP mode has no HTTPS. Your token and data cross the network unencrypted. Use it only for testing.
</Aside>

## For server operators

### What the installer sets up

- Puts `sandboxd` (the server) and `toolboxd` (the helper inside each sandbox) in `/usr/local/bin`. Change the folder with `--install-prefix`.
- Writes settings to `/etc/sandboxd/sandboxd.env`, readable only by root. After you edit it, run `sudo systemctl restart sandboxd`. A later run rewrites it, so keep your own settings in [a file of your own](#keep-your-own-settings).
- Saves the options you gave it, except secrets, to `/etc/sandboxd/node.json`, readable only by root. A new run with no options uses them (see [Upgrade an install](#upgrade-an-install)).
- Keeps state in `/var/lib/sandboxd`.
- Installs a custom Caddy build with TCP routing (`caddy-l4`) and the Cloudflare DNS plugin. Caddy is the web server that gets the certificates and sends each link to the right sandbox. Its config is `/etc/caddy/Caddyfile`. The Cloudflare token goes in `/etc/default/caddy`.
- Registers the systemd services `sandboxd`, `caddy` and `aerolvm-egress-gateway`, which handles sandboxes' outbound traffic. If `sandboxd` crashes, systemd restarts it after 5 seconds, up to 10 times in 5 minutes.
- Adds `sandboxd-healthcheck.timer`, which checks every 30 seconds that the server still answers. It restarts a server only after it has stopped answering for 3 checks in a row over at least 90 seconds, so a server that is just busy keeps running. It also starts again a server that systemd gave up on after 10 failed starts. A server you stopped yourself is left alone.
- Starts an SSH gateway, so you can [log in to sandboxes over SSH](/ssh-access/).
- Installs the tools for [cloud storage](/external-storage/): `fuse3`, `sshfs`, `nfs-common`, `rclone` and `mount-s3`.
- Turns off `rpcbind`, which comes with `nfs-common`, so nothing listens on port `111`. If `rpcbind` was already on the server, the installer leaves it as it is.

In domain mode, `caddy-l4` holds port `443`. It reads the hostname that each client sends at the start of a TLS connection (SNI) and routes on it. Normal HTTPS sites run on `127.0.0.1:8443` behind it. This is why [TLS ports](/tcp-vs-tls-ports/) work without extra setup.

Caddy gets exactly two certificates from Let's Encrypt: one for `sandbox.example.com` and one wildcard for `*.sandbox.example.com`. The wildcard covers every sandbox link. Caddy renews both on its own.

### Ports to keep closed

| Port | What uses it |
|---|---|
| `21212` | The AerolVM API. In domain mode, Caddy forwards HTTPS traffic to it, so keep it closed. |
| `2019` | Caddy's admin API. It listens on `127.0.0.1` only. Never open it. |
| `111` | `rpcbind`. The installer turns it off. Mounting an NFS version 3 share that locks files starts it again, on every address, until the server restarts. A server set up by an older installer may still run it. Turn it off with `sudo systemctl disable --now rpcbind.socket rpcbind.service`. |

The SSH gateway listens on `0.0.0.0:2220`. Change it with `SB_SSH_LISTEN_ADDR`.

### What the extra flags change

- `--with-gvisor` installs `runsc` and `containerd-shim-runsc-v1`, registers `runsc` in `/etc/docker/daemon.json`, and restarts Docker if that file changed. It also writes `SB_HOST_RUNTIMES=docker,gvisor`. Use `--runsc-path` to point at a `runsc` you already have.
- `--with-containerd-engine` installs the CNI networking plugins (`bridge`, `host-local`, `loopback`) in `/opt/cni/bin` and writes `SB_CONTAINER_ENGINE=containerd`. It also installs BuildKit, which builds images on containerd: `buildkitd` and `buildctl` in `/usr/local/bin`, and the `buildkit.service` unit. Each build step runs on the sandbox network (the `aerolvm0` bridge), so the same firewall rules apply to it as to a sandbox: no cloud metadata service and no ports on the machine. A BuildKit that is already there is kept; a `buildkit.service` that an earlier AerolVM installer wrote is updated to the sandbox network. Docker stays installed, so older sandboxes keep working. Not with `--local`: a local install always uses Docker.
- `--buildkit-rootless` runs BuildKit in its rootless mode instead. `buildkitd` runs as the `aerolvm-build` user, which owns nothing else on the machine, and build steps run as ids from a range of its own, never as root. BuildKit no longer writes into containerd: each build comes back to sandboxd as an image archive, and sandboxd adds it to containerd itself. Builds use their own network namespace, `aerolvm.build`, on the sandbox network, so the sandbox firewall rules apply to every download and every build step. Each build step gets a private link of its own, and a step cannot reach another build's steps, BuildKit itself or anything on the machine. The installer adds RootlessKit (checked against a pinned SHA-256), the `uidmap` package, the `aerolvm-build-net.service` unit and a rootless `buildkit.service`, and writes `SB_CONTAINERD_BUILDKIT_ROOTLESS=true`. Only root and the `aerolvm-build` user may run RootlessKit. On Ubuntu 23.10 and later the installer also adds an AppArmor profile that lets RootlessKit, and only RootlessKit, make a user namespace. A `buildkit.service` you wrote yourself is kept. A rootless BuildKit cannot see the images on this machine, so every `FROM` image comes from its registry: a Dockerfile that starts from a snapshot or an earlier build needs the root BuildKit. `--no-buildkit-rootless` puts the root BuildKit back.
- `--with-isolate` installs `workerd`, Cloudflare's program for running JavaScript, to `/usr/local/bin/workerd`. The version is pinned and its checksum is checked. It writes `SB_ENABLE_ISOLATE=true` and creates a `sandboxd-isolate` system user and the jail folder `/srv/isolate-jail`, so each workerd process runs locked down. Use `--workerd-path` to point at a `workerd` you already have.
- `--with-firecracker` first checks that the server has `/dev/kvm`, and stops before it installs anything if not. Then it installs `firecracker` and `jailer` to `/usr/local/bin`, a guest Linux kernel to `/var/lib/sandboxd/firecracker/vmlinux` (`/usr/local/lib/aerolvm-firecracker/vmlinux` with `--privilege-mode split`), and `skopeo`, `umoci` and `e2fsprogs`, which turn container images into virtual machine disks. The versions are pinned and every download's checksum is checked. It creates a `sandboxd-jailer` system user, so each virtual machine runs without root rights, and writes `SB_ENABLE_FIRECRACKER=true`. Not with `--local`.

### Run the server without root

`--privilege-mode split` runs the AerolVM server as a normal user with no special rights. A small helper, `aerolvm-rootd`, runs as root and does only the work that needs root: sandbox networks, the firewall, cgroups, the files a container needs, and external storage mounts. The server asks the helper over a local socket, and the helper checks every request itself. A bug in the code that reads requests from the internet then stops at that user, not at root.

It needs `--with-containerd-engine`. It turns on `--buildkit-rootless`, because a root BuildKit writes into containerd past the helper's checks. It works with `--with-isolate` and `--with-firecracker`: the helper runs each V8 isolate group in its jail and each virtual machine through `jailer`, never without them. In split mode the installer also writes the settings the helper and the server must share, so both use the same programs, folders and users: `SB_ISOLATE_USE_JAIL=true`, `SB_FIRECRACKER_USE_JAILER=true`, `SB_JAILER_BINARY`, `SB_FIRECRACKER_BINARY`, `SB_JAILER_CHROOT_BASE` and `SB_FIRECRACKER_KERNEL`. The guest kernel goes to `/usr/local/lib/aerolvm-firecracker/vmlinux`, a folder only root can write, because the helper puts it into every virtual machine's jail. Firecracker's warm pool of paused virtual machines runs in split mode too: the helper runs each pooled virtual machine under its own slot name. The default, `--privilege-mode single`, keeps the server running as root, as before. [Run the server without root](/enterprise/privilege-mode/) explains what split protects against, its speed and its limits.

What the installer sets up in split mode:

- The `sandboxd` user, uid `65531`, which the server runs as. It also makes the `aerolvm` group (only its members may reach the helper's socket), the `aerolvm-mounts` user (external storage tools run as this user, never as root), and the `aerolvm-wasm` group, gid `61000`.
- The helper in `/usr/local/lib/aerolvm-rootd`. The installer puts it there only after the new `sandboxd` checks its release signature against the keys built into `sandboxd`, and installs its own checked copy. A helper that fails the check stops the install. A server built with `--build-from-source` gets the helper built from the same code, with no signature.
- `aerolvm-rootd.service`, which runs the helper as root. Its own settings are in `/etc/sandboxd/rootd.env`, readable only by root.
- A new `sandboxd.service`: it runs as `sandboxd`, with no capabilities, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes` and `PrivateTmp=yes`, and it may write only to `/var/lib/sandboxd`, `/run/sandboxd` and the cluster's certificate folders. With `--with-firecracker` it may also write under `/srv/jailer`, but only in the folder the helper makes for each virtual machine's files: every other folder there stays root's. It starts after the helper and needs it.
- Before each start, the helper's program gives the `sandboxd` user every file that root left in the server's folders. The first start after the switch does this for the whole data folder. Later starts fix only the files that root tools wrote since, such as `sandboxd join`. It never follows a link and never changes another user's file. It does not go into a mount: it skips a folder the kernel marks as the top of a mount (Linux 5.8 and later, which also catches a bind mount from the same disk) or that sits on another disk.
- Small systemd drop-ins named `privilege-split.conf`, so the server can reach the egress gateway and the rootless BuildKit socket. BuildKit's socket gets an ACL (an extra permission entry for one user) for the `sandboxd` user. The user never joins the `aerolvm-build` group. ACLs on `/run` need a kernel built with tmpfs ACLs, as Ubuntu's and Amazon Linux's are. On a kernel without them the installer warns you: sandboxes still work, but image builds fail.
- `SB_PRIVILEGE_MODE=split` in `sandboxd.env`, with Docker turned off for the server (`SB_DOCKER_ENABLED=false`).

Upgrades work as before when you run the installer again or `sudo sandboxd upgrade node`. The upgrade installs a new helper only after the same signature check, and only if it is not older than the one running. Upgrades over the API (`aerolvm upgrade apply`) are off on a split server (`SB_REMOTE_UPGRADE=false`), because starting the upgrader needs root.

Running sandboxes keep running when you switch a server to split mode, when the server restarts, and when the helper restarts. `--privilege-mode single` switches back: the server's files go back to root, the helper stops, and the server runs as root again. The users and the helper's program stay on the server for a later switch.

A switch either way removes the old upgrade records in `/var/lib/sandboxd/upgrade`. Split mode never uses them, and the server, running without root, could have written them. A switch back to single also removes the server's runtime folders in `/run` (it makes them again when it starts) and every symbolic link in its data folders, before the root server starts.

<Aside type="caution">
Switching back to single gives root the server's database as the server wrote it in split mode. If you think the server was broken into, rebuild the machine instead of switching it back. The installer prints this as a warning when it switches a server back.
</Aside>

### Turn on Firecracker

The server needs `/dev/kvm`. That means a bare-metal server, or a virtual machine with nested virtualization turned on. On AWS, pick a `.metal` instance type. Check before you install. This needs no `sudo`:

```bash
ls -l /dev/kvm
```

If it is missing on your own hardware, turn on Intel VT-x or AMD-V in the BIOS, then load the KVM module. Loading it needs root. On AMD, use `kvm_amd`:

```bash
sudo modprobe kvm_intel
```

Then add `--with-firecracker` to the install command. The installer runs as root, so pipe it to `sudo bash`:

```bash
curl -fsSL https://aerolvm.aerol.ai | sudo bash -s -- \
    --domain sandbox.example.com \
    --pat-token your-secret-pat \
    --dns-provider cloudflare \
    --dns-api-token your-cloudflare-api-token \
    --with-firecracker
```

Without `/dev/kvm` the installer stops before it installs anything, and tells you what to change. Running it again is safe: it downloads nothing that is already in place. Pass `--with-firecracker` on every later run too. A run without it turns Firecracker off.

To use your own guest kernel, put it in place before you install. The installer keeps a kernel it finds there, and downloads its own only when there is none. The folder belongs to root, so each step needs `sudo`:

```bash
sudo install -D -m 0644 vmlinux /var/lib/sandboxd/firecracker/vmlinux
sudo install -m 0644 vmlinux.config /var/lib/sandboxd/firecracker/vmlinux.config
sudo grep -x CONFIG_VMGENID=y /var/lib/sandboxd/firecracker/vmlinux.config
```

The last command must print `CONFIG_VMGENID=y`. If it prints nothing, the installer refuses the kernel.

To set Firecracker up by hand instead, first load your own settings file (see [Keep your own settings](#keep-your-own-settings)). Then run these from a folder that holds `firecracker`, `jailer`, `vmlinux` and `vmlinux.config`. Every step but `id` changes the system, so it needs `sudo`:

```bash
sudo install -m 0755 firecracker jailer /usr/local/bin/
sudo install -D -m 0644 vmlinux /var/lib/sandboxd/firecracker/vmlinux
sudo install -m 0644 vmlinux.config /var/lib/sandboxd/firecracker/vmlinux.config
sudo apt-get install -y skopeo umoci e2fsprogs
sudo useradd --system --no-create-home --shell /usr/sbin/nologin --user-group sandboxd-jailer
printf 'SB_ENABLE_FIRECRACKER=true\nSB_JAILER_UID=%s\nSB_JAILER_GID=%s\n' \
    "$(id -u sandboxd-jailer)" "$(id -g sandboxd-jailer)" | sudo tee -a /etc/sandboxd/local.env
sudo systemctl restart sandboxd
```

The `sandboxd-jailer` user keeps each virtual machine from running as a login user. If your files live elsewhere, settings such as `SB_FIRECRACKER_BINARY`, `SB_JAILER_BINARY` and `SB_FIRECRACKER_KERNEL` point to them. The [cluster setup](/cluster/aws/#step-5-turn-on-more-kinds-of-sandbox-optional) does all of this for you with `with_firecracker = true`. Next, build images with [Firecracker templates](/firecracker-templates/).

### Turn on WebAssembly

Add `SB_ENABLE_WASM=true` to `/etc/sandboxd/sandboxd.env` and restart `sandboxd`. The server looks for modules in `/var/lib/sandboxd/wasm/modules` (change it with `SB_WASM_MODULES_DIR`). See [WASM modules](/wasm-modules/).

### Where downloads come from

Most files the installer downloads live on GitHub. If GitHub fails, the installer gets the same file from a copy we keep, called the mirror. The mirror is a public bucket at `https://aerolvm-downloads.s3.us-east-1.amazonaws.com`.

For each file, the installer tries these places in order and stops at the first one that works:

| Order | Where | Notes |
|---|---|---|
| 1 | The file's own home | GitHub for AerolVM releases, Caddy, CNI plugins, BuildKit, `workerd` and Firecracker. |
| 2 | The mirror | AerolVM releases are under `aerolvm/<tag>/`, with the same file names as on GitHub. Other projects' files are under `deps/<project>/<version>/`. |
| 3 | The project's own download site | Only where one exists. The custom Caddy build falls back to Caddy's build service. |

A place that fails is retried twice, a few seconds apart, and then the installer moves on. So a GitHub outage costs seconds, not minutes. The last place is retried for longer, because there is nothing after it.

The mirror changes where a file comes from, not how it is checked. Every file is checked the same way, wherever it came from:

- AerolVM release files must match the release's `checksums.txt`.
- Every other file must match a SHA-256 hash written into the installer.

If a file does not match, the installer stops. It does not try the next place.

To use your own mirror, pass `--download-mirror <url>` or set `AEROL_DOWNLOAD_MIRROR`. The flag wins if you set both. Your mirror must use `https` and the same folder layout. To turn the mirror off, pass `--download-mirror off`, or set `AEROL_DOWNLOAD_MIRROR` to an empty value.

<Aside>
If you install the newest release and GitHub fails part way through, some files can come from GitHub's newest release and some from the mirror's. They may then be from different releases, and the checksum check stops the install. Run the installer again, or pass `--version <tag>` so every file comes from one release.
</Aside>

The [cluster setup](/cluster/aws/#firecracker-files-and-the-download-mirror) downloads Firecracker from GitHub on its own. To use the mirror there too, set `binary_url` and `jailer_url` in its `firecracker` block to the mirror's copies.

### More installer options

| Option | What it does |
|---|---|
| `--download-mirror <url\|off>` | Where to get a file when GitHub fails. Defaults to the public mirror, or to `AEROL_DOWNLOAD_MIRROR` when that is set. `off` turns it off. See [Where downloads come from](#where-downloads-come-from). |
| `--acme-ca <url>` and `--acme-ca-root <pem>` | Get certificates from your own ACME server (the protocol Let's Encrypt uses) instead of Let's Encrypt. For private networks that cannot reach the internet. |
| `--tls-issuer internal` | Caddy's own certificate authority signs every certificate. No DNS provider needed, but clients must trust Caddy's root certificate. For labs. |
| `--caddy-storage-s3` and the `--caddy-storage-s3-*` options | Share certificates between several servers through an S3 bucket. |
| `--ingress-proxy-routing` | Route sandbox links without a Caddy route for each sandbox. Then creating or deleting a sandbox, or opening a port, does not make Caddy reload and drop new connections ([TLS ports](/tcp-vs-tls-ports/) still do). On by default with `--domain`. Does nothing without a domain. |
| `--no-ingress-proxy-routing` | Domain mode only. Turns that routing off: Caddy gets a route for each sandbox, as before. With neither option, a `--domain` install gets routing on and an install without a domain gets it off. A later run of the installer without this option turns routing back on. In the [cluster setup](/cluster/aws/), `default_ingress_proxy_routing` picks: unset passes neither option, `true` passes `--ingress-proxy-routing`, `false` passes this one. |
| `--pat-scope <any\|host>` | Where the server's token (`--pat-token`) works. `any`, the default, keeps today's behavior. `host` accepts it only on the server itself (`127.0.0.1:21212`) and from other cluster servers. Everyone else must sign in with SSO or use a named API token. Caddy then talks to the server through a private socket. [Enterprise mode](/enterprise/enterprise-mode/) requires `host`. Turn it on only after every server runs a release that has it, and see the caution above about settings you added by hand. See [SSO](/enterprise/sso/#step-5-limit-the-server-token-to-the-server). |
| `--privilege-mode <single\|split>` | `split` runs the server as a normal user with no rights, and a small root helper does the work that needs root. Needs `--with-containerd-engine`. See [Run the server without root](#run-the-server-without-root). Default `single`. |
| `--l4-proxy-protocol` | Domain mode only. Passes each caller's real address through Caddy to the server, so audit records and alerts show it instead of `127.0.0.1`. Off by default. |
| `--lb-health-port <port>` | Domain mode only. For a server behind a load balancer: serves `/health` on this port over plain HTTP for the balancer's health check. It answers `200` only when the whole path a user takes works (Caddy, its port 443 and the AerolVM server), so the balancer stops sending users to this server while any part is down. Open the port to the load balancer only. Off by default. See [Put a load balancer in front](/cluster/aws/#step-6-add-a-load-balancer-for-production). |
| `--build-from-source` | Build `sandboxd` and `toolboxd` from the current checkout instead of downloading them. |
