A gVisor sandbox is a container with an extra wall around it. In a normal container, programs talk straight to the server's Linux kernel, the core of the operating system. In a gVisor sandbox, a program called `runsc` sits in between. It catches every request the program makes to the kernel (a system call) and decides what to pass on.

Choose gVisor for code you do not trust, such as code written by an AI model. It protects the server better than a normal container. It is lighter than a full virtual machine like [Firecracker](/firecracker-sandbox/). Most common programs run fine under gVisor.

gVisor works on any normal Linux server or cloud VM. It does not need bare-metal hardware.

## What the server needs

The server operator installs gVisor with the `--with-gvisor` installer flag. The server's Linux must use cgroup v2 and systemd (cgroup v2 is how Linux limits a program's CPU and memory). Ubuntu 22.04 and newer have both by default. See [For server operators](#for-server-operators).

## Create a gVisor sandbox

Add `runtime: "gvisor"` to a normal create call. Everything else works like any other sandbox.

## Set resources and auto-stop

CPU, memory and lifecycle timers work the same as on any sandbox. This one gets 2 CPU cores and 1 GB of memory. It stops after 30 idle minutes and is deleted when it is 4 hours old. Timer values are in nanoseconds, except in Go, which uses `time.Duration`.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({
      image: "ubuntu:22.04",
      runtime: "gvisor",
      cpu: 2,
      memoryMB: 1024,
      lifecycle: {
        stopIfIdleFor: 30 * 60 * 1_000_000_000,     // 30 minutes
        destroyAtAge:  4 * 60 * 60 * 1_000_000_000, // 4 hours
      },
    });
    ```
  </TabItem>
  <TabItem label="Python">

    sandbox = client.create(

            "stopIfIdleFor": 1_800_000_000_000,  # 30 minutes
            "destroyAtAge": 14_400_000_000_000,  # 4 hours
        },

  </TabItem>
  <TabItem label="Go">

## Good to know

- **No GPU.** A sandbox can use gVisor or a GPU, not both. Asking for both fails.
- **No privileged containers.** gVisor refuses containers that ask for full access to the server.
- **Disk limits are not enforced.** gVisor ignores `diskGB`, so disk use is limited only by the server.
- **Some programs may not run.** gVisor implements most, but not all, of the Linux kernel's features. If a program fails only under gVisor, try it in a normal sandbox.

## For server operators

Add `--with-gvisor` to the install command (see [Install on a server](/getting-started/single-node-setup/)). The installer then:

- downloads `runsc` and checks its SHA-512 checksum, unless it is already on the `PATH`;
- registers `runsc` with Docker in `/etc/docker/daemon.json`, and restarts Docker if that file changed;
- installs the `containerd-shim-runsc-v1` helper, so the containerd engine (another container engine AerolVM can use) can run gVisor too;
- writes `SB_HOST_RUNTIMES=docker,gvisor`, so the server reports that it can run gVisor sandboxes.

Use `--runsc-path /path/to/runsc` with `--with-gvisor` to register a `runsc` you installed yourself.

On a cluster, set `with_gvisor = true` on each worker in `terraform.tfvars` (see [Cluster setup](/cluster-setup/)). Workers without it keep running normal containers only.

If a create fails with `runtime "gvisor" not supported on this host`, the server does not list gVisor in `SB_HOST_RUNTIMES`. Add it there and restart the server.
