---
title: gVisor kernel probe
description: Run one probe under Docker and under gVisor, and see how much less code can learn about your server under gVisor.
---

In this tutorial you run the same small Python program twice: once in a normal Docker sandbox and once in a gVisor sandbox. The program reads files that describe the server's kernel and hardware. Under Docker it sees the real values. Under gVisor it sees made-up values, or nothing at all.

The kernel is the core of the operating system. In a Docker sandbox, code talks straight to your server's real kernel. An attacker who learns the exact kernel version can look up known bugs for it. gVisor puts its own kernel, written as a normal program, in between. So code in the sandbox never talks to the real one.

This is a safe demo. The probe only reads information. It contains no attack code.

## What the probe checks

| Check | Command | What it shows |
|---|---|---|
| `capabilities` | `grep ^CapEff: /proc/self/status` | Which special Linux permissions the program has |
| `kernel_version` | `uname -r` | The kernel's version number |
| `kernel_build` | `cat /proc/version` | How and when the kernel was built |
| `physical_memory_buddy` | `cat /proc/buddyinfo` | How the server's physical memory is laid out |
| `hardware_io_regions` | `cat /proc/iomem` | The server's hardware address map |
| `net_stats` | `cat /proc/net/sockstat` | Counts of open network connections |

The only change between the two runs is one setting: `runtime: "docker"` or `runtime: "gvisor"`. The runtime is the technology that runs and walls off the sandbox.

## What you need

- **An AerolVM server with gVisor.** gVisor runs on Linux. The server operator adds it with the `--with-gvisor` installer flag. See [gVisor](/gvisor-sandbox/).
- **`SB_API_URL` and `SB_PAT_TOKEN`** set in your terminal, as shown in [SDK setup](/sdk-setup/).
- **Node.js 20 or newer.**

### Step 1: Set up a project

```bash
mkdir gvisor-probe && cd gvisor-probe
npm init -y
npm pkg set type=module
npm install @aerol-ai/aerolvm-sdk
```

### Step 2: Save the Docker version

Save this as `dockerRuntime.ts`. Both versions are also in the [examples repository](https://github.com/aerol-ai/aerolvm-examples/tree/main/customer-facing/gVisor-kernel).

```ts
import { MicroVM } from "@aerol-ai/aerolvm-sdk";
import { writeFile } from "node:fs/promises";

const apiUrl = process.env.SB_API_URL ?? "http://127.0.0.1:21212";
const patToken = process.env.SB_PAT_TOKEN;

if (!patToken) {
  throw new Error("Set SB_PAT_TOKEN before running this example.");
}

const probePython = `import json
import subprocess

# These checks probe kernel information exposure.
# In a Docker (runc) container the process shares the real host kernel, so
# /proc surfaces the true kernel version, hardware memory layout, and I/O
# regions - everything an attacker needs to fingerprint and target known CVEs.
# Under gVisor the same reads return synthetic data from the Sentry user-space
# kernel: the host kernel version, memory layout, and hardware topology are
# never visible inside the sandbox.
checks = [
    ("capabilities",          "sh -lc 'grep ^CapEff: /proc/self/status'"),
    ("kernel_version",        "uname -r"),
    ("kernel_build",          "cat /proc/version"),
    ("physical_memory_buddy", "cat /proc/buddyinfo"),
    ("hardware_io_regions",   "cat /proc/iomem"),
    ("net_stats",             "cat /proc/net/sockstat"),
]

results = []
for name, command in checks:
    completed = subprocess.run(command, shell=True, capture_output=True, text=True)
    results.append(
        {
            "check": name,
            "command": command,
            "exitCode": completed.returncode,
            "stdout": completed.stdout.strip(),
            "stderr": completed.stderr.strip(),
        }
    )

payload = {"runtime": "docker", "results": results}

with open("/workspace/run/probe-report.json", "w", encoding="utf-8") as handle:
  json.dump(payload, handle, indent=2)

print(json.dumps(payload, indent=2))
`;

async function main() {
  const client = new MicroVM({ apiUrl, patToken });
  const sandbox = await client.create({
    image: "python:3.12-bookworm",
    runtime: "docker",
    networkBlockAll: true,
    cpu: 0.5,
    memoryMB: 256,
    diskGB: 4,
  });

  try {
    await sandbox.exec("mkdir -p /workspace/run");
    await sandbox.uploadFile("/workspace/run/probe.py", probePython);

    const result = await sandbox.exec({
      command: "python /workspace/run/probe.py",
      timeoutSeconds: 10,
    });

    const report = new TextDecoder().decode(
      await sandbox.downloadFile("/workspace/run/probe-report.json"),
    );

    const payload = {
      stdout: result.stdout,
      stderr: result.stderr,
      exitCode: result.exitCode,
      report: JSON.parse(report),
    };

    await writeFile(
      "docker-kernel-probe-result.json",
      `${JSON.stringify(payload, null, 2)}\n`,
    );

    console.log(JSON.stringify(payload, null, 2));
  } finally {
    await sandbox.destroy();
  }
}

main().catch((error) => {
  console.error(error);
  process.exitCode = 1;
});
```

The script creates a sandbox with no internet access (`networkBlockAll: true`). It uploads the probe, runs it, downloads the report and deletes the sandbox. The `finally` block deletes the sandbox even if the probe fails.

### Step 3: Make the gVisor version

Copy the file to `gVisorRuntime.ts`. Then change three lines:

```ts
payload = {"runtime": "gvisor", "results": results}   // in the Python text
runtime: "gvisor",                                    // in client.create()
"gvisor-kernel-probe-result.json",                    // in writeFile()
```

The examples repository's version also gives the sandbox `cpu: 0.25` instead of `0.5`. That does not change the result.

### Step 4: Run both

```bash
npx tsx dockerRuntime.ts
npx tsx gVisorRuntime.ts
```

Each run prints its report and saves it: `docker-kernel-probe-result.json` and `gvisor-kernel-probe-result.json`.

## Compare the results

These results come from one of our test servers, an AWS machine. You can read the full files: [Docker result](https://github.com/aerol-ai/aerolvm-examples/blob/main/customer-facing/gVisor-kernel/docker-kernel-probe-result.json), [gVisor result](https://github.com/aerol-ai/aerolvm-examples/blob/main/customer-facing/gVisor-kernel/gvisor-kernel-probe-result.json).

| Check | Under Docker | Under gVisor |
|---|---|---|
| `capabilities` | `CapEff: 00000000a80425fb` | `CapEff: 00000000a80405fb` (almost the same) |
| `kernel_version` | `7.0.0-1004-aws`: the server's real kernel | `4.19.0-gvisor`: a made-up version |
| `kernel_build` | The real build line, with the compiler used | `Linux version 4.19.0-gvisor #1 SMP Sun Jan 10 15:06:54 PST 2016`: also made up |
| `physical_memory_buddy` | The server's real memory layout | No such file |
| `hardware_io_regions` | The server's hardware address map | No such file |
| `net_stats` | Connection counts | No such file |

What this means:

- **Under Docker**, code can find out exactly which kernel your server runs, and details about its memory and hardware. That is the first step in aiming a known kernel bug at your server.
- **Under gVisor**, the same code talks to gVisor's own kernel instead. It sees a fake version and cannot read the hardware details at all. Your server's real kernel never gets the requests.

So gVisor is a better wall for code you do not trust, such as code your users send or code an AI writes.

## Good to know

- **gVisor has limits.** It cannot run privileged containers, it does not enforce `diskGB`, and it does not work with GPUs. See [gVisor](/gvisor-sandbox/).
- **Some programs act differently under gVisor.** Its kernel does not have every feature of the real Linux kernel. Test your workload under gVisor before you switch to it.
