A sandbox's container is ephemeral. Files written into the container's writable layer (`/tmp`, the working directory, anywhere not on a mount) live only as long as the container itself. If the container is destroyed - by an explicit `Destroy`, by a host crash, or by an owner-node failover in cluster mode - that data is gone.

This is the same model used by GitHub Codespaces, Daytona workspaces, and Coder workspaces. Persistent state lives on a separate, declared volume; the container is treated as cattle.

## What survives, what does not

| Asset | Single-node `Destroy` | Single-node host crash | Cluster-mode owner failover |
|---|---|---|---|
| Container writable layer | Lost | Lost | Lost |
| Mounted volumes (S3, NFS, SSHFS, rclone) | Survive (external) | Survive (external) | Survive (external) |
| Sandbox ID | Reused on next `Create` | Preserved if record persisted | Preserved (recreated on new owner) |
| Environment variables, image, resource limits | N/A | Restored on `Start` | Restored from replicated spec |
| Idle lifecycle policy | N/A | Restored on `Start` | Restored from replicated spec |
| Exposed ports (preview, TCP, TLS) | Removed | Restored on `Start` | Re-exposed on the new owner from replicated intent |
| Caddy routes | Removed | Restored on `Start` | Re-created on the new owner when ports are re-exposed |
| Host port number | N/A | Same host, same port | TCP host ports are replayed from replicated route metadata when available |
| Public URL | Removed | Restored on `Start` | HTTP/TLS URLs stay derived from the sandbox ID; TCP URLs stay stable when the replicated host port can be rebound |

## Make workspace state durable

Mount external storage at the path you want to keep across container lifetimes. The mount is established by the host (not the sandbox), so credentials never enter the container, and the data persists independently of any single sandbox or node.

Anything written under `/workspace` outlives the container. Anything written elsewhere does not. See [External Storage](/external-storage) for the full mount surface (S3, NFS, SSHFS, rclone).

## Cluster-mode failover

When `SB_ENABLE_CLUSTER=true`, the cluster replicates each sandbox's create spec (image, env, resource limits, mounts, lifecycle) and every exposed-port route intent into a Raft log. HTTP/TLS routes record their public URL metadata; raw TCP routes also record the selected `hostPort` so the cluster ingress can keep a stable endpoint. If the owner node leaves the cluster and stays gone past the dead-owner grace period, the leader reassigns every placement that carries a spec to a live node. The new owner detects the reassignment within a few seconds, recreates the sandbox locally with the original ID, and re-runs `ExposePort` for each replicated route intent.

The recreated sandbox is a **fresh container** with the same identity:

- Same sandbox ID - existing client references keep working.
- Same image, env, resource limits, mounts, lifecycle policy.
- Mounted volumes attach to the same external sources, so workspace state under mount targets is intact.
- Container writable layer is empty - any in-container files outside mounts are lost.
- Same set of exposed ports - re-issued automatically on the new owner. HTTP/TLS URLs stay stable because they are derived from the sandbox ID and domain. Raw TCP keeps the same host port when the new owner can bind the replicated port; if that local port is already occupied, the exposure must be retried or inspected by the operator.

If you ever need to re-expose a port manually (for example, the original `ExposePort` call landed during a network partition and was dropped), the API is idempotent:

## Cluster network security

Cluster traffic uses two transports:

- **Gossip** (`SB_GOSSIP_BIND_ADDR`, default `:7001`) — SWIM membership and capacity dissemination.
- **Raft** (`SB_RAFT_BIND_ADDR`, default `:7000`) — placement-map consensus.

When a node successfully joins gossip, it is added to the Raft configuration as a voter until `SB_CLUSTER_MAX_AUTO_VOTERS` is reached, then as a non-voter. **Anyone who can reach these ports can still join the cluster and influence placement replication.** Run them on a private network the operator controls (VPC peering, WireGuard mesh, dedicated cluster subnet); never expose them to the public internet.

To authenticate gossip and reject foreign joiners, set `SB_GOSSIP_SECRET_KEY` to a base64-encoded 16, 24, or 32-byte key (AES-128/192/256-GCM). The same key must be configured on every node in the cluster.

```sh
# Generate a 32-byte key once and distribute it to every node.
openssl rand -base64 32

# Then on each node:
export SB_GOSSIP_SECRET_KEY="<the-base64-key>"
```

When `SB_GOSSIP_SECRET_KEY` is unset, the daemon logs a warning at boot. Raft itself remains plaintext today; the gossip key is what gates the join, so a peer that can't decrypt the gossip handshake never reaches Raft. Wrap Raft in TLS at the network layer (e.g., a private overlay) for defense in depth.

## Limitations

- **Pre-cluster sandboxes are backfilled at boot.** Sandboxes created before the cluster was enabled, or before spec replication shipped, get their spec, exposed-port intents, and registry credentials written into the Raft log on the next daemon start under cluster mode. Registry credentials persisted before the encrypted column existed are absent from the row and won't be backfilled — those sandboxes rely on the new owner already having the image cached, or a fresh `Create` to re-seed credentials.
- **Ingress has a convergence window.** Public HTTP/TLS URLs and raw TCP host ports are replicated through the cluster route map, but non-owner ingress routes refresh periodically. Immediately after failover or a new exposure, a backend can briefly return 404/502 until it has reconciled.
- **Writable-layer state is not replicated.** Treat anything outside a mount as cache. If you need it after a crash, write it to a mount.
- **Single-node deployments inherit the same model.** A host crash loses the writable layer just as a failover does. Mount external storage for anything that must survive.

## Recommended pattern

1. Pick the directory your workload writes durable state to (often a project root, a database data dir, or a model cache).
2. Declare it as a mount target at `Create` time.
3. Treat everything else inside the container as scratch.
4. In cluster mode, tolerate a short ingress convergence window after failover - the sandbox ID and exposed port routes survive, but the recreated container is fresh.

This keeps the durability story identical across single-node, cluster-mode, and any future runtime: the spec describes the sandbox, the mounts hold the data, the container is replaceable.
