A [WASM sandbox](/wasm-sandbox/) runs a module: a compiled `.wasm` program. You choose it with `moduleRef` when you create the sandbox. This page covers where modules come from and how the server stores them.

## How the server finds a module

The server reads `moduleRef` and checks these kinds of names in order:

1. **Standard module name**, such as `python` or `javascript`. Your operator puts these on every server. This is the easiest choice: no upload and no file paths. See [Use a standard module](#use-a-standard-module).
2. **Registry reference**, such as `oci://registry.example.com/team/app:v1`. The server downloads the module from a container registry with your credentials and keeps a copy. See [Bring your own module](#bring-your-own-module).
3. **Catalogue ID**: the `id` that `createWasmModule` returned. See [Register a module on the server](#register-a-module-on-the-server).
4. **File on the server**: `file:///path/to/module.wasm`, or a bare file name inside the server's modules folder. For self-hosted servers.

Whatever you pass, the server checks that the file is a core WASI preview 1 (`wasip1`) module. WASI is the standard set of system functions a WASM program uses for files, the clock and the network. The server rejects WASI components, a newer module format. It then records the module's digest (a hash that names the exact bytes) and ties it to the sandbox. A restart or a move to another server runs exactly the same bytes.

## Use a standard module

Pass the name your operator gave the module. There is nothing to upload.

A standard module name always wins over a file with the same name in the modules folder. A stray file cannot replace the real module.

## Bring your own module

First compile your program to a core `wasip1` module:

- **Go:** `GOOS=wasip1 GOARCH=wasm go build -o app.wasm`
- **Rust:** `cargo build --target wasm32-wasip1`

Then upload it with `pushWasmModule`, using your own registry credentials. The server checks the file and passes it on to the registry. It never stores the file itself. It returns the `oci://` reference to use when you create a sandbox.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    import { readFile } from "node:fs/promises";

    const wasm = await readFile("app.wasm");
    const pushed = await client.pushWasmModule({
      name: "tenant/app",
      tag: "v1",
      module: new Uint8Array(wasm),
      registryUsername: process.env.AOCR_USER,
      registryToken: process.env.AOCR_TOKEN!,
    });
    await client.create({ image: pushed.moduleRef, moduleRef: pushed.moduleRef, runtime: "wasm" });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import os

    with open("app.wasm", "rb") as f:
        module = f.read()
    pushed = client.push_wasm_module({
        "name": "tenant/app",
        "tag": "v1",
        "module": module,
        "registryUsername": os.environ["AOCR_USER"],
        "registryToken": os.environ["AOCR_TOKEN"],
    })
    client.create(image=pushed["moduleRef"], module_ref=pushed["moduleRef"], runtime="wasm")
    ```
  </TabItem>

You can also skip the server and push the module to the registry yourself with `oras push`. Then create the sandbox with the `oci://` reference and your registry credentials in the `registry` create option. Either way, the registry holds the module, and the server only downloads it to run it.

<Aside type="caution">
`pushWasmModule` works only when the operator has set an upload registry (`SB_WASM_REGISTRY_PUSH_HOST`). The server downloads `oci://` modules only from registries on its allow list (`SB_WASM_REGISTRY_ALLOWLIST`). With an empty list, it downloads nothing from registries.
</Aside>

## Register a module on the server

You can add a module to the server's catalogue (its list of known modules) before you create sandboxes. You can also skip this and let the create call find the module. The catalogue belongs to one server: in a cluster, each server has its own.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const mod = await client.createWasmModule({
      moduleRef: "file:///opt/agent.wasm",
      entrypoint: "_start",
    });
    const rows = await client.listWasmModules();
    console.log(rows.length);
    await client.deleteWasmModule(mod.id);
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    mod = client.create_wasm_module({
        "moduleRef": "file:///opt/agent.wasm",
        "entrypoint": "_start",
    })
    rows = client.list_wasm_modules()
    print(len(rows))
    client.delete_wasm_module(mod["id"])
    ```
  </TabItem>
  <TabItem label="Go">

    ```rust
    client.delete_wasm_module(&module.id)?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java

        .setModuleRef("file:///opt/agent.wasm")
        .setEntrypoint("_start"));

    System.out.println(rows.size());
    client.deleteWasmModule(mod.id);
    ```

| Option | What it does | Default |
|---|---|---|
| `moduleRef` | The module to register, in any form from [How the server finds a module](#how-the-server-finds-a-module). | None (required) |
| `entrypoint` | The function the server calls to start the module. | `_start` |
| `id` | Your own ID for the catalogue entry. | The module's digest |

The server checks the module during the call, so the returned entry is usually already `ready`. If it is `failed`, `lastError` says why.

## Faster starts with warm workers

The server keeps a few worker processes started and ready for each module it knows. A create for that module takes a ready worker and skips starting a new one. Your create call does not change. This is on by default.

- The server starts warming a module the first time you create a sandbox from it, or as soon as you [register it](#register-a-module-on-the-server). Registering first makes even the first create fast.
- Ready workers use the server's default WASM memory. A sandbox that asks for a different `memoryMB` starts a fresh worker instead.

In a cluster, servers tell each other which modules they have cached. AerolVM prefers to place a new sandbox on a server that already has its module.

## For server operators

### Standard modules and registries

| Setting | What it does | Default |
|---|---|---|
| `SB_WASM_STANDARD_MODULES` | Standard module names, as `alias=file.wasm,...`. The files live in the modules folder. | Empty |
| `SB_WASM_MODULES_DIR` | The modules folder. | `/var/lib/sandboxd/wasm/modules` |
| `SB_WASM_REGISTRY_ALLOWLIST` | Registry hosts that `oci://` references may download from. Empty blocks all registry downloads. | Empty |
| `SB_WASM_REGISTRY_PUSH_HOST` | The registry `pushWasmModule` uploads to. Empty turns uploads off. | Empty |

On a cluster, list standard modules under `wasm.standard_modules` in `config/cluster.yml`. Then run the `stage-wasm-modules` Ansible playbook. It downloads each module to every server and checks its sha256 hash.

### Warm workers

| Setting | What it does | Default |
|---|---|---|
| `SB_WASM_POOL_ENABLED` | Keep started workers ready for each module. | `true` |
| `SB_WASM_POOL_DEPTH_DEFAULT` | How many ready workers to keep per module. | `2` |

Turn the pool off on servers that are short of memory, since ready workers hold memory while they wait.

### Cleanup

The server cleans up unused modules on a timer (`SB_WASM_MODULE_GC_INTERVAL`, every 15 minutes by default). It is on by default (`SB_WASM_MODULE_GC_ENABLED=true`). Each run does two sweeps:

- **Catalogue entries.** It removes entries that nothing uses and that are older than `SB_WASM_MODULE_GC_TTL` (7 days by default).
- **Downloaded modules.** It deletes cached `oci://` files (`<digest>.wasm` under `SB_WASM_CACHE_DIR`) older than `SB_WASM_CACHE_GC_TTL` (24 hours by default). If the cache is bigger than `SB_WASM_CACHE_MAX_BYTES` (no limit by default), it deletes the oldest files first.

A module that a sandbox or a catalogue entry still uses is **never** deleted, however old it is or however full the disk is. Cleanup only removes downloaded modules that nothing depends on.
