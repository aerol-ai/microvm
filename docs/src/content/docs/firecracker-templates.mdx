A template is a [Firecracker](/firecracker-sandbox/) sandbox prepared ahead of time. It holds two things. The first is the VM's disk (the root filesystem, or rootfs), built from a container image as an `ext4` disk file. The second is a snapshot: a saved copy of a VM that has already booted and then paused.

Without a template, every Firecracker create builds the disk from the image again, which takes 10 to 60 seconds. With a template, a new sandbox copies the snapshot and resumes it. It skips the build and the kernel boot, and starts in under 100 ms.

<Aside type="note" title="Not using Firecracker?">
Templates only apply to `runtime: "firecracker"`. To save and reuse a normal container sandbox, use [Snapshots](/snapshots/) instead. A snapshot turns a running sandbox into a named image you can start copies from.
</Aside>

Use templates when you want:

- **Fast starts.** Good for CI runners, code playgrounds and AI agents that create many sandboxes.
- **Fixed contents.** A template is built once and reused. You decide when it is rebuilt.
- **One build for a whole cluster.** A template can be published once, and other servers download it when they first need it.

<Aside type="caution" title="Operator token only">
Template calls (create, list, get, delete and rebuild) manage files shared by every user of the server. They need the server's operator token, the `SB_PAT_TOKEN` set at install. Per-user tokens on a managed setup cannot use them.
</Aside>

## Create a template

Give the template an `id` you choose. Then a retried script cannot make a second copy: the server rejects a repeated `id` with `409 Conflict`. The call returns at once with status `pending`, and the build runs in the background.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const tpl = await client.createTemplate({
      id: "py311",
      image: "docker://python:3.11",
      minSizeMiB: 1024,
    });
    console.log(tpl.id, tpl.status); // py311 pending
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    tpl = client.create_template({
        "id": "py311",
        "image": "docker://python:3.11",
        "minSizeMiB": 1024,

    print(tpl["id"], tpl["status"])  # py311 pending
    ```
  </TabItem>
  <TabItem label="Go">

  </TabItem>
  <TabItem label="Rust">

| Option | What it does | Default |
|---|---|---|
| `id` | Your name for the template. Starts with a letter or digit, then letters, digits, `.`, `_` or `-`. At most 128 characters. | The server picks one |
| `image` | The container image to build from. See [Image names](#image-names). | None (required) |
| `minSizeMiB` | The smallest size for the disk file, in MiB. | Just big enough for the image |

### Image names

The server builds the disk with [skopeo](https://github.com/containers/skopeo), so any image name skopeo understands works:

- `docker://python:3.11` for an image on Docker Hub or another registry
- `oci-archive:/path/to/image.tar` for an image saved as a file on the server
- `docker-daemon:my-tag:latest` for an image in the server's local Docker

## Wait until it is ready

The build takes a while. There is no callback when it finishes, so check the status every few seconds.

| Status | What it means |
|---|---|
| `pending` | Waiting to start. |
| `building_rootfs` | Building the disk from the image. |
| `snapshotting` | Booting the VM once and saving the paused copy. |
| `ready` | Done. Sandboxes start from the snapshot, which is fast. |
| `ready_no_snapshot` | The disk is built, but saving the snapshot failed (see `snapshotError`). Sandboxes still work, but they boot the kernel normally, which is slower. |
| `failed` | The build failed. `lastError` says why. Delete the template and create it again. |
| `unhealthy` | A rebuild is running, or the snapshot was found damaged. |

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    async function awaitReady(id: string) {
      for (;;) {
        const tpl = await client.getTemplate(id);
        if (tpl.status === "ready" || tpl.status === "ready_no_snapshot") return tpl;
        if (tpl.status === "failed") throw new Error(`build failed: ${tpl.lastError}`);
        await new Promise((r) => setTimeout(r, 2000));
      }
    }
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    import time

    def await_ready(id: str):
        while True:
            tpl = client.get_template(id)
            if tpl["status"] in ("ready", "ready_no_snapshot"):
                return tpl
            if tpl["status"] == "failed":
                raise RuntimeError(f"build failed: {tpl.get('lastError')}")
            time.sleep(2)
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    func awaitReady(ctx context.Context, c *microvm.Client, id string) (sdktypes.Template, error) {
        for {
            tpl, err := c.GetTemplate(ctx, id)
            if err != nil {
                return tpl, err
            }
            switch tpl.Status {
            case sdktypes.TemplateStatusReady, sdktypes.TemplateStatusReadyNoSnapshot:
                return tpl, nil
            case sdktypes.TemplateStatusFailed:
                return tpl, fmt.Errorf("build failed: %s", tpl.LastError)
            }
            time.Sleep(2 * time.Second)
        }
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use std::{thread, time::Duration};
    use aerolvm_sdk::TemplateStatus;

    fn await_ready(client: &aerolvm_sdk::Client, id: &str) -> Result<aerolvm_sdk::Template, aerolvm_sdk::Error> {
        loop {
            let tpl = client.get_template(id)?;
            match tpl.status {
                TemplateStatus::Ready | TemplateStatus::ReadyNoSnapshot => return Ok(tpl),
                TemplateStatus::Failed => {
                    return Err(aerolvm_sdk::Error::Api(format!(
                        "build failed: {}",
                        tpl.last_error.unwrap_or_default()
                    )));
                }
                _ => thread::sleep(Duration::from_secs(2)),
            }
        }
    }
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    Template awaitReady(MicroVMClient c, String id) throws InterruptedException {

            switch (tpl.status) {
                case READY:
                case READY_NO_SNAPSHOT:
                    return tpl;
                case FAILED:
                    throw new RuntimeException("build failed: " + tpl.lastError);
                default:
                    Thread.sleep(2000);
            }
        }
    }
    ```

## Create a sandbox from a template

Pass the template's ID: `templateId` in TypeScript and Python, `TemplateID` in Go, `template_id` in Rust and `setTemplateId` in Java. A sandbox with a template is always a Firecracker sandbox. The image is still required, so pass the image the template was built from. SDK versions 0.6.4 and older can only do this from Go.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({
      image: "python:3.11",
      runtime: "firecracker",
      templateId: "py311",
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox = client.create(
        image="python:3.11",
        runtime="firecracker",
        templateId="py311",
    )
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    sandbox, err := client.Create(ctx, sdktypes.CreateSandboxOptions{
        Image:      "python:3.11",
        Runtime:    sdktypes.RuntimeFirecracker,
        TemplateID: "py311",
    })
    if err != nil {
        log.Fatal(err)
    }
    defer sandbox.Destroy(ctx)
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust

        image: "python:3.11".into(),
        runtime: Some("firecracker".into()),
    ```

  </TabItem>
  <TabItem label="Java">

The template must be `ready`, `ready_no_snapshot` or `unhealthy`. The last two still work, but they boot the kernel normally, which is slower. While the template is still building, or if it failed, the create fails with an error such as `template "py311" is pending, not ready`.

## List your templates

`hasSnapshot` tells you whether sandboxes from the template take the fast path.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    for (const tpl of await client.listTemplates()) {
      console.log(tpl.id, tpl.status, tpl.hasSnapshot ? "fast-boot" : "cold-boot");
    }
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    for tpl in client.list_templates():
        kind = "fast-boot" if tpl["hasSnapshot"] else "cold-boot"
        print(tpl["id"], tpl["status"], kind)
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    rows, err := client.ListTemplates(ctx)
    if err != nil {
        log.Fatal(err)
    }
    for _, tpl := range rows {
        kind := "cold-boot"
        if tpl.HasSnapshot {
            kind = "fast-boot"
        }
        fmt.Println(tpl.ID, tpl.Status, kind)
    }
    ```
  </TabItem>
  <TabItem label="Rust">

## Rebuild a template

A rebuild makes a new snapshot from the disk the template already has. Rebuild when:

- the snapshot is damaged and you want it fixed before the next create;
- the server's kernel or toolbox (the helper program inside each sandbox) was upgraded. A rebuild picks up the change without waiting for the optional [scheduled rebuild](#rebuild-templates-on-a-schedule).

It is safe to call many times at once. Parallel calls for the same `ready` template start only one rebuild. The call returns the template with status `unhealthy`. Wait for it to become `ready` again.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const tpl = await client.rebuildTemplate("py311");
    console.log(tpl.status); // unhealthy
    await awaitReady("py311");
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    tpl = client.rebuild_template("py311")
    print(tpl["status"])  # unhealthy
    await_ready("py311")
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    tpl, err := client.RebuildTemplate(ctx, "py311")
    if err != nil {
        log.Fatal(err)
    }
    fmt.Println(tpl.Status) // unhealthy
    awaitReady(ctx, client, "py311")
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let tpl = client.rebuild_template("py311")?;
    println!("{:?}", tpl.status); // Unhealthy
    await_ready(&client, "py311")?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    Template tpl = client.rebuildTemplate("py311");
    System.out.println(tpl.status); // UNHEALTHY
    awaitReady(client, "py311");
    ```
  </TabItem>
</Tabs>

### When a rebuild is refused

Some statuses cannot be rebuilt. The server answers with `412 Precondition Failed`:

| Current status | Why |
|---|---|
| `pending`, `building_rootfs`, `snapshotting` | The first build is still running. |
| `ready_no_snapshot` | There is no snapshot to rebuild from. Delete the template and create it again. |
| `failed` | The first build failed. Delete the template and create it again. |

If the template is already `unhealthy`, the call returns it unchanged. A rebuild is already running, or the server starts it again on its next restart.

## Delete a template

Deleting removes the disk and snapshot files. If any sandbox still uses the template, the server refuses with `409 Conflict`. Delete those sandboxes first.

## For server operators

### Share templates across a cluster

In a cluster, templates can be published to AOCR, AerolVM's image registry (a server that stores images). The server that built the template uploads its disk and snapshot as one file, named `cluster/<id>/templates/<tid>:latest`. Other servers download it the first time a sandbox from that template lands on them, so that first create waits for the download. When AerolVM places a sandbox, it prefers servers that already have the template. In cluster mode, each template call goes to the worker that owns the template, and the cluster leader combines the list results.

This uses the same upload switch as [Snapshots](/snapshots/). One setting turns on both, and both upload to the same AOCR host with the same cluster token:

| Setting | What it does |
|---|---|
| `SB_SNAPSHOT_PUSH_ENABLED` | Turns on background uploads for snapshots **and** templates. When `false` (the default), templates stay on the server that built them. |
| `SB_ENABLE_FIRECRACKER` | Templates exist only on Firecracker servers, so template uploads also need this. |
| `SB_MIRROR_PUSH_HOST` | The AOCR host to upload to. Falls back to `SB_IMAGE_DISTRIBUTION_AOCR_HOST`. |
| `SB_AUTO_IMPORT_CLUSTER_ID` | The cluster name. It is part of each file's name and limits what the token can reach. |
| `SB_AUTO_IMPORT_CLUSTER_PAT_PATH` | A file holding the cluster token used to upload **and** download. The server reads it on every call, so you rotate the token by rewriting the file. |

Downloading does not need `SB_SNAPSHOT_PUSH_ENABLED`. A server that only downloads needs just the cluster ID and the token file. Each template reports a `pushState` (and `registryRef` once uploaded) so you can follow the upload, the same as snapshots. Unlike snapshots, a template cannot be made from an image already in the registry. It always carries the disk and snapshot this cluster built. See [Cluster setup](/cluster-setup/) for the rest of the cluster settings.

### Rebuild templates on a schedule

Set both `SB_FIRECRACKER_TEMPLATE_ROTATION_INTERVAL` and `SB_FIRECRACKER_TEMPLATE_MAX_AGE`. On each interval, the server rebuilds every template older than the max age. Both must be above zero. If you set only the interval, the server logs a warning and does nothing. This is the same as calling `rebuildTemplate` on every `ready` template yourself, which you can do from your own code for finer control.
