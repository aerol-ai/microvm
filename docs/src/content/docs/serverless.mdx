A serverless sandbox stops by itself when it sits idle. When the next request reaches one of its public ports, the server starts it again, then passes the request through. The request can be web traffic (HTTP), a raw TCP connection, or a TLS connection (encrypted TCP). The sandbox keeps its files and its public URL the whole time.

Use this for sandboxes that serve traffic only now and then, such as preview sites, per-user coding spaces or model endpoints. While they sleep, they use no CPU or memory.

## What you can build with it

- **Many sandboxes on one server.** Idle sandboxes give back their CPU and memory, so one server can hold thousands of mostly idle workspaces.
- **Preview deployments.** Each branch or customer gets a web app that sleeps when unused and wakes on the next visit.
- **A database per customer.** Run a Postgres or Redis sandbox per customer that sleeps when idle and wakes when a query arrives. [Your own Postgres](/use-cases/customer-facing-product-experiences/spawn-postgres/) shows how to run the database.
- **On-demand practice spaces.** Coding interviews, tutorials, web playgrounds and throwaway browsers that only use resources while someone is on them.

## Turn it on

Set `serverless: true` in the sandbox's lifecycle, together with `stopIfIdleFor`. The idle time is required: the server rejects `serverless` without it. Times are in nanoseconds; five minutes is `5 * 60 * 1_000_000_000`.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({
      image: "ghcr.io/me/my-http-app:latest",
      lifecycle: {
        stopIfIdleFor: 5 * 60 * 1_000_000_000, // 5 minutes
        serverless: true,
      },
    });
    await sandbox.exposePort(8080);
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox = client.create(
        image="ghcr.io/me/my-http-app:latest",
        lifecycle={
            "stopIfIdleFor": 5 * 60 * 1_000_000_000,  # 5 minutes
            "serverless": True,
        },
    )
    sandbox.expose_port(8080)
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    sandbox, err := client.Create(ctx, sdktypes.CreateSandboxOptions{
        Image: "ghcr.io/me/my-http-app:latest",
        Lifecycle: &sdktypes.Lifecycle{
            StopIfIdleFor: 5 * time.Minute,
            Serverless:    true,
        },
    })
    if err != nil {
        log.Fatal(err)
    }
    if _, err := sandbox.ExposePort(ctx, 8080); err != nil {
        log.Fatal(err)
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust

        image: "ghcr.io/me/my-http-app:latest".into(),

            stop_if_idle_for: 5 * 60 * 1_000_000_000, // 5 minutes
            serverless: true,
            ..Default::default()

    })?;

    ```
  </TabItem>
  <TabItem label="Java">
    ```java

        .setImage("ghcr.io/me/my-http-app:latest")
        .setLifecycle(new Lifecycle()

            .setServerless(true)));
    sandbox.exposePort(8080);
    ```
  </TabItem>

A sandbox wakes up through its **public** addresses, so it must be public. A new sandbox is private, but `exposePort` makes it public for you, so the example above needs nothing more. Only a serverless sandbox that never exposes a port needs `allowPublicTraffic: true` at create to wake through its main URL. See [Block or allow the internet](/network-isolation/).

## What happens while it sleeps

When the idle timer runs out, the sandbox stops. Its public routes stay in place in a "wake on request" form. The next request starts the sandbox, then goes through to it.

| Topic | What happens |
|---|---|
| What stops it | The `stopIfIdleFor` timer. A stop caused by another lifecycle timer, or by the sandbox exiting on its own, also leaves it ready to wake. |
| A stop you make yourself | Turns wake off. The sandbox stays down until you start it. See [Take a sandbox out of service](#take-a-sandbox-out-of-service). |
| Wake-up time | From a few hundred milliseconds to a few seconds. Most of it is the container starting. |
| Wake-up limit | 15 seconds. After that, the server answers `503` with `Retry-After: 2` (try again in 2 seconds). |
| Request size during wake-up | Up to 8 MiB. A bigger request that arrives while the sandbox wakes gets `413`. |
| What can wake it | HTTP, TCP and TLS ports. HTTP requests wait in a buffer, up to the size limit. TCP and TLS connections wait for the sandbox, then pass bytes through. |

The sandbox keeps its ID, public URL, environment variables, attached storage and files across each sleep. Memory and running programs do not survive. Think of it as a container that stops and starts quickly, not one that is frozen and thawed.

## Turn it on or off for a sandbox you already have

`updateLifecycle` takes the same `serverless` field. The change applies the next time the server checks for idle sandboxes.

`updateLifecycle` replaces all the timers at once. Send `stopIfIdleFor` along with `serverless`, plus any other timers you want to keep.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    await sandbox.updateLifecycle({
      stopIfIdleFor: 5 * 60 * 1_000_000_000,
      serverless: true,
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox.update_lifecycle({
        "stopIfIdleFor": 5 * 60 * 1_000_000_000,
        "serverless": True,
    })
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    err := sandbox.UpdateLifecycle(ctx, sdktypes.Lifecycle{
        StopIfIdleFor: 5 * time.Minute,
        Serverless:    true,
    })
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    client.update_lifecycle(&sandbox.data.id, Lifecycle {
        stop_if_idle_for: 5 * 60 * 1_000_000_000,
    ```

## Take a sandbox out of service

When you call `stop` yourself, the server treats it as your decision. Wake turns off, and requests to the sandbox's public addresses fail (HTTP 409) until you call `start`. Only stops caused by the lifecycle (an idle timer, an age timer, or the sandbox exiting on its own) leave wake on.

Use this to take a serverless sandbox out of service without deleting it.

<Aside type="caution">
A manual stop is easy to forget. If a serverless sandbox stops answering, check whether someone stopped it by hand.
</Aside>

## For server operators

| Setting | What it does | Default |
|---|---|---|
| `SB_ENABLE_SERVERLESS` | Turns wake on for this server. When `false`, the API still accepts `serverless: true`, but sandboxes never wake on their own. | `true` |
| `SB_HTTP_WAKE_MAX_BUFFER` | The most request body, in bytes, the server holds while a sandbox wakes. | `8388608` (8 MiB) |

Inside the server, a sandbox that may wake is marked `wake_armed` in its database row. A manual stop clears the mark; a lifecycle stop sets it.
