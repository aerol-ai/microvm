I spent six months looking for an open-source sandbox runtime that could span more than one machine. (A sandbox runtime is the software that starts and runs sandboxes.) It did not exist. Not E2B, not Daytona, not Microsandbox, not moru, not Era, not Cognitora, not Beam, not Northflank's self-hosted option.

Every project in this space was one of two things. It was **a managed cloud you cannot run yourself**, or **a single-server tool you can run yourself but cannot grow past one machine**. The space had a hole shaped like Kubernetes, and I built the thing that fills it. This page covers the design, the four features that come out of it, and an honest comparison with every similar project I could find.

**In short:**

- AerolVM is one Go program, `sandboxd`. It runs alone on one server, or as a cluster of many servers with no extra services to run.
- It can publish raw TCP ports (for Postgres, Redis and similar) to the internet, not just web traffic.
- With storage outside the server, a sandbox can come back on a healthy server after its own server dies.
- Five SDKs, plus support for the E2B and Daytona SDKs, use the same calls on a laptop or a cluster.
- It is not a Kubernetes replacement or a managed database, and it is not yet proven at hundreds of servers.

## The gap, stated precisely

The projects in this space all work roughly the same way, but none of them spread across servers you own. You start a microVM (a small, fast virtual machine) or a container. You give it a public web address, run code through an SDK, and delete it.

The thirty-plus projects disagree on the isolation layer: Firecracker, gVisor, Kata, libkrun, V8 isolates or plain runc. They also disagree on the SDK: Python-first or TypeScript-first, code runner or dev environment.

They agree on one thing. The orchestration (the part that decides which server runs what) is **either "ours, managed" or "yours, on one box."**

That is not a small gap. It decides whether you can run sandboxes at real scale on hardware you own. The missing piece is a distributed control plane: the shared brain that coordinates many servers. Three things follow from not having one:

1. **You cannot survive a server going down.** A managed service handles this for you, out of sight. A single-server tool cannot, by definition. Only a self-hosted, multi-server runtime lets *you* own the failure *and* keep your sandboxes when a machine dies.
2. **You cannot publish raw TCP or TLS (the encryption behind HTTPS) from a sandbox to the internet.** The reason is dull: nobody built an open-source ingress layer for sandboxes. Ingress is the part that takes traffic from the internet and routes it to the right place. Managed services have one (Fly Machines does), but self-hosted tools do not.
3. **You cannot run stateful workloads with any promise that they stay up.** A stateful workload keeps data that matters: Postgres, Redis, MinIO, or a Jupyter kernel holding hours of work. On these tools, if the server dies, the work is gone. That is fine for short agent runs, but it is a ceiling for everything else.

So if you want to give a sandbox a real Postgres port today, you wire it up yourself. Or you move to a managed VM platform that is not sold as a sandbox.

I will back each claim with code below, and with a table comparing every project I tried. First comes the design, because the claims only mean something if the design supports them.

## How AerolVM is built

AerolVM is one Go program, `sandboxd`. It is a daemon (a program that runs in the background on a server). It runs in two modes from the same build:

- **Standalone:** it is the whole sandbox runtime on one server.
- **Cluster:** N copies of it, one per server, work together as one distributed control plane.

In cluster mode, three pieces do the coordinating:

- [hashicorp/raft](https://github.com/hashicorp/raft) decides placement (which server owns which sandbox). Raft is a consensus algorithm: a way for servers to agree on shared data even when some of them fail.
- [hashicorp/memberlist](https://github.com/hashicorp/memberlist) tracks membership using SWIM. SWIM is a gossip protocol, where servers keep telling each other who is alive.
- HTTP forwarding sends each change request to the server that owns the sandbox right now.

There is no separate scheduler, no etcd and no Kubernetes. A node is one server in the cluster, and in a small cluster every node does every job. Clusters above 10 nodes must give nodes separate server, worker and ingress roles, but every role runs the same program. When `EnableCluster=false`, the cluster code does nothing, so standalone mode pays nothing for it.

Ingress is [Caddy](https://caddyserver.com/), a web server that runs next to `sandboxd` on each node. [caddy-l4](https://github.com/mholt/caddy-l4) adds raw TCP and TLS routes on top of normal HTTPS. (L4 means layer 4 of the network: plain TCP connections, one level below HTTP.) `sandboxd` adds and removes Caddy routes as sandboxes come and go. It does this through Caddy's admin API, with no downtime.

Each node stores its data in SQLite, a database that lives in one file. Only one connection writes to it (`MaxOpenConns=1`), and it uses WAL mode so reads can run during a write.

Cluster state lives in memory in the Raft FSM and is copied to other servers through Raft. (FSM stands for finite state machine. Here it is the shared table every server changes only through agreed Raft log entries.)

That is the whole design. The four features below all come from it.

## 1. One program runs the whole cluster

The first feature is that a cluster needs nothing but copies of `sandboxd`. Other "distributed" tools in this space need at least one of these:

- A separate scheduler program (like Nomad).
- An external key-value store (etcd or Consul).
- An orchestrator (Kubernetes) with a sandbox runtime on top. That means KubeVirt plus custom controllers, or one of the failed "sandbox operator" projects.
- A split between control and data servers, which means at least two programs to deploy.

AerolVM needs none of those. The program that runs your sandboxes is also the Raft member, the SWIM member, the ingress controller, the API server and the SDK's target. `internal/cluster/` is about 20,000 lines of Go. When cluster mode is off, it returns the `Noop` implementation, and the rest of the daemon never checks which mode it is in.

For operators, it looks like this:

```bash
# Standalone: one server
sudo systemctl start sandboxd

# Cluster: the same program on three servers.
# On node A, turn the running daemon into the first cluster node:
sudo ./scripts/cluster-init.sh

# On nodes B and C, join node A with the key and trust bundles it printed:
sudo ./scripts/cluster-join.sh \
    --gossip-key '<key from node A>' \
    --peers <node-A-address>:7001 \
    --tls-bundle <bundle from node A> \
    --cred-bundle <key bundle from node A>
```

There is no external database to run, no companion service and no Helm chart. [Cluster setup](/cluster-setup/) has the full steps, and on AWS, Terraform runs them for you.

**Why nobody else did this.** There are two reasons, and both are honest:

- The agent-sandbox space is young: most projects launched between 2024 and 2026. A distributed control plane is a year of work. In early demos, it does not stand out the way "we have a fast cold start" does.
- The companies in this space are venture-funded. Shipping a multi-server open-source option takes money *directly* away from their managed service. The incentives point the other way.

I am not venture-funded, and I had the year. So here we are.

## 2. Raw TCP and TLS ports, not just HTTP

The second feature is that a sandbox can publish any TCP service, not only websites. Every sandbox vendor in this space exposes HTTP. None of the open-source, self-hosted ones publish raw TCP or TLS. HTTP ingress is a solved problem (nginx, Caddy, Envoy, Traefik), but TCP ingress for many tenants (customers or users sharing the platform) is not.

Raw TCP for many tenants needs one of two approaches, and both have ugly edge cases. One is SNI multiplexing on shared ports. SNI is the hostname a TLS client sends at the very start of a connection, so one port can serve many hostnames. The other is a separate host port for each sandbox.

AerolVM uses caddy-l4 to share ports by SNI. Where SNI does not apply, it uses the host-port pool described in [Safe retries (idempotency)](/engineering-idempotency/). Those cases are raw TCP without TLS, or protocols where the server expects to own the port. The daemon that runs the sandbox also updates Caddy's config, adding and removing L4 routes as sandboxes come and go.

The result: a sandbox can publish a real Postgres, Redis, MongoDB, MySQL or Mosquitto MQTT port to the public internet. Any TCP service works. TLS termination is optional (Caddy can handle the encryption for you), and the address sits on the domain your DNS already points at the cluster. (DNS is the system that turns names like `example.com` into server addresses.)

**No other open-source sandbox runtime does this.** Managed VM platforms that are not sold as sandboxes do, Fly Machines in particular. So the gap in the sandbox space is real.

See [TCP and TLS ports](/tcp-ports/) for the how-to. See [Deploy your own Supabase](/use-cases/customer-facing-product-experiences/spawn-postgres/) for a worked Postgres example.

## 3. Stateful sandboxes that survive a dead server

The third feature is that a sandbox can come back, with its data, after its server dies. This is the strongest claim on the page, so I will defend it the hardest. Database people will press on it.

The mechanism, step by step:

1. **Storage outside the server.** A sandbox can declare a mount backed by S3, NFS, SSHFS or any [rclone](https://rclone.org) remote (see [Attach cloud storage](/external-storage/)). The mount tools run on the host, not in the sandbox (see [Where secrets live](/engineering-trust-boundary/)). So credentials never enter the sandbox, and the mount does not live or die with the container.
2. **Cluster-wide placement state in Raft.** The sandbox's identity lives in the Raft FSM: its name, hostname binding, mounts and exposed ports. When the owner node dies, the surviving Raft leader (the one server that writes new Raft entries) still has that state.
3. **SWIM notices the dead owner.** `memberlist` marks a node `Failed` after its suspect-then-confirm window. That takes from under a second to a few seconds, depending on cluster size and probe interval.
4. **Re-placement.** This step applies to sandboxes created with the failover policy `recreate`. After a grace period (30 seconds by default), the leader picks a new owner. The placement code (`internal/cluster/placement.go`) uses power-of-two-choices: it samples two healthy nodes and picks the one with more spare capacity. The recovery code (`internal/cluster/recovery_replication.go` and `recovery_store.go`) rebuilds the sandbox on the new owner.
5. **Mount reattachment.** The new owner's mount manager attaches the same external volume. Because the storage is external (S3 or NFS), the bytes never moved. The new container sees the same files the old one wrote.
6. **Ingress cutover.** The Caddy route now points at the new owner. Clients using the public address, over HTTP or raw TCP, reach the new sandbox without any change on their side. Long-lived TCP connections drop at the cutover, and clients reconnect.

The honest caveats:

- **Writes still in flight can be lost.** The cutover does not promise zero RPO (recovery point objective: how much recent data you can lose). If Postgres had a transaction in memory, not yet flushed to the S3 mount, when the host died, that transaction is lost. Real Postgres behaves the same way after a `kill -9`; AerolVM adds no durability the database itself lacks.
- **There is downtime.** Detection, the grace period, re-placement, mounting and container start all take time. The grace period alone is 30 seconds by default (`SB_DEAD_OWNER_GRACE`), so expect at least that long. HTTP clients with retries cope on their own; custom TCP clients need a reconnect loop.
- **Your storage must handle the handoff.** S3 with one writer at a time is fine, but S3 with two writers at once never is. During the cutover the dying owner might still write, so AerolVM force-detaches its mount before the new owner mounts. We tested the common cases, but your data's safety still depends on your storage's consistency model.
- **You need at least one healthy node with room.** If the whole cluster is at capacity, the sandbox stays unplaced until capacity frees up.

With those caveats stated: **yes, kill the host, and the sandbox comes back on a healthy node with its data.** The public address routes to the new sandbox. Run your own Postgres, Redis or single-tenant MinIO in a sandbox, and it survives losing a node.

I know of no other open-source sandbox runtime that does this. The closest match is a Kubernetes StatefulSet with a PVC (a persistent volume claim).

That works, but you must run Kubernetes and find a CSI driver (a storage plugin) for your storage. You also accept that the workload is a pod, not a sandbox with an SDK. See [Durability and failover](/durability/) for the reference.

## 4. Five SDKs in step, plus E2B and Daytona support

The fourth feature is SDK coverage. Five SDKs (TypeScript, Python, Go, Rust and Java) ship from the same repository in the same release. They are not generated wrappers: each one is written by hand to feel natural in its language, with matching method names and matching tests. Every new server feature lands in all five packages at once.

On top of the native SDKs, AerolVM has two compatibility facades. A facade is a translation layer that speaks another product's API:

- **`/daytona`** speaks the Daytona SDK protocol. Point the official Daytona SDK at it, and your existing code runs unchanged.
- **`/e2b`** speaks the E2B SDK protocol. It includes the duplicate-request protection described in [Safe retries (idempotency)](/engineering-idempotency/).

This is not in the same league as stateful sandboxes that survive a dead server. It is a migration path. If you use E2B or Daytona today and want to move to AerolVM, self-hosted or managed, you change one URL.

See [Use the Daytona SDK](/using-daytona-sdk/) and [Use the E2B SDK](/using-e2b-sdk/).

## The competitive landscape, honestly

| **Era** | yes | no | no | no | local CLI | Local dev sandboxes, microVM. |

## The same SDK on a laptop or a cluster

The create call is not the interesting part, since every SDK has one. The interesting part is that the *same SDK* talks to one `sandboxd` on a laptop and to a 50-node cluster. The API does not change. The cluster is the operator's concern, and the SDK does not know about it.

This example starts Postgres with its data on S3, opts it into failover, and publishes its port over raw TCP:

The same calls work against `localhost` and against a cluster. The sandbox opted into `recreate`, so the owner of `shared-postgres` can die. The next `psql` connection then lands on the new owner with the data intact.

## What I am not claiming

In the spirit of these engineering pages, here is the honest list of what AerolVM is *not*:

- **Not a replacement for Kubernetes.** It does sandboxes well. Kubernetes runs pods, services, general container ingress, CRDs and operators; AerolVM does none of that. If you have microservices, run them on Kubernetes.
- **Not a replacement for managed databases.** HA Postgres in a sandbox is plain single-writer Postgres on a host that might fail. If you need streaming replication, point-in-time recovery and read replicas, you need a real database product. AerolVM gives you "Postgres that comes back": useful, but not "Postgres that never goes down".
- **Not at full parity with E2B or Daytona on every endpoint.** The facades cover the common paths: create, run commands, files and lifecycle. We add more as needed, so if you depend on one endpoint, check before you assume.
- **Not proven at hundreds of nodes.** Cluster mode is tested on small clusters. There is no public benchmark of a 50-node deployment yet.

If those limits rule out your use case, AerolVM is the wrong tool. If they do not, it is the only tool I know of in its category.

## What I want feedback on

These are three honest questions I would like readers to push on:

1. **The "Kubernetes-shaped, sandbox-sized" framing.** Is it the right metaphor? It captures the shape: a control plane, workers, ingress and reconciliation (a loop that repairs drift between what should run and what does), but it invites unfair comparisons. What would land better?
2. **The HA stateful claim.** I have stated the mechanism and the caveats. Is there a failure mode I have not covered that I should document up front? Database operators especially, please press on this.
3. **Compatibility facades versus a clean new API.** Is "drop-in for E2B and Daytona" a real migration path, or technical debt I will regret? The case for the facades is that nobody wants to rewrite their sandbox code. The case against: I am two version-skew bugs (our facade and their SDK drifting out of step) away from a never-ending chore.
