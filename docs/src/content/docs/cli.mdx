`aerolvm` opens a shell in a sandbox, runs commands in it, copies files and exposes ports from a terminal. It is built for scripts and AI coding agents as much as for people: stdout carries only data, every command has a `--json` form, and retries are safe. The same binary is also an MCP server; see [MCP Server](/mcp).

It is a thin client over the same API the SDKs use, so it works against a local daemon, a single node or a cluster.

## Install

Pick one. Every option installs the same static binary, for Linux, macOS and Windows on x64 and arm64.

| Option | Command | Notes |
|---|---|---|
| npm | `npm install -g @aerol-ai/aerolvm` | Or run it without installing: `npx -y @aerol-ai/aerolvm --help`. |
| Installer | the [Local Setup](/getting-started/local-setup) one-liner, with `--cli-only` in place of `--local` | Linux and macOS. Checks the release checksum. Needs no root: without it, installs to `~/.local/bin`. |
| Go | `go install github.com/aerol-ai/microvm/cmd/aerolvm@latest` | Builds from source. |
| Download | `aerolvm_<os>_<arch>` from the [GitHub releases](https://github.com/aerol-ai/microvm/releases) | Verify it against the release's `checksums.txt`. |

Point it at your server with the same variables the SDKs read, then check the connection:

```sh
export SB_API_URL=https://sandbox.example.com
export SB_PAT_TOKEN=your-token
aerolvm health
```

`SB_API_URL` defaults to `http://127.0.0.1:21212`, the [local setup](/getting-started/local-setup) address.

## Open a shell in a sandbox

```sh
aerolvm shell build-box
```

You get a login shell inside the sandbox: bash, or `sh` when the image has no bash. Run `aerolvm shell` with no name to choose from your sandboxes. Any sandbox you can reach works, including ones your application created through an SDK; you don't need to create it from the CLI.

- **The shell keeps running when you leave.** `Ctrl-]` detaches, and so does closing the terminal or losing the network. Run the same command again to get back in, with the shell's recent output on screen. `exit` or `Ctrl-D` ends the shell.
- **One shared shell per name.** Two terminals on the same sandbox share its `default` shell, like tmux, and an [SSH login](/ssh-access) lands in the same one. `--new` starts a separate shell, and `--session <name>` opens a named one.
- **It behaves like a local terminal.** Resizing the window resizes the remote terminal, so `vim`, `top` and `less` redraw to fit. The shell gets a `TERM` the image knows: your own when it is a common one, and `xterm-256color` otherwise.
- A stopped sandbox is started first. WASM and isolate sandboxes have no shell.
- `shell` needs a terminal. Scripts and agents use [`exec`](#running-commands).

## A first session

```sh
aerolvm create --name build-box --image python:3.12 --destroy-if-idle 2h
aerolvm cp ./requirements.txt build-box:/work/requirements.txt
aerolvm exec build-box --cwd /work -- "pip install -r requirements.txt && python -V"
aerolvm exec build-box --background -- python -m http.server 8000
aerolvm expose build-box 8000
aerolvm destroy build-box
```

`expose` prints the public URL. Sandboxes are [private by default](/network-isolation/), and `expose` is what makes a port reachable.

## Commands

| Command | What it does |
|---|---|
| `shell` | Open an interactive shell in a sandbox (`--new`, `--session`) |
| `exec` | Run a command and stream its output |
| `cp` | Copy a file between this machine and a sandbox (`<sandbox>:<path>`; `-` is stdin or stdout) |
| `ls` | List a directory in a sandbox |
| `logs` | Print a background command's output (`--follow` to keep streaming) |
| `expose` | Publish a sandbox port and print its URL (`--tcp` for raw TCP) |
| `list` | List sandboxes, one page at a time (`--tag`, `--limit`, `--page-token`) |
| `get` | Show one sandbox |
| `create` | Create a sandbox, or return the existing one with that name |
| `start` / `stop` | Start or stop sandboxes; stopping keeps the files |
| `destroy` | Destroy sandboxes; one that is already gone counts as destroyed |
| `snapshot` | Save a sandbox's filesystem as an image other sandboxes can start from |
| `health` | Check that sandboxd is reachable and the token works |
| `version` | Print the version |
| `mcp` | Run the [MCP server](/mcp) over stdio, or print client setup |

`aerolvm <command> --help` prints that command's flags, examples and JSON shape. The help is written for agents to read: it is short, and it is the reference for anything this page leaves out.

A sandbox is addressed as `<id-or-name>`. Anything shaped like a generated ID (`sb-` followed by 16 hex digits) is an ID, and anything else is a name. Names are [unique per account](/sandboxes#named-sandboxes).

## Safe to retry

`create` is keyed by name. If you already have a sandbox with that name, `create` returns it instead of making a second one, and `--json` reports `"created": false`. Without `--name`, aerolvm picks a name (`agent-` plus random characters) before the first attempt, so a retry after a dropped connection finds the sandbox that attempt made.

Every sandbox the CLI creates gets the tag `aerolvm.created_by=cli`, unless you set that tag yourself. `aerolvm list --tag aerolvm.created_by=cli` finds them.

`destroy` and `expose` are safe to repeat too. Destroying a sandbox that is already gone succeeds, and repeating `expose` returns the same URL.

## Output for scripts and agents

Stdout is data and stderr is everything else: progress, notes and errors. Pass `--json`, or set `AEROLVM_OUTPUT=json` once, to get one JSON document on stdout. With `--json`, an error is printed on stderr as:

```json
{"error":{"code":"not_found","message":"sandbox \"build-box\" not found","http_status":404,"retryable":false}}
```

The `code` field is stable and is the field to branch on. The common ones are `not_found`, `conflict`, `invalid_argument`, `unauthorized`, `unavailable`, `timeout`, `server_unsupported` and `unsupported_runtime`. `retryable` says whether repeating the same call can succeed.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | Success |
| `1` | The command failed |
| `2` | Bad usage: an unknown flag or a missing argument |

`exec` and `shell` exit with the remote command's own code instead. They exit with `128+n` when signal `n` killed the command, and `125` when aerolvm itself failed before the command produced an exit code. `exec` exits with `124` when `--timeout` fired, and `shell` exits with `0` when you detach.

## Running commands

One argument after `--` runs as a shell command line, so pipes and `&&` work. Several arguments are quoted and joined.

```sh
aerolvm exec build-box -- "make test | tail -50"
aerolvm exec build-box --cwd /app --env CI=1 --timeout 15m -- npm test
```

- **Live output.** Output streams as it is produced. With `--json`, aerolvm waits for the command and prints `{"exit_code","stdout","stderr",...}`. Each stream keeps its first 4 KiB and last 12 KiB, and the result says how much was cut.
- **Stdin.** aerolvm forwards stdin when it is not a terminal, so `echo hi | aerolvm exec box -- cat` works. Some agent harnesses leave stdin open and never close it. A command that reads stdin then waits until `--timeout`, so pass `--no-stdin` there. Pass `-i` to forward a terminal's stdin, and `-t` for an interactive terminal; `-it` does both, as in `docker exec`, so `aerolvm exec box -it -- htop` works. For a shell, use [`aerolvm shell`](#open-a-shell-in-a-sandbox): it survives a dropped connection, which an `exec` doesn't.
- **Stopping.** `--timeout` and Ctrl-C both kill the remote command, not just the local client. If the connection drops, the sandbox kills the command too. See [When the connection drops](/exec-streaming#when-the-connection-drops).
- **Background commands.** `--background` starts the command, prints a session ID, and returns. Read its output with `aerolvm logs <sandbox> <session-id> --follow`.
- **Stopped sandboxes** start before the command runs.

### Runtime differences

- **WASM sandboxes** have no streaming exec. `exec` runs the command buffered, without stdin, and prints the output when it finishes. `-i`, `-t` and `shell` are refused.
- **Isolate sandboxes** run a single `fetch` handler, with no shell and no filesystem. `shell`, `exec`, `cp` and `ls` return `unsupported_runtime`; use the SDK's invoke call instead. See [Isolate Sandbox](/isolate-sandbox).

## Limiting outbound network

`--allow-host` gives a new sandbox an allow list: it reaches only the destinations you name, and everything else is refused. Repeat the flag or pass a comma list. An entry is a host, a `*.` wildcard, `host:port` or a CIDR.

```sh
aerolvm create --name build-box --image python:3.12 --allow-host pypi.org --allow-host '*.pythonhosted.org'
aerolvm create --name deploy --allow-host github.com:22,10.0.0.0/8
```

`--block-network` turns outbound traffic off entirely, so it can't be combined with `--allow-host`. To change the list of a running sandbox, use `setNetworkPolicy` from an SDK. [Egress Domain Filtering](/egress-domain-filtering) covers the rules and how a denial is reported.

## Debugging

`--debug` logs every API request and response status to stderr. The token is redacted.
