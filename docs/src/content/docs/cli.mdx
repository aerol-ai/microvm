`aerolvm` lets you work with sandboxes from your terminal. You can create a sandbox, run commands in it, copy files in and out, and share a web server from it. It talks to the same server as the SDKs, so it works with a local install, one server or a cluster.

Scripts and AI agents can use it too. The same program is also an [MCP server](/mcp/) for AI coding tools.

## Install

```bash
curl -fsSL https://aerolvm.aerol.ai | bash -s -- --cli-only
```

This installs only the CLI. It needs no server, no Docker and no admin rights, and works on Linux and macOS. If it tells you to add a folder to your `PATH`, do that, then open a new terminal.

Other ways to install:

- **With Go:** `go install github.com/aerol-ai/microvm/cmd/aerolvm@latest`
- **By hand, including on Windows:** download the file for your system from [GitHub releases](https://github.com/aerol-ai/microvm/releases). Check it against `checksums.txt`, then put it in a folder on your `PATH`.

## Sign in

The CLI uses the same two settings as the SDKs: your server's address and your token. If you followed the [Quickstart](/quick-start/), they are already set. If not, set them now:

```bash
export SB_API_URL=http://localhost:21212
export SB_PAT_TOKEN=your-secret-pat
```

Then check that the CLI can reach your server:

```bash
aerolvm health
```

To skip the `export` lines in every new terminal, run `aerolvm login` once. It asks for the address and the token and saves them. See [Save your login](#save-your-login).

## Your first sandbox

### Step 1: Create a sandbox

```bash
aerolvm create --name build-box --image python:3.12 --destroy-if-idle 2h
```

This starts a sandbox named `build-box` from the `python:3.12` image. It deletes itself after 2 hours with no activity. If you already have a sandbox with that name, you get that one back instead of a second one.

### Step 2: Run a command in it

```bash
aerolvm exec build-box -- python -V
```

Everything after `--` runs inside the sandbox, and the output shows up live. To use pipes or `&&`, put the whole command in quotes:

```bash
aerolvm exec build-box -- "pip install requests && pip list"
```

### Step 3: Copy files in and out

```bash
aerolvm cp ./data.csv build-box:/tmp/data.csv
aerolvm cp build-box:/tmp/data.csv ./copy.csv
```

Write a path inside the sandbox as `<sandbox>:<path>`. `cp` copies one file at a time.

### Step 4: Share a web server

```bash
aerolvm exec build-box --background -- python -m http.server 8000
aerolvm expose build-box 8000
```

`--background` starts the server and returns right away. `expose` prints a public web address for port 8000. Sandboxes are [private](/network-access/) until you expose a port.

Public addresses need a [server install](/getting-started/single-node-setup/). On a local install, `expose` still prints an address, but nothing answers there.

### Step 5: Delete it

```bash
aerolvm destroy build-box
```

## Open a shell in a sandbox

```bash
aerolvm shell build-box
```

You get a terminal inside the sandbox, as if you had logged in to it. Type `exit` to end the shell.

- **Leave without closing it:** press `Ctrl-]`. The shell keeps running. Run the same command to get back in, with your recent output on screen.
- **Pick from a list:** run `aerolvm shell` with no name.
- **Not every sandbox has a shell.** WebAssembly and V8 isolate sandboxes do not, and neither do images without `bash` or `sh`. Use `exec` for those.

More in [Shell details](#shell-details).

## More things you can do

| To do this | Run |
|---|---|
| List your sandboxes | `aerolvm list` |
| See one sandbox | `aerolvm get build-box` |
| Stop a sandbox and keep its files | `aerolvm stop build-box` |
| Start it again | `aerolvm start build-box` |
| List a folder | `aerolvm ls build-box:/tmp` |
| Follow a background command's output | `aerolvm logs build-box <session-id> --follow` |
| Save a sandbox as an image | `aerolvm snapshot build-box my-image` |
| Run a command in a folder, with a time limit | `aerolvm exec build-box --cwd /app --timeout 10m -- npm test` |
| Give a command an environment variable | `aerolvm exec build-box --env CI=1 -- npm test` |
| Share a raw TCP port, such as a database | `aerolvm expose build-box 5432 --tcp` |
| See every option of a command | `aerolvm <command> --help` |

You can name a sandbox by its name or by its ID (`sb-` and 16 hex digits). `--background` prints the session ID that `logs` needs.

## Limit what a sandbox can reach

A new sandbox can reach the internet. To allow only some sites, list them when you create it:

```bash
aerolvm create --name build-box --image python:3.12 --allow-host pypi.org --allow-host '*.pythonhosted.org'
```

Everything else is refused. An entry can be a site name, a `*.` wildcard, `host:port`, or a range of IP addresses such as `10.0.0.0/8`. To turn the internet off completely, use `--block-network` instead. To change the list later, use an SDK. [Allow only some websites](/network-access/#allow-only-some-websites) has the details.

## Reference

### Save your login

```bash
aerolvm login https://sandbox.example.com
```

- It asks for your token with typing hidden, checks it with the server, then saves it in `~/.config/aerolvm/config.json`. Only you can read that file.
- With no address, it asks for one. The default is the local install, `http://127.0.0.1:21212`.
- `SB_API_URL` and `SB_PAT_TOKEN` still win over the saved login when they are set.
- The saved token is only ever sent to the address it was saved for.
- In CI, pipe the token in: `aerolvm login <url> --token-stdin`.
- `aerolvm logout` forgets the login on this machine. The token keeps working on the server.

### Shell details

- **Shells are shared.** Two terminals on the same sandbox share its `default` shell, like `tmux`. An [SSH login](/ssh-access/) lands in the same one. `--new` starts a separate shell, and `--session <name>` opens a named one.
- **It acts like a local terminal.** Resizing your window resizes the remote one, so `vim`, `top` and `less` fit.
- **A stopped sandbox is started first.**
- **Stopping or deleting the sandbox ends the shell.** When the connection drops, `aerolvm shell` tells you whether the shell is still there to reopen.
- **`shell` needs a real terminal.** Scripts and agents use `exec`.

These shells are [terminal sessions](/sessions/), so the SDKs can see and manage them too.

### Output for scripts and agents

Normal output is data. Progress, notes and errors go to the error stream (stderr).

Add `--json` to any command, or set `AEROLVM_OUTPUT=json` once, to get one JSON document instead. `exec --json` waits for the command and prints its `exit_code`, `stdout` and `stderr`. Long output keeps its first 4 KB and last 12 KB.

With `--json`, errors look like this:

```json
{"error":{"code":"not_found","message":"sandbox \"build-box\" not found","http_status":404,"retryable":false}}
```

Check the `code` field. It does not change between versions. Common codes are `not_found`, `conflict`, `invalid_argument`, `unauthorized`, `unavailable`, `timeout`, `server_unsupported` and `unsupported_runtime`. `retryable` says whether trying again can work.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | It worked. |
| `1` | The command failed. |
| `2` | Bad usage, such as an unknown flag. |

`exec` and `shell` exit with the remote command's own code instead. It is `128+n` when signal `n` killed the command, and `125` when `aerolvm` itself failed. `exec` exits with `124` when `--timeout` fires, and `shell` with `0` when you detach.

`audit verify` exits with `3` when the result is INCOMPLETE. See [Check an audit log against its witness](#check-an-audit-log-against-its-witness).

### Safe to repeat

- **`create`** returns the sandbox that already has the name. With `--json`, it reports `"created": false`. Without `--name`, the CLI picks a name (`agent-` and random characters) before the first try, so a retry finds the same sandbox.
- **`destroy`** of a sandbox that is already gone succeeds.
- **`expose`** returns the same address each time.

Every sandbox the CLI creates gets the tag `aerolvm.created_by=cli`. Find them with `aerolvm list --tag aerolvm.created_by=cli`.

### Input and stopping

- **Input is passed along** when it is not a terminal, so `echo hi | aerolvm exec build-box -- cat` works. Some agent tools leave input open forever. Pass `--no-stdin` there, or a command that reads input waits until `--timeout`.
- **Interactive programs:** `aerolvm exec build-box -it -- htop` works like `docker exec -it`.
- **Stopping:** `--timeout` and `Ctrl-C` stop the command inside the sandbox, not just on your machine. A dropped connection stops it too. See [If the connection drops](/exec-streaming/#if-the-connection-drops).

### Sandbox types

- **WebAssembly sandboxes** run a command and print the output when it ends. They pass no input, and `-i`, `-t` and `shell` are refused.
- **V8 isolate sandboxes** run one request handler, with no shell and no files. `shell`, `exec`, `cp` and `ls` fail with `unsupported_runtime`. Call the handler from an SDK instead. See [V8 isolate](/isolate-sandbox/).

### Check an audit log against its witness

```bash
aerolvm audit verify --witness s3://my-audit-witness --since 30d --export s3://my-audit-export
```

This is for servers in [enterprise mode](/enterprise/enterprise-mode/). Each server stores its audit log's newest fingerprint in a locked S3 bucket, called the witness. `audit verify` checks that every fingerprint stored since `--since` links to the next one through the audit records.

- It needs no server and no token. It reads the buckets with your usual AWS credentials, and read access is enough.
- Run it on a machine outside the cluster you are checking.
- It checks every server in the bucket, one by one. The worst result wins.

| Flag | What it does |
|---|---|
| `--witness s3://<bucket>[/<prefix>]` | The witness bucket. Required. The prefix defaults to `witness/`. |
| `--since <when>` | Where the window starts. Required. Give a time such as `2026-10-01T00:00:00Z`, a duration such as `720h`, or days such as `30d`. |
| `--export s3://<bucket>[/<prefix>]` | The S3 audit export. Give this or `--export-dir`, not both. |
| `--export-dir <dir>` | Batches saved from a webhook or bus receiver, laid out as `<dir>/node=<id>/YYYY/MM/DD/<batch>.jsonl`. |
| `--local <id>=<path>` | A copy of one server's `secrets.jsonl`, for records not exported yet. Repeat it for more servers. A bare path works with exactly one `--node`. |
| `--node <id>` | Check only this server. Repeat it for more. By default, every server in the bucket. |
| `--max-lag <duration>` | How long a fingerprint may wait for its records. Default `15m`. |
| `--region`, `--endpoint`, `--path-style` | S3 client settings, used for both buckets. |
| `--json` | Print the full report as JSON. |

| Result | Exit code | Meaning |
|---|---|---|
| PASS | `0` | Every fingerprint in the window links to the records. |
| FAIL | `1` | A fingerprint does not link: a rewritten history, a rollback, or missing records. Also used when the check cannot run. |
| INCOMPLETE | `3` | Nothing contradicts the witness, but some fingerprints have waited longer than `--max-lag` for their records. The export is behind. Never read this as PASS. |

Keep exported records at least as long as your `--since` window, or the result is FAIL. [Check the whole history](/enterprise/enterprise-mode/#check-the-whole-history) explains how to pick the window.

### Debugging

`--debug` prints every API request and response status to stderr. The token is hidden.


If two programs race to create the same name, both calls succeed. One creates the sandbox. The other gets HTTP 409 (Conflict) and should look the name up again. The CLI does that for you.
