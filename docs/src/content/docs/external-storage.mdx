import { Aside, Tabs, TabItem } from '@astrojs/starlight/components';

A sandbox's own disk is deleted with the sandbox. To keep data longer, or to work on data that already lives somewhere else, attach your own storage. It shows up as a normal folder inside the sandbox.

## How it works

```mermaid
flowchart LR
    Storage["Your storage<br/>(S3, NFS, SSH server, rclone)"] -- "connected with your credentials" --> Server["AerolVM server<br/>(runs the mount program)"]
    Server -- "a plain folder, no credentials" --> Folder
    subgraph Box["Sandbox"]
        Folder["/workspace"]
    end
```

1. **You list the storage when you create the sandbox,** with its credentials.
2. **The server connects to it** on its own machine. This is called mounting.
3. **The server passes the folder into the sandbox.** Your code reads and writes it like any folder. Your image needs no extra tools, and your credentials never enter the sandbox.

## Attach an S3 bucket

This puts the `prefix` folder of `my-bucket` at `/workspace` inside the sandbox.

Files your code writes to `/workspace` go straight to the bucket, and stay there after the sandbox is deleted. If the mount fails, the create call fails, so you never get a sandbox with a missing folder.

## Kinds of storage you can attach

| Type | What it is | `source` looks like | Credentials |
|---|---|---|---|
| `s3` | An Amazon S3 bucket, or any S3-compatible store | `s3://bucket/prefix` or just `bucket` | `access_key_id`, `secret_access_key`, `session_token` (all optional) |
| `nfs` | A shared folder on your network (NFS) | `host:/exports/path` | None |
| `sshfs` | A folder on any server you can reach with SSH | `user@host:/path` | `private_key_pem` (required) |
| `rclone` | Remote storage that rclone supports, such as Google Drive or Azure. See [which rclone storage is accepted](#which-rclone-storage-is-accepted). | `remote:path`, where `remote` is a section of `rclone_conf`, or `:backend:path` | `rclone_conf` (the text of an `rclone.conf` file) |

### Mounts that would use the server's own cloud login

Give each mount its own keys. Some settings make the mount program sign in with the server's own cloud login instead, such as the cloud machine role of the server it runs on. The server limits them:

- **rclone settings that use the server's login are refused.** These are `env_auth`, `use_msi` and `use_az` (unless set to `false`), the `msi_*` settings (`msi_object_id`, `msi_client_id`, `msi_mi_res_id` and `msi_endpoint`), and Oracle's `provider` values `env_auth`, `instance_principal_auth`, `workload_identity_auth` and `resource_principal_auth`. This holds in `rclone_conf` and in `source`, in both privilege modes. Put the storage's own keys in `rclone_conf` instead.
- **An S3 mount with no credentials depends on the privilege mode.** In the default mode (`single`), it uses the server's own AWS access, such as a cloud machine role, if it has one. This is the same as before. In privilege mode `split` (`SB_PRIVILEGE_MODE=split`), it is refused. Give it `access_key_id` and `secret_access_key`. For a public bucket, add `--no-sign-request` to `extra_args` instead.
- **The operator can allow both.** Set `SB_MOUNTS_ALLOW_NODE_CREDENTIALS=true` and restart. It is `false` by default. `sandboxd` reads it. In privilege mode `split`, the root helper reads it from its own settings too, so set it for both. Turn it on only if everyone with an API token may use the server's cloud login.

## Mount options

| Field | What it does | Default |
|---|---|---|
| `type` | One of `s3`, `nfs`, `sshfs` or `rclone`. | Required |
| `source` | Where the storage is. See the table above. | Required |
| `target` | The folder inside the sandbox, as a full path such as `/data`. | Required |
| `credentials` | Secrets for the storage. They are encrypted and never shown again. | None |
| `options` | Extra settings for each type (below). | None |
| `readOnly` | Let the sandbox read the storage but not change it. | `false` |

Go spells these `Type`, `Source`, `Target`, `Credentials`, `Options` and `ReadOnly`. Rust uses `mount_type` (with `MountType::S3` and so on) and `read_only`. Java has a setter for each.

For example, an NFS share that code can read but not change is `{ type: "nfs", source: "10.0.0.1:/exports/data", target: "/data", readOnly: true }`, with no credentials.

| Type | Option | What it does |
|---|---|---|
| `s3` | `region` | The bucket's region, such as `us-east-1`. |
| `s3` | `endpoint` | The address of an S3-compatible store, such as MinIO or Cloudflare R2. |
| `s3` | `extra_args` | More `mount-s3` flags, separated by spaces, such as `--allow-delete --uid 1000`. Only the flags listed below are accepted. |
| `nfs` | `opts` | NFS mount options, separated by commas, such as `vers=4.1,hard`. The default is `rw`. Only the options listed below are accepted. |
| `rclone` | `vfs_cache_mode` | rclone's file cache mode: `off`, `minimal`, `writes` or `full`. The default is `writes`. |

### Which flags are accepted

The server runs the mount program itself, with full rights on its own machine. So it accepts only flags that change how your storage is reached, read and written. It refuses a flag that names a file or folder on the server, uses the server's own credentials or settings, sends data somewhere else, or starts another program. A refused flag gets a `400` error that names the flag.

In `extra_args`, write a flag as `--flag value` or `--flag=value`. Short forms such as `-d` are refused.

| `mount-s3` flags in `extra_args` | |
|---|---|
| What the sandbox may do | `--allow-delete`, `--allow-overwrite`, `--incremental-upload`, `--read-only`, `--allow-other`, `--allow-root`, `--uid`, `--gid`, `--dir-mode`, `--file-mode` |
| Reaching the bucket | `--region`, `--endpoint-url`, `--force-path-style`, `--transfer-acceleration`, `--dual-stack`, `--requester-pays`, `--no-sign-request`, `--bucket-type`, `--expected-bucket-owner` |
| Writing new objects | `--storage-class`, `--sse`, `--sse-kms-key-id`, `--upload-checksums`, `--infer-content-type` |
| Speed | `--maximum-throughput-gbps`, `--max-threads`, `--memory-target`, `--part-size`, `--read-part-size`, `--write-part-size`, `--metadata-ttl`, `--negative-metadata-ttl` |
| Refused, for example | `--cache`, `--log-directory`, `--ca-bundle`, `--profile`, `--otlp-endpoint`, `--bind`, `--debug`, `--prefix` (use `source` for the prefix) |

| NFS options in `opts` | |
|---|---|
| Version and network | `vers` and `nfsvers` (`3`, `4`, `4.0`, `4.1`, `4.2`), `minorversion`, `proto` and `mountproto` (`tcp`, `udp`, `rdma`, `tcp6`, `udp6`, `rdma6`), `port`, `mountport`, `mountvers`, `nconnect`, `max_connect`, `tcp`, `udp`, `rdma`, `resvport`, `noresvport`, `sec` (`sys`, `krb5`, `krb5i`, `krb5p`, joined with `:`) |
| Timeouts and retries | `hard`, `soft`, `softerr`, `softreval`, `nosoftreval`, `intr`, `nointr`, `timeo`, `retrans`, `retry` |
| Sizes and caching | `rsize`, `wsize`, `bsize`, `namlen`, `ac`, `noac`, `acregmin`, `acregmax`, `acdirmin`, `acdirmax`, `actimeo`, `cto`, `nocto`, `lookupcache` (`all`, `none`, `pos`, `positive`), `sharecache`, `nosharecache`, `rdirplus`, `nordirplus` |
| Locking and ACLs | `lock`, `nolock`, `local_lock` (`all`, `flock`, `posix`, `none`), `acl`, `noacl` |
| General | `ro`, `rw`, `sync`, `async`, `atime`, `noatime`, `diratime`, `nodiratime`, `relatime`, `norelatime`, `strictatime`, `nostrictatime`, `lazytime`, `nolazytime`, `exec`, `noexec`, `nosuid`, `nodev`, `nosymfollow`, `_netdev`, `nofail` |
| Refused, for example | `suid`, `dev`, `defaults`, `remount`, `bind`, `loop`, `helper`, `context`, `x-mount.mkdir`, `bg`, `fsc`, `clientaddr` |

- **Options that take a number take digits only,** such as `timeo=600` or `--uid 1000`. `opts` may not hold spaces or quotes.
- **Every NFS mount gets `nosuid,nodev`,** whatever `opts` says. A program on the share cannot gain extra rights, and a device file on it does not work.
- **`extra_args` is for S3 mounts only, and `opts` for NFS mounts only.** The server refuses them on other types. SSH and rclone mounts take no extra flags.
- **The same rules apply when a sandbox starts again.** A sandbox made before a flag was refused does not start with it: the start fails with an error that names the mount and the flag. Create the sandbox again without that flag.
- **A sandbox that is running when the server restarts keeps its mount, if the refused flag is harmless while the mount runs.** Those flags are `--cache`, `--max-cache-size`, `--debug`, `-d`, `--debug-crt`, `--log-metrics`, `--no-log` and `--auto-unmount` for S3, and `defaults`, `suid`, `dev`, `bg`, `fg`, `fsc`, `auto`, `noauto` and `nouser` for NFS. The mount runs on as it was, but nothing restarts it if it stops, and the sandbox's next start fails as above. Any other refused flag, any refused rclone setting, and a `--cache` folder that is not a full path, is `/`, or is in one of the server's system folders (such as `/etc`, `/usr`, `/var/lib` or `/run`) makes the server unmount the storage right away. That sandbox keeps running without it. Either way the server logs it and writes an audit record (`mounts.refused_kept` or `mounts.refused_removed`) that names the sandbox and the flag.

### Which rclone storage is accepted

rclone takes no flags from you, but `source` and `rclone_conf` pick a storage type (a backend) and set its options. So both are checked: the backend that `source` names, and every `[section]` of `rclone_conf`, whether `source` uses it or not.

- **Accepted backends reach storage over the network:** `s3`, `b2`, `gcs` (or `google cloud storage`), `drive`, `dropbox`, `onedrive`, `box`, `azureblob`, `azurefiles`, `swift`, `sftp`, `ftp`, `http`, `webdav`, `smb`, `pcloud`, `mega`, `jottacloud`, `koofr`, `yandex`, `mailru`, `opendrive`, `pikpak`, `putio`, `qingstor`, `seafile`, `sharefile`, `storj`, `sugarsync`, `zoho`, `hidrive`, `internetarchive`, `netstorage`, `oracleobjectstorage`, `protondrive`, `quatrix`, `filefabric`, `fichier`, `premiumizeme`, `linkbox`, `pixeldrain` and `gphotos` (or `google photos`).
- **`alias`, `crypt`, `chunker`, `compress` and `hasher` are accepted when they wrap one of those:** their `remote` must be another section of `rclone_conf` or `:backend:path`.
- **Refused backends:** `local` (a folder on the server), `union`, `combine`, `cache`, `hdfs`, and any backend not listed.
- **Refused options:** `ssh` and any option ending in `_command` (they run a program), any option ending in `_file`, `_path` or `_dir` (a file or folder on the server, such as `key_file`), `key_use_agent`, `profile`, and any `global.` or `override.` option. Put key material in the config itself instead, for example `key_pem` for `sftp`.
- **In `source`, settings after a comma are checked the same way** (`remote,key_file=...:path` is refused), and `type`, `remote` and `upstreams` cannot be set there.
- **`rclone_conf` must be plain:** `[section]` lines and `key = value` lines. An encrypted `rclone.conf` is refused, since its settings cannot be checked.

## What happens when the sandbox stops

```mermaid
stateDiagram-v2
    direction LR
    [*] --> Connected: create
    Connected --> Disconnected: stop
    Disconnected --> Connected: start
    Connected --> [*]: delete
    Disconnected --> [*]: delete
```

- **Stop** disconnects the storage, and **start** connects it again. After a server restart, it connects again the next time the sandbox starts.
- **Delete** disconnects the storage. Your data stays in the bucket or share.
- **If the mount program crashes,** the server restarts it once. If it crashes twice within 30 seconds, the server gives up and removes the mount.

## Keeping credentials safe

- **Credentials never enter the sandbox.** Only the server's mount program sees them, and they are stored encrypted (AES-256-GCM).
- **Reading the mounts back shows no secrets.** `client.mounts(id)` (Go: `client.Mounts(ctx, id)`) returns `hasCredentials: true`, never the values. Rust calls the field `has_credentials`.
- **`source` and `options` are not secret.** Reading the mounts back shows them. In a cluster they are copied as plain text to other servers, so another one can mount the storage if this one fails.
- **A mount program's arguments are not secret either.** Other programs on the server can read them while the mount runs.
- **So every secret belongs in `credentials`.** The server refuses a create that puts a secret-like name in `options` or `source`. Examples are an `extra_args` flag like `--s3-secret-access-key` or `--key`, a word like `AWS_SECRET_ACCESS_KEY=...`, or an rclone source like `:s3,secret_access_key=...:bucket`. It also refuses an AWS access key id, and a link with a user name or password in it (`https://user:pass@host`). The error names the field to use instead, never the secret.

<Aside type="caution" title="Anyone with an API token is trusted with the server">
The mount programs (`mount-s3`, `mount`, `sshfs`, `rclone`) run on the server itself, outside every sandbox, as the server's own user. They receive your `source` and `options`. The server refuses a `source` that a mount program could mistake for one of its own options, and accepts only the [flags](#which-flags-are-accepted) and [rclone storage](#which-rclone-storage-is-accepted) listed above. Still, give API tokens only to people you would trust to run the server.
</Aside>

## Good to know

- **Up to 8 mounts per sandbox.** [Platform volumes](/platform-volumes/) count toward the same 8.
- **Credentials can have up to 32 keys and 4 KB in total** for each mount.
- **Some folders are off limits** as a `target`: `/`, `/proc`, `/sys`, `/dev`, `/etc`, `/usr`, `/bin`, `/sbin`, `/lib`, `/lib32`, `/lib64`, `/boot`, `/run` and `/var/run`. So is the folder where the server puts its own helper program inside the sandbox.
- **Outbound network rules do not cover mounts.** [Network access](/network-access/) controls traffic from inside the sandbox. The mount runs on the server, so it can still reach the storage.
- **Which sandboxes support mounts:** Docker, gVisor and WebAssembly sandboxes. Firecracker and V8 isolate sandboxes refuse them.
- **An SSH server's host key is trusted on first use.** The server accepts the storage server's key the first time it connects.
- **The server needs the mount program installed.** The [server installer](/getting-started/installer-options/) adds them, and so does the [Kubernetes](/kubernetes/) worker image. A server without the program for a mount, such as a [local install](/getting-started/local-setup/), refuses the sandbox with `501` and the code `mount_tool_unavailable`. The error names the missing program. Retrying does not help: the operator installs the program, or you create the sandbox without the mount.
- **On Kubernetes, the operator turns external storage on.** It is off by default: a create with a mount gets `501` and the code `mounts_unavailable`, and the sandbox is not made. The operator turns it on with the chart value [`worker.externalStorage.enabled`](/kubernetes/values/). Retrying does not help.
- **In a cluster, a sandbox with a mount is not rebuilt on another node.** A mount runs on the server, and only the operator or an admin may add one, so another node does not take it from the sandbox's record. With `failover.policy = "recreate"`, when the sandbox's node dies the sandbox waits for that node to return instead of moving to another node. [Platform volumes](/platform-volumes/) are the exception: they move with the sandbox, unless the operator has since moved the platform volumes to another bucket or NFS server.
- **On Kubernetes, the mount is checked before the sandbox starts.** A worker pod mounts the storage in one container and builds the sandbox in another, so before it answers, the worker checks the sandbox will really see the mount. If it would not, the create fails and the mount is removed: the sandbox never writes to its own disk while you think it writes to your storage. The mount programs keep running when the worker's agent restarts, so a running sandbox keeps its storage.
