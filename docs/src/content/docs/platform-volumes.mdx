A platform volume is named storage that outlives your sandboxes. Your server operator connects AerolVM to one shared storage system, such as an S3 bucket or a network share. You only pick a name and a folder. You never handle a bucket address or credentials.

A platform volume:

- has a **name** that belongs to your account;
- **keeps its files** when a sandbox stops or is deleted;
- can be **attached again by the same name** from a later sandbox, on any server in a cluster;
- can be **shared** by several sandboxes at once.

## Attach a volume

The first time you use a name, the volume is created. After that, the same name brings back the same files. This attaches the volume `data` at `/workspace`.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({
      image: "ubuntu:22.04",
      platformVolumes: [{ name: "data", path: "/workspace" }],
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox = client.create(
        image="ubuntu:22.04",
        platformVolumes=[{"name": "data", "path": "/workspace"}],
    )
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    sandbox, err := client.Create(ctx, sdktypes.CreateSandboxOptions{
        Image: "ubuntu:22.04",
        PlatformVolumes: []sdktypes.PlatformVolumeMount{
            {Name: "data", Path: "/workspace"},
        },
    })
    if err != nil {
        log.Fatal(err)
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    use aerolvm_sdk::PlatformVolumeMount;

    let sandbox = client.create(CreateOptions {
        image: "ubuntu:22.04".into(),
        platform_volumes: Some(vec![PlatformVolumeMount {
            name: "data".into(),
            path: "/workspace".into(),
            read_only: None,
        }]),
        ..Default::default()
    })?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    Sandbox sandbox = client.create(new CreateOptions()
        .setImage("ubuntu:22.04")
        .setPlatformVolumes(List.of(
            new PlatformVolumeMount().setName("data").setPath("/workspace"))));
    ```
  </TabItem>
</Tabs>

| Field | What it does | Default |
|---|---|---|
| `name` | The volume's name. | Required |
| `path` | The folder inside the sandbox, as a full path. | Required |
| `readOnly` | Let the sandbox read the files but not change them. | `false` |

Go spells these `Name`, `Path` and `ReadOnly`. Rust uses `read_only`. Python also accepts `platform_volumes` and `read_only`.

<Aside>
Platform volumes only work when your operator has turned them on. If they are off, every request that uses a volume fails with HTTP 412 (Precondition Failed). See [For server operators](#for-server-operators).
</Aside>

## Use the same files from another sandbox

Give a second sandbox the same name to see what the first one wrote. The files live in shared storage, so the second sandbox can run on a different server and still read them. Here the second sandbox gets the volume read-only.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    // The first sandbox writes into the volume.
    const writer = await client.create({
      image: "ubuntu:22.04",
      platformVolumes: [{ name: "data", path: "/workspace" }],
    });

    // A second sandbox reads the same files, but cannot change them.
    const reader = await client.create({
      image: "ubuntu:22.04",
      platformVolumes: [{ name: "data", path: "/workspace", readOnly: true }],
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    # The first sandbox writes into the volume.
    writer = client.create(
        image="ubuntu:22.04",
        platformVolumes=[{"name": "data", "path": "/workspace"}],
    )

    # A second sandbox reads the same files, but cannot change them.
    reader = client.create(
        image="ubuntu:22.04",
        platformVolumes=[{"name": "data", "path": "/workspace", "readOnly": True}],
    )
    ```
  </TabItem>
  <TabItem label="Go">

## Platform volume or your own storage?

| | [Attach cloud storage](/external-storage/) | Platform volume |
|---|---|---|
| Who owns the storage | You: your bucket and your keys | Your operator: one shared store |
| What you pass | A `source` and `credentials` | Only a `name` |
| How long the files last | As long as your storage keeps them | Until the volume is deleted |
| In a cluster | Works, because you point at your own store | Works, because the shared store holds the files |

## Naming rules

- Names are turned into lowercase. They may use only `a` to `z`, `0` to `9`, `.`, `_` and `-`. Any other character is refused, not removed.
- A name can be up to 64 characters. `.` and `..` are not allowed.
- **Each account has its own names.** Two tenants (separate accounts on the same server) can both use `data`, and each gets separate storage.

## Good to know

- **Deleting a sandbox never deletes the volume's files.** Attach the same name again to get them back.
- **Only Docker and gVisor sandboxes** can attach platform volumes. Firecracker, WebAssembly and V8 isolate sandboxes refuse them with HTTP 400.
- **A sandbox can have up to 8 mounts in total.** Platform volumes and [cloud storage mounts](/external-storage/) share that limit.
- **Your operator can limit how many volumes each account has.** Going over the limit fails with HTTP 409 (Conflict).
- **Two writers at once can lose data.** The S3 store has no file locking, and a change can take a moment to show up elsewhere. Use one sandbox that writes and others that attach read-only, or coordinate writes in your app.
- **There is no AerolVM SDK call to list or delete volumes yet.** The [Daytona SDK](/using-daytona-sdk/) can list, get and delete them through AerolVM. Deleting a volume also deletes its files, in the background. A volume that a sandbox still has attached cannot be deleted (HTTP 409).
- **The E2B SDK** can attach volumes too, with its `volumeMounts` option. See [Use the E2B SDK](/using-e2b-sdk/).

## For server operators

Platform volumes are off by default. Turn them on by pointing the server at one shared storage backend.

S3, or any S3-compatible store such as Cloudflare R2 or MinIO:

```bash
SB_PLATFORM_VOLUMES_ENABLED=true
SB_PLATFORM_VOLUMES_BACKEND=s3
SB_PLATFORM_VOLUMES_S3_BUCKET=my-org-volumes
SB_PLATFORM_VOLUMES_S3_PREFIX=volumes            # optional, default "volumes"
SB_PLATFORM_VOLUMES_S3_REGION=us-east-1
SB_PLATFORM_VOLUMES_S3_ENDPOINT=                 # optional, for R2 or MinIO
SB_PLATFORM_VOLUMES_S3_ACCESS_KEY_ID=...         # leave out to use the machine's cloud role
SB_PLATFORM_VOLUMES_S3_SECRET_ACCESS_KEY=...
SB_PLATFORM_VOLUMES_MAX_PER_TENANT=0             # 0 means no limit
```

NFS, a shared network folder that needs no credentials:

```bash
SB_PLATFORM_VOLUMES_ENABLED=true
SB_PLATFORM_VOLUMES_BACKEND=nfs
SB_PLATFORM_VOLUMES_NFS_SERVER=10.0.0.5
SB_PLATFORM_VOLUMES_NFS_EXPORT=/exports/volumes
SB_PLATFORM_VOLUMES_NFS_OPTIONS=vers=4.1         # optional
```

| Setup | What happens |
|---|---|
| Off or not set | Every volume request fails with HTTP 412. |
| On, but a required setting is missing | The server refuses to start, so you find out at once. |
| On and fully set | Volumes attach normally. |

You own and pay for the shared store, and you set any lifecycle or retention rules on it. The store's credentials are encrypted at rest. No read API returns them, and they never enter a sandbox, because the mount runs on the server.

When a volume is deleted, its files are removed in the background. These settings control that cleanup:

| Variable | What it does | Default |
|---|---|---|
| `SB_PLATFORM_VOLUMES_RECLAIM_INTERVAL` | How often the server looks for deleted volumes to clean up. | `5m` |
| `SB_PLATFORM_VOLUMES_RECLAIM_CONCURRENCY` | How many cleanups run at the same time. | `8` |
| `SB_PLATFORM_VOLUMES_RECLAIM_MOUNT_ROOT` | The scratch folder used while cleaning up NFS volumes. | `/var/lib/aerolvm/volume-reclaim` |
