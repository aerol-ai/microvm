A Firecracker sandbox runs inside its own small virtual machine, called a microVM, instead of a container. A virtual machine is a whole computer made in software. Each one boots its own Linux kernel (the core of the operating system).

Containers all share the server's kernel. A Firecracker sandbox does not, so a kernel bug inside one sandbox cannot reach the server or the other sandboxes. The wall between them is enforced by the CPU's hardware.

Choose Firecracker when:

- you run untrusted or AI-written code that must have no path to the server's kernel;
- you need a virtual-machine boundary for compliance or to keep customers apart;
- you want stronger walls than [gVisor](/gvisor-sandbox/), but faster starts than a full virtual machine.

## How fast it starts

The start time depends on whether you use a template, a disk image prepared ahead of time (see [Firecracker templates](/firecracker-templates/)).

| How you create it | Typical start time |
|---|---|
| From a template | About 34 ms on the server (median, on an AWS `c5.metal` test server). Measured from a laptop, about 300 ms, most of it network travel time. |
| From an image, no template | 10 to 60 seconds. The server builds a fresh disk image from the container image on every create. |

## What the server needs

Firecracker needs KVM, the Linux feature that lets the CPU run virtual machines. It shows up on the server as `/dev/kvm`.

- **Your own hardware:** any Linux server with hardware virtualization turned on.
- **Cloud servers:** standard AWS types such as `t3`, `c6i` and `m5` are virtual machines themselves and do not offer `/dev/kvm`. Use a bare-metal type instead, such as `c5.metal` or `m5.metal`.

Firecracker is off by default. The server operator turns it on (see [For server operators](#for-server-operators)). Until they do, a create fails with `runtime "firecracker" requires SB_ENABLE_FIRECRACKER=true`.

## Create a Firecracker sandbox

Add `runtime: "firecracker"` and a normal container image. The server turns the image into a virtual machine disk, boots it, and runs your command inside.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    import { MicroVM } from "@aerol-ai/aerolvm-sdk";

    const client = new MicroVM(); // reads SB_API_URL and SB_PAT_TOKEN

    const sandbox = await client.create({ image: "ubuntu:22.04", runtime: "firecracker" });
    const result = await sandbox.exec("uname -r");
    console.log(result.stdout); // the sandbox's own kernel version

    await sandbox.destroy();
    ```
  </TabItem>

## Start in milliseconds with a template

A template is a disk image plus a saved, paused copy of a booted VM. A sandbox made from a template skips the image build and the kernel boot. See [Firecracker templates](/firecracker-templates/) to build one and create sandboxes from it.

## Set resources and auto-stop

This sandbox gets 2 CPU cores and 1 GB of memory. It stops after 30 idle minutes and is deleted when it is 4 hours old. Timer values are in nanoseconds, except in Go, which uses `time.Duration`.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({
      image: "ubuntu:22.04",
      runtime: "firecracker",
      cpu: 2,
      memoryMB: 1024,
      lifecycle: {
        stopIfIdleFor: 30 * 60 * 1_000_000_000,     // 30 minutes
        destroyAtAge:  4 * 60 * 60 * 1_000_000_000, // 4 hours
      },
    });
    ```

## Good to know

- **Memory is reserved up front.** A container uses memory only as it needs it. A Firecracker VM takes its full `memoryMB` the moment it starts. Ask only for what the program needs.
- **Stop saves the whole VM.** Stopping writes the VM's memory and disks to the server's disk. Start brings it back with the same internal IP address. Delete removes the saved copy.
- **No resizing yet.** Changing CPU or memory on a running Firecracker sandbox fails with `not yet implemented`. Create a new sandbox with the size you need.
- **No GPU.** Firecracker VMs cannot use the server's GPU.

## For server operators

Turn Firecracker on with `SB_ENABLE_FIRECRACKER=true` in the server's environment file. The install script has no flag for it. Before you restart the server, put these files in place:

| Setting | What it points to | Default |
|---|---|---|
| `SB_FIRECRACKER_BINARY` | The `firecracker` program. | `/usr/local/bin/firecracker` |
| `SB_FIRECRACKER_KERNEL` | The Linux kernel the VMs boot. A `<kernel>.config` file with `CONFIG_VMGENID=y` must sit next to it. | `/var/lib/sandboxd/firecracker/vmlinux` |
| `SB_FIRECRACKER_USE_JAILER` | Run each VM under Firecracker's `jailer`, which locks the VM process into its own folder and user. | `true` |
| `SB_FIRECRACKER_SKOPEO_BIN`, `SB_FIRECRACKER_UMOCI_BIN`, `SB_FIRECRACKER_MKFS_BIN` | The tools that turn a container image into a VM disk. | `/usr/bin/skopeo`, `/usr/bin/umoci`, `/sbin/mkfs.ext4` |

On a cluster, set `with_firecracker = true` and a bare-metal `instance_type` on each worker, and add a `firecracker` block with download links for the binaries and kernel. See [Cluster setup](/cluster-setup/).

For how the VMs, snapshots and networking work inside, see [Firecracker architecture](/firecracker-architecture/).
