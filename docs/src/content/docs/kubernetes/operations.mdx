Most of this page is about cluster mode, where the operator does the work. Single mode has one pod: its [upgrade](/kubernetes/single-node/#upgrade) is on its own page, and [monitoring](#monitoring) works the same in both modes.

## Workers scale with load

The operator reads AerolVM's own numbers: how much CPU and memory is free on each worker, per zone. It keeps each worker pool's `headroomPercent` free in every zone:

- **A zone runs short:** the operator adds a worker pod there. It fits on no machine yet, so Karpenter, Node Auto Provisioning or Cluster Autoscaler starts one. That takes a minute or two; the headroom covers the wait.
- **A zone has twice the room it needs:** the operator picks the emptiest worker there and [decommissions](#replace-a-machine) it. The machine is then empty, and Karpenter takes it back.

The worker pod itself is what Kubernetes sees. There are no placeholder pods. `minWorkers` and `maxWorkers` bound each pool.

## Replace a machine

Machines go away on purpose all the time: a new AMI, a Kubernetes upgrade, a smaller pool. The rule: **the operator moves sandboxes off a machine before the machine goes.**

It starts a **decommission** when:

- the machine is cordoned;
- Karpenter marks it drifted;
- the pool shrinks;
- the machine is older than `maxMachineAge`;
- its pool is removed from `cluster.workerPools`.

Old machines and a removed pool's workers leave one per zone at a time, so their sandboxes have somewhere to go.

1. **Drain.** The worker takes no new sandboxes. For the `drainWindow` (15 minutes by default), sandboxes may finish by themselves.
2. **Move.** A sandbox created with `failover.policy: recreate` moves to a worker in another zone. The new worker pulls the image first; then the old copy stops and the new one starts, with the same ID and the same links. It is down for a few seconds.
   A Firecracker or gVisor sandbox without that policy moves **with its memory**: it is saved, copied to another worker over the cluster's encrypted link, and started there where it left off. Its programs keep running and its files stay; open connections drop. If a move fails, the sandbox starts again where it was, and the next pass tries again. A sandbox with external storage mounted does not move this way. `worker.gvisor.checkpointMoves: false` turns off gVisor moves.
3. **Tell.** The owner of every other sandbox finds a notice in the sandbox's audit log, with the time it will stop.
4. **Finish.** At the `deadline` (45 minutes by default), whatever could not move stops. The worker leaves the cluster, its pod goes, and the machine is handed back. With `provisioner: eks-managed`, the whole decommission takes at most 14 minutes, inside the managed node group's 15-minute limit.

Each step is saved on the worker's `AerolNode`, so an operator restart picks up where it stopped. `kubectl describe aerolnode <name>` shows the progress as events.

**To replace one machine now**, cordon it. The operator does the rest:

```bash title="Your machine"
kubectl cordon <node>
```

**A worker pod cannot be removed by mistake.** A validating webhook refuses `kubectl delete pod` on a live worker, also while its sandboxes are moving. A PodDisruptionBudget allows no eviction, so `kubectl drain`, node group updates and Karpenter wait while the operator moves the sandboxes; the operator then deletes the pod itself. To delete one anyway, annotate the pod `aerolvm.io/force-delete=true` first. The delete is logged. The webhook fails open, so a down operator never blocks a repair.

On an EKS managed node group, suspend the Auto Scaling group's `AZRebalance` process on worker node groups: AZRebalance and scale-in do not wait for the PodDisruptionBudget.

<Aside>
A machine that dies without warning is different: nothing can be moved. Sandboxes with `failover.policy: recreate` start again on a worker in another zone after about 30 seconds, or 16 seconds once the operator sees the machine is gone. Other sandboxes on it are lost.
</Aside>

Servers never move zone: EBS and Azure disks cannot cross zones, so each server stays with its disk.

## Upgrade

In cluster mode, one `helm upgrade` moves the whole cluster. Clone the [new release](/kubernetes/#get-the-chart), then:

```bash title="Your machine"
helm upgrade aerolvm charts/aerolvm --namespace aerolvm-system -f aerolvm-cluster.yaml
```

Two values decide the version, and both default to the chart's `appVersion`:

- `image.tag`: the operator's image.
- `cluster.version`: the AerolVM release every server, gateway and worker runs.

So with neither set, a new chart moves both. **If you pin one, pin both to the same version.**

What happens:

1. **The CRDs update first.** Helm installs a chart's CRDs on the first install and never updates them, so the chart runs a short Job that updates `AerolCluster` and `AerolNode`, then removes itself. That Job may touch those two CRDs and nothing else.
2. **The operator rolls**, as a normal Deployment.
3. **The operator upgrades the cluster in order:** servers one at a time with the Raft leader last, then gateways, then workers in batches. On each worker it swaps the AerolVM server in place. **Sandboxes keep running.**

Watch it: `kubectl -n aerolvm-system get aerolcluster` shows `VERSION` (wanted) and `RUNNING`. `aerolvm upgrade status` shows each node.

**To roll back**, set `cluster.version` back and run `helm upgrade` again. A `helm rollback` works too, and keeps the newer CRDs: their new fields do no harm to an older operator.

The operator owns the version here, so `aerolvm upgrade apply` and `aerolvm upgrade rollback` refuse. `status`, `stop`, `resume` and `finalize` work as usual.

**If someone else manages your CRDs**, set `cluster.operator.upgradeCRDs: false`, and apply them yourself before each upgrade:

```bash title="Your machine"
helm show crds charts/aerolvm | kubectl apply --server-side --force-conflicts -f -
```

## Back up and restore the servers

The servers hold the cluster's records: which sandboxes exist and where they run. Back them up with `sandboxd backup`, run inside a server pod in **maintenance mode**:

```bash title="Your machine"
# 1. Put one server in maintenance mode. The operator makes its pod again,
#    with its disk but without the AerolVM server running.
kubectl -n aerolvm-system annotate aerolnode aerolvm-server-0 aerolvm.io/maintenance=true

# 2. Take the backup, and copy it out.
kubectl -n aerolvm-system exec aerolvm-server-0 -- sandboxd backup --output /var/lib/sandboxd/backup.tgz
kubectl -n aerolvm-system cp aerolvm-server-0:/var/lib/sandboxd/backup.tgz ./aerolvm-backup.tgz

# 3. Bring the server back.
kubectl -n aerolvm-system annotate aerolnode aerolvm-server-0 aerolvm.io/maintenance-
```

`sandboxd restore` and `sandboxd recover-quorum` run the same way. To recover after losing most servers, put **every** surviving server in maintenance mode first. `recover-quorum` refuses while the AerolVM server runs on any of them. And the operator replaces no lost server while one is in maintenance. The [runbooks](/operational-runbooks/) walk through it.

## GitOps with Argo CD

You can manage the release, or the `AerolCluster` object directly, from Argo CD. Two things to set:

- **CRDs.** Argo CD applies the chart's CRDs on every sync, so set `cluster.operator.upgradeCRDs: false`.
- **Health.** Argo CD does not know an `AerolCluster`'s or `AerolNode`'s health. Add these checks to the `argocd-cm` ConfigMap. An app then shows Progressing while the cluster builds or upgrades, Healthy when it is Ready, and Degraded when a server is missing or a worker's machine failed its checks:

```yaml title="argocd-cm"
data:
  resource.customizations.health.aerolvm.io_AerolCluster: |
    hs = { status = "Progressing", message = "waiting for the operator" }
    if obj.status ~= nil and obj.status.phase ~= nil then
      local p = obj.status.phase
      hs.message = p
      if p == "Ready" then hs.status = "Healthy"
      elseif p == "Degraded" or p == "Refused" then hs.status = "Degraded"
      end
      if obj.status.observedGeneration ~= nil and obj.status.observedGeneration < obj.metadata.generation then
        hs.status = "Progressing"
        hs.message = "the operator has not seen the latest change yet"
      end
    end
    return hs
  resource.customizations.health.aerolvm.io_AerolNode: |
    hs = { status = "Progressing", message = "starting" }
    if obj.status ~= nil and obj.status.state ~= nil then
      local st = obj.status.state
      hs.message = st
      if obj.status.reason ~= nil and obj.status.reason ~= "" then
        hs.message = st .. ": " .. obj.status.reason
      end
      if st == "Serving" or st == "Maintenance" then hs.status = "Healthy"
      elseif st == "Failed" or st == "Dead" or st == "Suspect" then hs.status = "Degraded"
      end
    end
    return hs
```

A worker that is draining or decommissioning shows Progressing: it is leaving on purpose.

## Monitoring

The chart can set up Prometheus and Grafana for you, in both modes. It needs the Prometheus Operator, which [kube-prometheus-stack](https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack) installs. It is off by default, because without the Prometheus Operator's CRDs the install would fail.

```bash title="Your machine"
helm upgrade aerolvm charts/aerolvm --namespace <namespace> --reuse-values \
  --set monitoring.enabled=true \
  --set monitoring.labels.release=kube-prometheus-stack
```

`monitoring.labels` must match what your Prometheus selects. kube-prometheus-stack selects objects labelled with its own release name, shown here as `kube-prometheus-stack`.

You get:

- **Scraping.** A ServiceMonitor per kind of pod. Prometheus reads [`/v1/metrics`](/dashboard/#collect-metrics-with-prometheus) on every AerolVM pod, once each.
- **24 alerts** in a PrometheusRule: a pod not ready, a `runtime` container that restarted, a disk filling up, no room for new sandboxes, a stuck upgrade, and more. Each links to its entry in the [Kubernetes runbook](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/kubernetes.md), which says what it means and what to do.
- **Two Grafana dashboards**, as ConfigMaps for the Grafana sidecar: **AerolVM on Kubernetes** (health, room, sandboxes, failover, upgrades) and **AerolVM usage per team**. The sidecar must watch the namespace they land in (`monitoring.dashboardsNamespace`, by default the release namespace).
- **The [usage per team](#usage-per-team) recording rules.**

Good to know:

- **Three alerts read kube-state-metrics:** `AerolVMPodNotReady`, `AerolVMRuntimeContainerRestarted` and `AerolVMPodImagePullStuck`. kube-prometheus-stack runs it. Without it, list them in `monitoring.prometheusRule.disabledAlerts`.
- **Alerts about nodes and upgrades** never fire in single mode.
- **In cluster mode**, the workers' NetworkPolicy lets only `monitoring.prometheusNamespace` (`monitoring` by default) read their metrics.

### Use a read-only scrape token

Prometheus needs a token to read `/v1/metrics`. By default it uses the API token, which can do everything. If you turned on API tokens (`SB_IDENTITY_ENABLED: "true"` in `worker.extraEnv`), make a read-only token and put it in a Secret in the release namespace:

```bash title="Your machine"
kubectl -n <namespace> create secret generic aerolvm-metrics-token \
  --from-literal=token="$(aerolvm token create --name prometheus --role viewer --team '*' --expires-in 90d)"
```

Then set `monitoring.scrapeToken.existingSecret=aerolvm-metrics-token`. Make a new token before this one expires.

## Usage per team

A worker pod asks Kubernetes for a whole machine, so OpenCost or Kubecost sees one big pod, not which team used it. To fill the gap, each worker adds four counters per **owner** (the team a sandbox belongs to) to its `/v1/metrics`:

| Counter | What it adds up | Use |
|---|---|---|
| `aerolvm_usage_reserved_cpu_seconds_total` | Each running sandbox's CPU limit × seconds it ran | The charge |
| `aerolvm_usage_reserved_memory_mib_seconds_total` | Each running sandbox's memory limit in MiB × seconds | The charge |
| `aerolvm_usage_consumed_cpu_seconds_total` | CPU time sandboxes really used, from their cgroups | Shown, never billed |
| `aerolvm_usage_consumed_memory_mib_seconds_total` | Memory sandboxes really held, in MiB × seconds | Shown, never billed |

Labels: `owner` (empty for sandboxes made with the main API token) and `incarnation` (new each time the server starts, so counters never go back to zero).

**Reserved is the charge**: a sandbox's limits block that room for everyone else, used or not. Consumed sits beside it, so a team can see how much of its room it really uses.

Good to know:

- **Units, not money.** Your cost tool knows what each worker pod costs; these counters say how to split it.
- **Nothing is sent anywhere.** The counters stay in the pod until Prometheus scrapes them. `worker.usageMetrics.enabled=false` turns them off.
- **Sampled every 15 seconds.** A team's series stays for an hour after its last sandbox on that worker stops.
- **Consumed needs a cgroup per sandbox.** runc and gVisor sandboxes have one. Firecracker, WASM and V8 isolate sandboxes are charged for what they reserve, but show no consumed use.

### The recording rules

With [monitoring](#monitoring) on, the chart adds these rules for you, with an `aerolvm_cluster` label. Without it, scrape `/v1/metrics` on every worker pod and add them yourself:

```yaml title="aerolvm-usage-rules.yml"
groups:
  - name: aerolvm-usage
    rules:
      # CPUs and MiB each team holds, averaged over 5 minutes.
      - record: owner:aerolvm_usage_reserved_cpu_seconds:rate5m
        expr: sum by (owner) (rate(aerolvm_usage_reserved_cpu_seconds_total[5m]))
      - record: owner:aerolvm_usage_reserved_memory_mib_seconds:rate5m
        expr: sum by (owner) (rate(aerolvm_usage_reserved_memory_mib_seconds_total[5m]))
      - record: owner:aerolvm_usage_consumed_cpu_seconds:rate5m
        expr: sum by (owner) (rate(aerolvm_usage_consumed_cpu_seconds_total[5m]))
      - record: owner:aerolvm_usage_consumed_memory_mib_seconds:rate5m
        expr: sum by (owner) (rate(aerolvm_usage_consumed_memory_mib_seconds_total[5m]))
      # A worker whose usage counters stopped moving for 10 minutes.
      - alert: AerolVMUsageExporterStale
        expr: time() - aerolvm_usage_last_sample_timestamp_seconds > 600
        for: 5m
```

A rate of seconds per second is a count of CPUs (or MiB) held. Each worker keeps its own counters, so a restart, a worker leaving, or a new leader loses or double-counts nothing that was scraped. With many workers and teams, keep the recorded sums for long-term storage and the raw counters only as long as you need them.

### Split a worker's cost by team

For each worker pod, over a window such as one day:

1. **CPU share:** the team's increase in `aerolvm_usage_reserved_cpu_seconds_total` on that pod, divided by the larger of: all teams' increase on that pod, or the pod's CPU request × the window's seconds.
2. **Memory share:** the same with `aerolvm_usage_reserved_memory_mib_seconds_total` and the pod's memory request in MiB.
3. **Charge** the team the pod's CPU cost × its CPU share, plus the pod's memory cost × its memory share.
4. **Book the rest as idle:** room no sandbox reserved, plus AerolVM's own containers. Give it to the team that runs AerolVM.

The shares never add up to more than one, so each pod's cost is counted once. Step 1 in PromQL, for the last day (the pod's request comes from kube-state-metrics, and the `pod` label from your scrape setup):

```text title="PromQL"
sum by (pod, owner) (increase(aerolvm_usage_reserved_cpu_seconds_total[1d]))
/ on (pod) group_left
(
  (
    sum by (pod) (increase(aerolvm_usage_reserved_cpu_seconds_total[1d]))
    >= on (pod)
    86400 * sum by (pod) (kube_pod_container_resource_requests{namespace="aerolvm-workers", resource="cpu"})
  )
  or on (pod)
  86400 * sum by (pod) (kube_pod_container_resource_requests{namespace="aerolvm-workers", resource="cpu"})
)
```
