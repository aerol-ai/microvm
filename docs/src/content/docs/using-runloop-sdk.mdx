AerolVM serves a Runloop-compatible API under `/runloop`, so code written against the official Runloop SDKs (`@runloop/api-client` for TypeScript, `runloop_api_client` for Python) can run its devboxes on an AerolVM server. Both SDKs read their server address from `RUNLOOP_BASE_URL`, so switching is an environment change. A devbox is an ordinary AerolVM sandbox, so it also shows up in `/v1`, the dashboard and the CLI.

## Required environment

```bash
export RUNLOOP_BASE_URL=https://sandbox.example.com/runloop
export RUNLOOP_API_KEY="$SB_PAT_TOKEN"
```

Point `RUNLOOP_BASE_URL` at the `/runloop` prefix, not at `/runloop/v1`: the SDKs add `/v1/...` themselves. `RUNLOOP_API_KEY` takes the same credentials as the rest of the API: the operator PAT, or a user token when a control plane is attached.

The TypeScript SDK on Node talks HTTP/2 by default. Behind TLS that is negotiated as usual; on a plain `http://` base URL it opens with HTTP/2 directly (h2c), which sandboxd's listener accepts alongside HTTP/1.1.

## What works today

- Devboxes: create (including `create_and_await_running`, which both SDKs use), get, list, update name and metadata, suspend, resume, keep-alive, shutdown, and `wait_for_status`.
- Commands: `execute`, `execute_async`, `execute_sync`, execution status and `wait_for_status`, kill, and `send_std_in` with text. Named shells (`devbox.shell(name)`) keep their working directory and environment between commands.
- Output streaming (`stream_stdout_updates`, `stream_stderr_updates`), which the SDKs use for output callbacks and for output past `last_n` lines.
- Files: `read_file_contents`, `write_file_contents`, `upload_file`, `download_file`. Relative paths resolve against the devbox user's home directory, as on Runloop.
- Disk snapshots: `snapshot_disk`, `snapshot_disk_async`, status, list (with `devbox_id` and `metadata[...]` filters), update, delete, and creating a devbox from `snapshot_id`.
- Retries are safe. Both SDKs resend the same `x-request-id` (and the same `command_id` on `execute`) when they retry, and the facade answers a retry with the devbox, execution or snapshot the first attempt made. A retried command never runs twice, even after sandboxd restarts: the facade remembers each command until 24 hours after it finishes. If the facade cannot tell whether a command ran, for example because its devbox restarted while it ran, a retry with the same `command_id` gets `409`. Send it with a new `command_id` if you still want it to run. Keep proxies in front of sandboxd from rewriting `X-Request-Id`.

## How Runloop settings map

| Runloop | AerolVM |
|---|---|
| `blueprint_id` / `blueprint_name` | An image, looked up in `SB_RUNLOOP_BLUEPRINT_MAP_JSON` (a JSON object of blueprint name to image). With neither set, the `default` entry is used, `ubuntu:22.04` unless you map it. An unmapped blueprint is refused. |
| `snapshot_id` | The snapshot's committed image. In a cluster, the new devbox runs on the node that holds the snapshot. |
| `launch_parameters.resource_size_request` | CPU, memory and disk from Runloop's size table; `CUSTOM_SIZE` uses the `custom_*` fields. |
| `launch_parameters.keep_alive_time_seconds` | The devbox is destroyed that long after create. Defaults to one hour, as on Runloop. |
| `launch_parameters.after_idle` | `on_idle: suspend` stops the devbox after the idle time; `shutdown` destroys it. `keep_alive` resets the idle clock. |
| `metadata` | Sandbox [tags](/sandbox-tags). |
| shutdown | Destroys the sandbox. Shutdown is terminal on Runloop too, and keeping the stopped container would hold its disk. |

```bash
export SB_RUNLOOP_BLUEPRINT_MAP_JSON='{"default":"ubuntu:24.04","python":"python:3.12"}'
```

## Current gaps

- Tunnels answer `501` (`enable_tunnel`, `remove_tunnel`, and PTY tunnels), as does `tunnel` on a create. `getTunnelUrl` is a client-side SDK helper, not a server call — it builds `{port}-{key}.tunnel.{domain}`, which does not match AerolVM's port routes, so the URL never resolves. To share a port, use the AerolVM SDK's `exposePort`; see [Public URLs](/public-urls/).
- Create fields with no equivalent are refused with `501` rather than ignored: `entrypoint`, `launch_commands`, `secrets`, `mounts`, `code_mounts`, `file_mounts`, `gateways`, `mcp`, `user_parameters`, `network_policy_id`, `required_services`, the `flex` provisioning tier, lifecycle hooks, and resume triggers.
- Blueprint builds, storage objects, secrets, agents, axons and network policies are not part of the facade — those routes do not exist. Devbox logs, usage and SSH keys are routed but answer `501`. Eviction notices answer `404`.
- Streamed output arrives while the command runs, usually within a second of being written. A devbox started on an AerolVM release before live output gets all of it when the command finishes. Output that is not valid UTF-8 arrives with a `?` for each such byte.
- After a command finishes, the facade keeps the last 1 MiB of its stdout and the last 1 MiB of its stderr, for up to an hour. If a command printed more, output callbacks first get a line like `[AerolVM: 40319 earlier bytes of stdout were not kept; ...]` and then the last 1 MiB. When that output is dropped (after an hour, or sooner on a busy node), the exit status is still there, and callbacks get only the notice line. To keep everything, write long output to a file in the devbox and read the file.
- `send_std_in` signals (`EOF`, `INTERRUPT`) answer `501`. Killing an execution in a named shell ends that shell.
- A snapshot stays on the node that took it. You can still reach it through any node, even after its source devbox shuts down. If that node leaves the cluster, the snapshot goes with it, and its routes answer `503`.
- In a cluster, the snapshot list shows the snapshots on the node that answers.

## Same thing from the SDK

The AerolVM SDKs reach the same sandbox directly:

  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({ name: 'agent-box', image: 'ubuntu:22.04' })
    const result = await sandbox.exec({ command: 'echo "Hello from AerolVM"' })
    console.log(result.exitCode, result.stdout)
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox = client.create({'name': 'agent-box', 'image': 'ubuntu:22.04'})
    result = sandbox.exec_command('echo "Hello from AerolVM"')
    print(result['exit_code'], result['stdout'])
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    sandbox, err := client.Create(ctx, sdktypes.CreateSandboxOptions{
        Name:  "agent-box",
        Image: "ubuntu:22.04",
    })
    if err != nil {
        log.Fatal(err)
    }
    result, err := sandbox.ExecCommand(ctx, `echo "Hello from AerolVM"`)
    if err != nil {
        log.Fatal(err)
    }
    fmt.Println(result.ExitCode, result.Stdout)
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let sandbox = client.create(CreateOptions {

    })?;

        command: r#"echo "Hello from AerolVM""#.to_string(),
        ..Default::default()
    })?;
    println!("{} {}", result.exit_code, result.stdout);
    ```
  </TabItem>
