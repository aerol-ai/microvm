A lifecycle is a set of timers. When one runs out, the server stops or deletes the sandbox for you. Use it so sandboxes you forget about do not keep using the server.

Every timer is optional, and a timer you leave out is off.

## The timers

| Option | What it does |
|---|---|
| `stopIfIdleFor` | Stop the sandbox after it has had no activity for this long. |
| `destroyIfIdleFor` | Delete the sandbox after it has had no activity for this long. |
| `stopAtAge` | Stop the sandbox this long after it was created. |
| `destroyAtAge` | Delete the sandbox this long after it was created. |
| `serverless` | Start the sandbox again by itself when a request reaches it. Needs `stopIfIdleFor`. See [Ghost sandboxes](/ghost-sandboxes/). |

Activity means anything that reaches the sandbox: a command, a file read or write, a terminal or SSH session, or traffic to its public URL.

A stopped sandbox keeps its files. Start it again with `start`. A deleted sandbox is gone for good.

## Set timers when you create a sandbox

This example stops the sandbox after one hour with no activity, and deletes it 24 hours after it was created.

The SDKs take each time in nanoseconds (billionths of a second). One hour is `60 * 60 * 1_000_000_000` nanoseconds. Go takes a normal `time.Duration` instead, so `time.Hour` just works. Rust and Java can convert with `Duration::from_secs(3600).as_nanos() as u64` and `Duration.ofHours(1).toNanos()`.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    const HOUR = 60 * 60 * 1_000_000_000; // one hour in nanoseconds

    const sandbox = await client.create({
      image: "ubuntu:22.04",
      lifecycle: {
        stopIfIdleFor: HOUR,
        destroyAtAge: 24 * HOUR,
      },
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    HOUR = 60 * 60 * 1_000_000_000  # one hour in nanoseconds

    sandbox = client.create(
        image="ubuntu:22.04",
        lifecycle={"stopIfIdleFor": HOUR, "destroyAtAge": 24 * HOUR},
    )
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    sandbox, err := client.Create(ctx, sdktypes.CreateSandboxOptions{
        Image: "ubuntu:22.04",
        Lifecycle: &sdktypes.Lifecycle{
            StopIfIdleFor: time.Hour,
            DestroyAtAge:  24 * time.Hour,
        },
    })
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust

    let hour: u64 = 60 * 60 * 1_000_000_000; // one hour in nanoseconds

    let sandbox = client.create(CreateOptions {
        image: "ubuntu:22.04".into(),
        lifecycle: Some(Lifecycle {
            stop_if_idle_for: hour,
            destroy_at_age: 24 * hour,
            ..Default::default()
        }),
        ..Default::default()
    })?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java

        .setImage("ubuntu:22.04")
        .setLifecycle(new Lifecycle()
            .setStopIfIdleFor(hour)
            .setDestroyAtAge(24 * hour)));
    ```

## Change the timers later

`updateLifecycle` sets new timers on a sandbox without a restart. It replaces all of them at once. A timer you leave out is turned off, so send every timer you want to keep.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    await sandbox.updateLifecycle({
      stopIfIdleFor: 2 * HOUR,
      destroyAtAge: 48 * HOUR,
    });
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox.update_lifecycle({"stopIfIdleFor": 2 * HOUR, "destroyAtAge": 48 * HOUR})
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    err := sandbox.UpdateLifecycle(ctx, sdktypes.Lifecycle{
        StopIfIdleFor: 2 * time.Hour,
        DestroyAtAge:  48 * time.Hour,
    })
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    // update_lifecycle() updates the sandbox, so declare it with `let mut`.
    sandbox.update_lifecycle(Lifecycle {
        stop_if_idle_for: 2 * hour,
        destroy_at_age: 48 * hour,
        ..Default::default()
    })?;
    ```
  </TabItem>
  <TabItem label="Java">
    ```java
    sandbox.updateLifecycle(new Lifecycle()
        .setStopIfIdleFor(2 * hour)
        .setDestroyAtAge(48 * hour));
    ```
  </TabItem>
</Tabs>

## Why a sandbox stopped

Every sandbox has a `statusReason`. It tells you why the sandbox is in its current state. When the reason comes from a program that ended, `exitCode` holds that program's exit code.

| `statusReason` | Status | What happened |
|---|---|---|
| `user_stop` | stopped | Someone called `stop`: your code, the CLI, another SDK, or the server's operator. |
| `idle` | stopped | `stopIfIdleFor` ran out, or the server's default idle stop did. |
| `max_age` | stopped | `stopAtAge` ran out. |
| `out_of_memory` | stopped | The sandbox used more memory than it has, and the system killed it. `exitCode` is set. |
| `disk_limit` | stopped | The sandbox wrote more than its disk size. |
| `crashed` | stopped | The sandbox went down on its own with a non-zero exit code. `exitCode` is set. |
| `reconcile` | stopped | The server found the sandbox stopped but did not see it stop, so it cannot say why. This can happen after the server itself restarts. |
| `program_exited` | stopped or started | The sandbox's main program ended. `exitCode` says how. |
| `failover` | started | The server the sandbox ran on failed, so the sandbox was created again on another server. Running programs and files outside a volume were lost. |
| `restarted` | started | The sandbox crashed and was started again for you. `exitCode` is the exit code of the crash. |

A sandbox that you created or started yourself has no reason. Starting a sandbox clears the reason. `lastError` still holds the full message, such as `container exited with code 3`.

## Restart after a crash

Set `restartOnFailure` and the server starts the sandbox again when it crashes or runs out of memory. It is off by default.

The server waits before each restart, so a sandbox that keeps crashing does not use up the server. The first wait is 5 seconds. Each crash after that doubles the wait: 10 seconds, 20 seconds, and so on, up to 5 minutes. Once the sandbox has run for 10 minutes without a crash, the wait goes back to 5 seconds.

After a restart, `statusReason` is `restarted` and `exitCode` is the exit code of the crash. `lastError` keeps the crash message.

  <TabItem label="TypeScript">
    ```ts
    const sandbox = await client.create({
      image: "ubuntu:22.04",
      lifecycle: { restartOnFailure: true },
    });
    ```
  </TabItem>
  <TabItem label="Python">

A restart never fights you or your timers:

- **A stop you ask for is never undone.** If you stop a sandbox, it stays stopped. Stopping a sandbox that is waiting for a restart cancels the restart.
- **Timers still win.** A sandbox whose idle or age timer has run out is not restarted. A restart does not count as activity, so a sandbox that keeps crashing still stops when it has been idle long enough.
- **Deleting a sandbox cancels its restart.**
- **Only real crashes count.** A stop by a timer, by the disk limit, or by you is not a crash. Neither is a program that ends with exit code `0`.

`restartOnFailure` works on Docker, gVisor and containerd sandboxes. Firecracker, WebAssembly and V8-isolate sandboxes reject it with a `400` error.

If the server itself restarts while a sandbox waits, the wait is kept. The restart happens within about a minute of the server coming back, or later if the wait is longer.

## Good to know

- **The longest timer is 30 days.** A longer value is rejected.
- **Delete cannot come before stop.** If you set both `stopIfIdleFor` and `destroyIfIdleFor`, the delete time must be the same or longer. The same rule applies to `stopAtAge` and `destroyAtAge`.
- **Delete wins.** If a stop timer and a delete timer are both due, the sandbox is deleted.
- **Timers are checked about once a minute.** A sandbox can run up to a minute past its timer.

## For server operators

`SB_IDLE_TIMEOUT_MIN` sets a default idle stop for the whole server. It stops any running sandbox that has been idle for that many minutes. It only applies to sandboxes with no lifecycle timers of their own. The default is `0` (off).
