A **runbook** is a step-by-step guide for one kind of problem. AerolVM's runbooks are in the repository, in [`setup/runbooks/`](https://github.com/aerol-ai/microvm/tree/main/setup/runbooks). Each Prometheus alert that ships with AerolVM links to its runbook.

Most runbooks have the same parts:

- How serious the problem is.
- Safety rules.
- Checks to run first.
- The fix.
- How to check that the fix worked.

Many end with a drill, so you can practice. For a first look at a cluster that seems wrong, start with [Fix problems](/cluster/troubleshooting/). Come here when an alert fires, or when the fix needs more steps.

`sandboxd` is the AerolVM program on each node.

## Words to know

| Word | What it means |
|---|---|
| **Incident** | An outage, or an alert that needs people to act. |
| **Prometheus** | The tool that collects metrics and fires alerts. |
| **Grafana** | The tool that shows metrics as dashboards. |
| **Alertmanager** | The tool that sends Prometheus alerts to people. |
| **SLO** | Service level objective: a target your service should meet, such as how fast creates finish. |
| **Leader** | The server node that writes down each cluster change. |
| **Voter** | A server or mixed node that votes on cluster changes. |
| **Majority** | More than half of the voters. The cluster needs a majority to make a change. |
| **Drill** | A practice run of a runbook, on a test cluster. |

## Pick a runbook

| Runbook | Use it when |
|---|---|
| [Backup and restore](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/backup-restore.md) | You need to put a node back from a backup. Or you lost local data, or need to prove your backups work. See also [Back up and recover](/cluster/backup/). |
| [Cluster upgrades](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/cluster-upgrades.md) | An upgrade failed or is stuck. Or it waits on a node marked `manual` or `skipped`. Or you need to finish (finalize) or undo (roll back) an upgrade. It also covers failing joins and failing node certificate renewals. See also [Upgrade](/cluster/upgrade/). |
| [Lost majority recovery](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/lost-quorum-recovery.md) (`lost-quorum-recovery.md`) | The cluster has no leader, because too many voters are gone. You cannot bring a majority back. This is the last thing to try. See also [Most server nodes died](/cluster/backup/#most-server-nodes-died). |
| [SLO breach](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/slo-breach.md) | An SLO alert fires and the cause is not clear. Start here, then move to a narrower runbook. |
| [Image-pull storm](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/image-pull-storm.md) | Image downloads are queued, failing or rate-limited. Or the node holds them back after repeated failures. |
| [Cluster ingress topology](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/cluster-ingress-topology.md) | The `SandboxdClusterTopologyViolation` alert fires. One cause: more than 10 ingress nodes, with no router that knows which ingress node holds which sandbox. The other cause: mixed nodes in a cluster of more than 10 nodes. |
| [Egress gateway](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/egress-gateway.md) | A `SandboxdEgress*` alert fires. Or creates that use a website allow list return `503 egress_gateway_unavailable`. |
| [Secrets and audit](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/secrets-and-audit.md) | An alert fires for secret audit, secret copies or your key store. Or a stored secret does not open, or `failover_ready` stays `false`. Or the startup check of your key store fails. |
| [Firecracker template health](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/firecracker-template-health.md) | Alerts fire for Firecracker template builds, uploads, downloads or rebuilds. |
| [Container engine coexistence](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/containerd-engine-coexistence.md) | You switch a node between Docker and containerd. Or you run both on one node while you drain it. |
| [WASM runtime health](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/wasm-runtime-health.md) | WASM sandboxes are stuck in `passivated` or `awaiting_runtime`. Or they stay cold after failover. Or WASM module uploads and downloads fail in the logs. |
| [Isolate jail](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/isolate-jail.md) | You need to check or debug the lock-down around `workerd`, the program that runs V8 isolates. |
| [Isolate workerd upgrade](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/isolate-workerd-upgrade.md) | You upgrade, or roll back, the fixed `workerd` version that V8 isolates use. |
| [Remote MCP](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/remote-mcp.md) | Agents that use the remote MCP endpoint (`/mcp`) report failures. Or `SandboxdRemoteMCPErrorRate` fires. Or you set up or check an OAuth connector, such as claude.ai or ChatGPT. |
| [Identity and access](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/identity-and-access.md) | An identity alert fires: `SandboxdBreakGlassPATUse`, `SandboxdPATScopeDrift` or `SandboxdIdentity*`. Or your sign-in provider is down. Or HTTPS breaks after you turn on the PROXY protocol. Also use it to change the admin token or the metrics scrape token. It shows how to make the first API token with the `admin` role. It also shows how to accept the admin token only on the node itself (`SB_PAT_SCOPE=host`). |

The [runbook overview](https://github.com/aerol-ai/microvm/blob/main/setup/runbooks/README.md) lists them too. See the [Glossary](/cluster-glossary/) for other cluster words.

## The first five minutes of any incident

The runbook overview sets the same start for every incident:

1. Find the alert that fired, and the cluster it affects.
2. Open the Grafana dashboard and the current Prometheus alerts page.
3. Save the leader, the member list and the metrics. Take metrics from one server node, one worker node and one ingress node.
4. Stop deploys and node changes until the incident lead says to go on.
5. Pick the narrowest runbook above. Run its checks before you change anything.

For step 3, these print the leader and the members:

```bash title="On your computer"
aerolvm cluster-info
aerolvm get nodes -o wide
```

The [Dashboard](/dashboard/) shows the same. To save the recent log of one node:

```bash title="On a node"
sudo journalctl -u sandboxd --since "30 minutes ago" --no-pager
```

The runbook overview also names four roles:

| Role | What they do |
|---|---|
| **Incident lead** | Makes the decisions, says how serious it is, and writes down the time of each action. |
| **Operator** | Runs the commands and changes the cluster. |
| **Comms** | Keeps users and other people up to date. |
| **Observer** | Records metrics before, during and after the fix. |

On a small team, one person can hold several roles. Still keep one lead, and one log of commands with their times.

## Tools the runbooks use

You need no copy of the repository. Every tool below ships in a release, or inside a program you already have.

| Tool | Where it runs | What it does |
|---|---|---|
| `aerolvm` | Your computer | The cluster commands: `get nodes`, `cordon`, `drain`, `delete node`, `join-command`, `upgrade`, `release pull`. See [the aerolvm CLI](/cli/#run-a-cluster). |
| `sudo sandboxd init`, `join`, `preflight`, `adopt`, `reset`, `join-command` | On a node | `init` starts a cluster. `join` adds a machine. `preflight` checks a machine before `init` or `join`. `adopt` moves a cluster built with the old scripts onto join commands. `reset` takes a machine out of its cluster. `join-command` prints a join command, on a server node. See [Build a cluster](/cluster/create/) and [Add and remove nodes](/cluster/nodes/). |
| `sudo sandboxd backup`, `restore`, `recover-quorum` | On a node | `backup` saves the database, cluster records, settings folder and server key of a node into one file. `restore` puts that file back. `recover-quorum` is the last-resort fix when most server nodes died. See [Back up and recover](/cluster/backup/). |
| `sudo sandboxd upgrade node` | On a node | Upgrades this one node. Use it for a node that `aerolvm upgrade status` shows as `manual`, or a node left on an older version. See [Upgrade](/cluster/upgrade/). |
| [`install.sh`](https://github.com/aerol-ai/microvm/releases/latest/download/install.sh) | On a node | Installs AerolVM on one machine. With `init` or `join` at the end, it also starts or joins a cluster. |
| [`uninstall.sh`](https://github.com/aerol-ai/microvm/releases/latest/download/uninstall.sh) | On a node | Removes AerolVM from a machine. |
| `aerolvm-ops-<release>.tar.gz` | Your monitoring | Each release ships one. It holds the Prometheus alert rules, the Grafana dashboards, the Alertmanager example and these runbooks, for that release. |

What `reset` does:

- It asks the cluster to delete this node, if it can reach the cluster. Then it stops `sandboxd`.
- **It keeps** the database, the server key and `/etc/sandboxd/sandboxd.env`.
- **It removes** `/etc/sandboxd/cluster.env`, the node certificate and keys, the signing key folder and the cluster records.

A backup file holds the server key, so keep it like a password. A node with a locked server key (`SB_CREDENTIAL_KEY_CUSTODY=wrapped`) puts only the locked copy in it.

`sudo sandboxd upgrade node` is not for the first upgrade from a release before v0.7.0. For that one, run the installer again on each node. See [Upgrade](/cluster/upgrade/#the-first-upgrade-from-a-release-before-v070).

Use the copies that match the release your nodes run. `sudo sandboxd version` prints it, such as `v0.7.0`. For the files of another release, use `https://github.com/aerol-ai/microvm/releases/download/<release>/<file>`.

<Aside type="caution">
Use `sandboxd recover-quorum` only while you follow the lost majority runbook. It makes one surviving server node the only voter. Its records become the cluster's records, even changes that a majority never agreed on. Changes that only the dead nodes had are lost. Try to bring the original voters back first.
</Aside>

**The old scripts are going away.** `cluster-init.sh` and `cluster-join.sh` still ship in this release. They are thin wrappers over `sandboxd init` and `sandboxd join`. `cluster-sign-node.sh` also ships, for the old two-step join. All three go away in a later release. In the repository, `sandboxd-backup.sh`, `sandboxd-restore.sh` and `raft-lost-quorum-recover.sh` now call `sandboxd backup`, `restore` and `recover-quorum`.

## Ansible playbooks

**Ansible** is a tool that runs the same steps on many machines over SSH. A **playbook** is one Ansible script. You do not need Ansible to upgrade. `aerolvm upgrade apply` upgrades every node from your computer.

The playbooks are in [`Ansible/playbooks/`](https://github.com/aerol-ai/microvm/tree/main/Ansible/playbooks). They change host settings only. Run them from the `Ansible` folder. It holds `ansible.cfg` and the node list (`inventory/`). The node list finds your nodes in AWS. The settings the playbooks push come from `config/cluster.yml`, at the top of the repository. The [Ansible README](https://github.com/aerol-ai/microvm/blob/main/Ansible/README.md) has the full guide.

| Playbook | What it does |
|---|---|
| `ping.yml` | Checks that Ansible can reach every node with SSH and `sudo`. Run it before anything risky. |
| `configure-ops.yml` | Pushes operations settings to every node. It also copies the Grafana SLO dashboard, the alert rules, the Alertmanager example and six runbooks. |
| `prepare-role-change.yml` | Drains a node, and waits until it runs no sandboxes. Use it before you change the role of a node or replace its machine. `aerolvm drain` does the same from your computer. |
| `tail-logs.yml` | Shows the latest `sandboxd` log lines from every node. |
| `stage-wasm-modules.yml` | Copies the standard WASM modules onto every node ahead of time. It checks the checksum of each file. |

## Put the runbooks on your nodes

`configure-ops.yml` copies the runbook overview and six runbooks to each node:

- Backup and restore
- Lost majority recovery
- Image-pull storm
- SLO breach
- Container engine coexistence
- Cluster ingress topology

They go next to the Grafana SLO dashboard, the Prometheus alert rules and the Alertmanager example. From the top of the repository:

```bash title="On your computer"
cd Ansible
ansible-playbook playbooks/configure-ops.yml
```

The runbooks go to `/etc/sandboxd/runbooks` on each node. For every runbook, use the `aerolvm-ops-<release>.tar.gz` file of your release.

## Practice with drills

Run these drills on a test (staging) cluster at least once a month. They prove that your commands, access, metrics and call list work before a real outage.

- **Backup restore:** put the latest backup onto a replacement node.
- **Lost majority:** talk through the decision steps. Do not create `peers.json`.
- **Image-pull storm:** start one test sandbox from an image tag that does not exist. Check that the backoff alerts fire.
- **Firecracker template health:** mark a test template `unhealthy` with the rebuild endpoint. Check that the rebuild clears the alert.
- **SLO breach:** make a queue of creates with a small load test that you control. Check the alert, the dashboard and the fix steps.

Write down each result in the drill template inside the runbook.
