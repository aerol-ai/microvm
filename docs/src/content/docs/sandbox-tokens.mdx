Your API key can reach every sandbox you own. You should never put it in a web page or give it to a user. A **sandbox token** is the safe thing to hand out instead.

A sandbox token:

- works for **one sandbox** only,
- can be narrowed to **some paths** and **some HTTP methods**,
- **expires** on its own, after at most 24 hours (the server's default limit),
- can be **revoked**: one call stops every token of a sandbox,
- is checked by the server with **no extra database lookup**, so it is fast and works on every server of a cluster.

Use one to give a user a terminal or a file browser for their own sandbox, or to let a browser page talk to the sandbox directly.

## Make a token

This makes a token that can only list and attach to the sandbox's terminal sessions, for 15 minutes.

<Tabs syncKey="lang">

    const client = new MicroVM();
    const sandbox = await client.create({ image: "python:3.12-slim" });

    const tok = await sandbox.createToken({ expiresIn: "15m", pathPrefix: "/sessions" });
    console.log(tok.tokenID, tok.expiresAt);
    // Hand tok.token to the user. Never log it.
    ```

The answer holds the token itself (it starts with `avmst_`) and its **token id** (it starts with `stk_`). The server keeps no copy of the token, so you see it only in this answer. The token id is safe to log: audit records name it, never the token.

<Aside type="caution" title="Each call makes a new token">
Making a token is not idempotent: every call returns a new token with a new id. That is safe. If an answer is lost and the SDK retries, the server makes a second token that nobody holds, and it simply expires.
</Aside>

## What you can limit

| Option | What it does | If you leave it out |
|---|---|---|
| `expiresIn` | How long the token works: `"15m"`, `"2h"`, `"1d"`. Required. The server refuses anything above its limit (24 hours by default). | Refused: every token must expire. |
| `pathPrefix` | Only paths under this one. `"/files"` covers `/files` and `/files/download`, but not `/files-old`. | Any path. |
| `methods` | Only these HTTP methods, such as `["GET"]`. | Any method. |
| `port` | Makes a token for one port's public URL instead of the toolbox: a port exposed with `visibility: "token"` (see [Public URLs](/public-urls/)). | A toolbox token. |

A **toolbox token** (no port) works for the sandbox's helper program: running commands, files and terminal sessions. The path is the helper's path:

| Path prefix | Lets the token… |
|---|---|
| `/files` | read and write files (add `methods: ["GET"]` for read only) |
| `/process` | run commands |
| `/sessions` | list, open and attach to terminal sessions |

A path that tries to step outside the prefix, such as `/files/../process`, is refused.

## Use a token

Give the token to the user as their API key. It works with any of the SDKs, but only for calls that go to the sandbox's helper program, inside the token's limits.

In a browser, the token goes where the API key would: in the `Authorization: Bearer` header, or in the WebSocket protocol list the SDKs use for terminals. The server swaps it for the sandbox's own secret before the request reaches the sandbox, so code inside the sandbox never sees the token.

## What a token cannot do

A token is refused for anything outside its limits. Nothing reaches the sandbox.

| You try | The server answers |
|---|---|
| Another sandbox, a path or a method the token does not cover | `403`, naming the part that did not match (`sandbox`, `port`, `path` or `method`) |
| Any call that is not the sandbox's helper program: get, list, start, stop or delete a sandbox, expose a port, make another token | `403` |
| The Daytona, E2B or Runloop APIs | refused |
| An expired token | `401` with reason `expired` |
| A token made before a [revoke](#revoke-tokens) | `401` that says `revoked` |
| A changed or damaged token, or one from another server | `401` with reason `invalid_signature` or `malformed` |

Because a token can never make another token, a token can never be stretched past its limits or its expiry.

## Revoke tokens

If a token leaks, revoke it. A revoke works on the whole sandbox: every token made for that sandbox so far stops working at once. That includes toolbox tokens, port tokens, and the cookie a browser got from a port link. Tokens of other sandboxes keep working.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

    const result = await sandbox.revokeTokens();
    console.log(result.tokensNotBefore);

    // Make a new token for anyone who should keep access.
    const tok = await sandbox.createToken({ expiresIn: "15m", pathPrefix: "/sessions" });
    ```
  </TabItem>
  <TabItem label="Python">

If you have only the sandbox id, call it on the client instead: `revokeSandboxTokens(id)` in TypeScript and Java, `revoke_sandbox_tokens(id)` in Python and Rust, `RevokeSandboxTokens(ctx, id)` in Go.

What happens after the call:

- Every token made **before** it gets `401` that says `revoked`. Nothing reaches the sandbox.
- A token made **after** it works, even one made in the same second. So you can revoke, then hand new tokens to the people who should keep access.
- Calling it again is safe. Each call stops every token made before that call.
- The answer holds `tokensNotBefore`: tokens made before this time no longer work.

You cannot stop just one token. Revoke them all, then make new ones for everyone else.

Revoking needs the same permission as making a token (see below). A sandbox token cannot revoke tokens.

## Who can make a token

Making a token needs the `sandbox.exec` permission on that sandbox: the `runner` and `admin` roles, and the operator token. That is the most a token can do, so a token never holds more than the person who made it. A `viewer` cannot make one, and nobody can make one for a sandbox they cannot see.

## Good to know

- **A token stops working** when it expires, when its tokens are [revoked](#revoke-tokens), when its sandbox is deleted, or when the server key it was signed with is retired. Keep lifetimes short anyway: a revoke only helps once you know a token leaked.
- **A sandbox that moves to another server starts fresh.** In a cluster, when a sandbox is made again on another server (after its server fails), every token made before the move stops working. Make new tokens after a failover.
- **Lowering the limit takes effect at once.** If an operator lowers `SB_SANDBOX_TOKEN_MAX_TTL`, tokens that live longer than the new limit stop working.
- **Clocks may drift a little.** Servers accept a token up to 30 seconds early or late, so servers whose clocks differ slightly still agree.
- **The SDKs check option support** by calling the helper's `/version` path before some calls. A token with a narrow path prefix (for example `/files`) is refused there, so those calls fail. Use the options they need, or a wider prefix.

## For server operators

There is no separate key store for tokens. Each token is signed with an Ed25519 key that every server works out from its **server key** (the key that also seals secrets). Every server of a cluster holds the same server key, so a token made through one server works through every other.

- **Key rotation.** After `sandboxd key rotate --promote`, new tokens are signed with the new key and old tokens keep working. Retiring the old key ends every token it signed, so wait at least `SB_SANDBOX_TOKEN_MAX_TTL` after the promote before you retire. See [Key custody](/enterprise/key-custody/).
- **Key revoke.** If your key store revokes the server key, no token works until the key is back.
- **Setting.** `SB_SANDBOX_TOKEN_MAX_TTL` caps a token's lifetime. Default `24h`, at most `720h` (30 days).
- **Logs and audit.** The token is never written to a log, an audit record or a metric. The call that makes a token records the token id, and every call made with a token names `sandbox_token:stk_…` as its caller. A revoke is recorded like any other call on the sandbox.
- **How a revoke is stored.** A revoke saves one time on the sandbox's record, on the server that runs the sandbox. A token made before that time is refused. Checking it costs nothing extra: the server already reads that record for every toolbox call and every visit to a token port. Every new record (a new sandbox, or one made again on another server after a failover) starts with its own creation time, so no older token reaches it.
