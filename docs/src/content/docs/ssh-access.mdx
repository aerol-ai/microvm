You can log in to a sandbox with SSH (Secure Shell), the standard tool for opening a shell on another computer. When you create a sandbox, the server makes a new key pair just for it. You get the private key once, in the create response, and use it with `ssh`.

<Aside type="tip">
Don't want to handle keys? Run [`aerolvm shell <sandbox>`](/cli/#open-a-shell-in-a-sandbox). It signs in with your API token and opens the same shell an SSH login does.
</Aside>

## Save the key when you create the sandbox

The private key is in the result of `create`, and only there. The server does not store it, so it cannot give it to you again. Save it right away.

<Tabs syncKey="lang">
  <TabItem label="TypeScript">
    ```ts
    import { writeFileSync } from "node:fs";

    const sandbox = await client.create({ image: "ubuntu:22.04" });

    // Only set on create: save it now.
    writeFileSync("sandbox_key", sandbox.sshPrivateKey ?? "");
    console.log(sandbox.id); // you log in with this ID
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    sandbox = client.create(image="ubuntu:22.04")

    # Only set on create: save it now.
    with open("sandbox_key", "w") as f:
        f.write(sandbox.sshPrivateKey)
    print(sandbox.id)  # you log in with this ID
    ```
  </TabItem>

The matching public key stays on the sandbox as `sshPublicKey` (Go `SSHPublicKey`, Rust `data.ssh_public_key`). You can read it later with `get`.

<Aside type="caution">
Anyone with the private key can log in to the sandbox. Keep it as safe as your API token.
</Aside>

## Log in

Make the key file readable only by you, or `ssh` refuses to use it. Then connect to port `2220` on your AerolVM server. The user name is the sandbox ID.

```bash
chmod 600 sandbox_key
ssh -i sandbox_key -p 2220 sb-0123456789abcdef@sandbox.example.com
```

On a local install, the host is `127.0.0.1`. Use the sandbox's ID, such as `sb-0123456789abcdef`. Its name does not work as an SSH user name.

## Run one command

Put the command at the end, as with any SSH server. You get its output, and `ssh` exits with the command's exit code.

```bash
ssh -i sandbox_key -p 2220 sb-0123456789abcdef@sandbox.example.com 'python3 --version'
```

## Open a named shell

A plain login opens the sandbox's shared shell, named `default`. It keeps running when you disconnect, and the next login lands back in it. [`aerolvm shell`](/cli/) opens the same one.

To get a separate shell, add `+` and a name to the user name:

| User name | What you get |
|---|---|
| `<sandbox-id>` | The shared `default` shell |
| `<sandbox-id>+<name>` | The shell with that name, started if it is not running |

```bash
ssh -i sandbox_key -p 2220 sb-0123456789abcdef+build@sandbox.example.com
```

These shells are [terminal sessions](/sessions/), so you can also read and manage them from the SDK.

## Good to know

- **The sandbox must be running.** A stopped sandbox refuses the login.
- **Each sandbox accepts only its own key.** There is no shared login for all sandboxes on a server.
- **No file copy or port forwarding over SSH.** `sftp` and the default `scp` do not work, and neither does `ssh -L`. Copy files with the [Files](/file-system/) calls or `aerolvm cp`, and share ports with [Share a web app](/preview/).

## For server operators

The SSH gateway is the part of the server that accepts SSH logins and passes them to sandboxes. It is on by default.

| Variable | What it does | Default |
|---|---|---|
| `SB_ENABLE_SSH_GATEWAY` | Turns the SSH gateway on or off. | `true` |
| `SB_SSH_LISTEN_ADDR` | The address and port the gateway listens on. | `0.0.0.0:2220` |
| `SB_SSH_HOST_KEY_PATH` | Where the server's own host key is kept. It is created on first start if missing. | `/var/lib/aerolvm/ssh_host_ed25519_key` |

### SSH in a cluster

In a cluster, one server runs each sandbox, but SSH logins arrive at any ingress node (a server that takes outside traffic). Users connect the same way no matter which server runs their sandbox:

```bash
ssh -i sandbox_key -p 2220 sb-0123456789abcdef@sandbox.example.com
```

When a login reaches a server that does not run the sandbox, that server checks the key against the server that does. It then passes the session there over the cluster's private, encrypted channel. Only the sandbox's public key and the session itself cross between servers. The key is checked on every login and never cached, so a changed key takes effect at once.

### Give every node the same host key

By default each server makes its own host key. Users who land on different servers may then see a warning that the host key changed. To avoid it, give every ingress node the same host key:

- **Terraform:** set the `ssh_host_key_pem` variable (marked sensitive) to a shared OpenSSH ed25519 private key. Setup writes it to `SB_SSH_HOST_KEY_PATH` on every node.
- **Ansible:** set `ssh.host_key` in `config/secrets.yml`, or point `sandboxd_ssh_host_key_src` at a file on the control machine. The `configure-ops.yml` playbook installs it.

Leave both unset to keep a separate key per node.
