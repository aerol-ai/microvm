The AerolVM server keeps a database of every sandbox. Sometimes that database falls out of step with the containers that really exist. This happens after a server reboot, a crash, or when someone removes a container by hand (for example with `docker rm`).

**Reconcile** fixes that. It checks every sandbox record against the real containers and corrects the records. The server does this on its own, so most of the time you do nothing. You run it by hand when you need the records to be right *now*.

The call waits until the whole check is done. On success it returns nothing. On failure it raises an error with the server's message.

Good to know:

- **It needs operator access.** Use the server's own PAT token (its main access token, `SB_PAT_TOKEN`). Tenant tokens on a managed server are refused.
- **It checks one server.** The call runs on the server your SDK talks to. In a cluster, each node that runs sandboxes also reconciles itself on a timer.

## Fix "host capacity exceeded" after a restart

Each sandbox reserves some CPU and memory on the server. If the server rebooted, or containers were removed outside the API, the old records still hold those reservations. Then a new create fails with `host capacity exceeded`, even though the server is nearly empty.

Reconcile first, then create:

<Tabs syncKey="lang">
  <TabItem label="TypeScript">

    ```ts
    // Make the records match what is really running
    await client.reconcile();

    // Now the create succeeds
    const sandbox = await client.create({ image: "ubuntu:22.04" });
    ```

  <TabItem label="Python">

## What reconcile changes

For each sandbox record, the server looks for its container:

- **The container is gone.** The server removes the sandbox's web routes and exposed ports, and unmounts its storage. Then it deletes the record. That frees the sandbox's CPU and memory reservation, and any TCP port it held.
- **The container is there.** The server updates the record's status, IP address and public URL to match the container. It also fixes the CPU and memory reservation, and puts back a "block all internet" rule if one went missing.

Before it deletes a record, the server looks for that container once more, directly. So a container that was briefly hard to see (for example, while it was starting) is not deleted by mistake.

In a cluster, reconcile also removes local copies of sandboxes that another node now owns. This happens when a node comes back after an outage and finds its sandboxes were moved.

## When reconcile runs on its own

| When | What happens |
|---|---|
| **Server start** | One full check, before the server takes API requests. Only when `SB_AUTO_RECONCILE=true`, which is the default. |
| **On a timer** | A full check every 5 minutes by default, while the server runs. |
| **Container events** | When a container exits or is removed, the server updates that one sandbox right away. |

These run only on nodes that run sandboxes (`worker` or `mixed` nodes). Server-only and ingress-only nodes have no containers to check.

## For server operators

| Variable | What it does | Default |
|---|---|---|
| `SB_AUTO_RECONCILE` | Run reconcile at server start and on a timer. Set to `false` to turn off both. | `true` |
| `SB_RECONCILE_INTERVAL` | How often the timed check runs. `0` turns off the timer. | `5m` |
