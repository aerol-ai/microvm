## Vision

### 10x Check
Today a cluster needs the repo, SSH, hand-copied secrets and a 90-day cert
re-sign per node; upgrades re-run the installer with every flag on every
node. The 10x version: blank machine to cluster member with one pasted line,
certs that renew themselves, and one `aerolvm upgrade apply` that the
cluster itself carries out (staged, canaried, resumable by any leader,
skipping dead machines), from a laptop or CI, online or offline. The same
CLI grammar Kubernetes users already know.

### Platonic Ideal
EXPANSION mode only; not applicable in SELECTIVE EXPANSION.

## Accepted Scope (added to this plan)
- §6.6: rollout record in Raft (rollout ID, caller, target and previous
  version, per-arch SHA-256, batch, pause-after, hold flag, rollout state,
  per-node state); rollout state table; the leader drives it and any new
  leader resumes it; `aerolvm upgrade stop`; `apply --wait`; one rollout at a
  time; `--from` uploads to the leader; the first hop into this release uses
  `install.sh` once (no CLI fallback; removed in spec review as infeasible).
- §6.3: remote upgrade off on a node marks it `manual` and the rollout waits.
- §6.8: rollback (reverse order, `*.prev`); always possible before finalize
  because one-way migrations run only at finalize (CEO D16).
- §4.3: `sandboxd preflight` with per-role ports, dial-back to the join
  call's source IP only, cgroup v2 as a warning, local-only checks for `init`.
- §6.7: stage step on every node (servers first) with a free-space check,
  staged-file cleanup, `--pause-after N` and `aerolvm upgrade resume`.
- §7.1: `aerolvm release pull` offline bundle (manifest, checksums,
  provenance, every CPU type) accepted by `upgrade apply --from`.
- §6.1/§6.2: `--batch` takes a number or a percentage; default 10%, at least 1.
- §6.2: down members are `skipped`, come back cordoned, are upgraded, then
  uncordoned; finalize waits for them; servers restart only while a
  majority of voters stays up.
- §6.3: servers fetch from `SB_RELEASE_URL`; workers and ingress copy from
  servers over `GET /v1/cluster/internal/upgrade/files/{sha256}`, at most 20
  at once per server.
- §9: Phase 3 split into 3a (node upgrader, run on the node; auto-finalize;
  `release.json`) and 3b (node route, rollouts, release files on servers).
- D3, §7, §8: per-role token lifetime; Terraform makes one token per role.
- Spec review round 2 repairs inside accepted scope: discovery key derived
  from the token secret; deny record by node ID and cert key, cleared by a
  fresh join and checked on renewal; joins during a rollout limited to the
  target or previous version; worker batches cordoned before restart;
  single-node `apply` through `POST /v1/node/upgrade`; servers keep release
  files until finalize or rollback; `--from` files on every server before
  the rollout is written; failure restore only before the API opens;
  `release.json`; idempotent `stop`/`resume`/`finalize`; Phase 0 makes
  `install.sh` restart on a new binary and read old settings back.
- Spec review round 3 repairs inside accepted scope: rollout transition
  table; schema migrations with `n1_safe`; previous-version hashes in the
  record; single-node `--from`; old members kept cordoned after finalize;
  operator cordons restored; canary pause defined in §6.7; manual servers
  keep the quorum check; three join paths; join keeps its key on cleanup;
  stopped rollouts keep staged files; per-role `init --token`; `--hold`
  moved to Phase 3b; deny records mirrored to workers and checked at gossip
  join; workers never relay server joins; `contexts.json`.

- Review sections and outside-voice repairs inside accepted scope: upgrade
  commands fenced by leader, term and committed record, with one local
  upgrade at a time; DB restore only when the store's migrate step failed;
  `host apply --config-only` and `host_setup_needs_network`; `sandboxd

  gateway restarts when its protocol would fall out of range; crash-safe
  file swaps; one Raft op per join reserving the node ID; token secret of
  at least 128 bits; observability (§10.1).
