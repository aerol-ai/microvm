## Vision

### 10x Check
As written, the plan makes AerolVM runnable on EKS and AKS. The 10x version makes
it the default answer there. Once the Phase 6 facade lands, agent frameworks that already speak the Kubernetes
agent-sandbox API (LiteLLM Agent Platform, Dify, OpenSandbox users) point at AerolVM and get image-cached creates about 20x faster (gVisor 284 ms on the
warm path [measured] against 5.5 s for a cold pod [measured, kind]), no 110-pod
or VPC-address limit per machine, and zero etcd writes per sandbox, with no
code change for the common fields (unsupported upstream fields are refused with
a clear error). Warm creates are in the same range as agent-sandbox's own warm
pool (AerolVM's warm path 43 ms p50 on runc [measured,
`plans/warm-create-latency-tier1.md`] against 40–50 ms [measured, kind]); gVisor
from a warm pool is not measured yet, and Phase 0 measures it. A
bank's security team gets checkable evidence in a week, not a quarter.

### Platonic Ideal
1. A bank platform engineer runs `helm install aerolvm`, then applies one `AerolCluster` with their zones and their certificate issuer.
2. Twenty minutes later there is a 3-zone cell.
3. Their agent framework creates sandboxes on gVisor in a few hundred milliseconds cold, and faster from a warm pool, and `kubectl get sandboxes -n team-a` lists them.
4. Their cost tool shows sandbox spend per team.
5. Their admission policy passes with one named, documented exception.
6. Monthly machine patching moves running sandboxes with their memory.
7. Nothing is installed on the machines.

## Accepted Scope (added to this plan)
- Phase 6 keeps C17, the agent-sandbox API, with the RQ9 limits; its storage and namespace rules are decided when it is built (RQ10). Nothing about it is built in Phases 0–3.
- P7 evidence pack (Phase 0 draft v1, updated with S7; final in Phase 2) and P8 `aerolvm k8s verify` (Phase 1 subset, Phase 2 full).
- S7 least-privilege spike (Phase 0), decided per supported machine image: on each image, one supported mode (the list if S7 passes there, else privileged); Bottlerocket counts only if S1 passes on it; AKS images run S7 in Phase 4.
- C20 per-owner usage export (Phase 2): counters on each worker's own `/metrics`, summed by a P9 recording rule, so nothing is aggregated in the leader; two series per owner, reserved (the charge) and consumed (shown alongside, RQ16); off by default, the chart turns it on. P9 chart monitoring (Phase 2).
- C21 gVisor checkpoint moves (Phase 5), on by default for gVisor: a fenced hand-off (pause, checkpoint, restore paused, ownership compare-and-swap, then resume), one bundle with the memory checkpoint and the rootfs diff, sealing, local staging, per-worker sandbox address slices, up to 8 moves in parallel per worker, time budgets and compatibility checks; sandboxes with external-storage mounts are refused.
- P10 platform polish (Phases 1 and 2), inside the G4 write budget.
- R1 (user instruction): plan rebased on main and built on what shipped; C22 server-pod maintenance mode added for v0.7.0's recovery tools (every surviving server in maintenance for a lost-quorum recovery).

## Decided in the review sections
- S-1 (RQ14): C24, sandboxes cannot reach the bank's cluster network by default. The API server, the metadata service and the worker's own ports are an immutable floor; the pod, Service and node ranges are an overridable default.
- OV-3 (RQ15): an honest zone-loss promise (G1): every `recreate` sandbox comes back in the other zones, as much within 60 s as the spare room holds, plus a per-pool `zoneLossReserve`.
- OV-5 (RQ16): usage is charged on reserved CPU and memory; consumed use is shown alongside and never changes the bill.
