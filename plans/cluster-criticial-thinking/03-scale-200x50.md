# 03 — Scale at 200 × 50

This page does the arithmetic. The target is:

- **200 worker nodes.**
- **50 sandboxes/node steady-state ⇒ 10,000 concurrent sandboxes.**
- **Churn assumption: 1% of sandboxes destroyed and recreated per minute
  in steady state ⇒ ~100 destroys + 100 creates / min.**
- **Bursts: a single client may create 1000 sandboxes back-to-back.**
- **Failure assumption: at least one node dies / week unplanned, plus
  planned restarts during deploys.**

These numbers come from a generous-but-realistic CI/AI-agent workload
shape. Anything that breaks at *less* than this is a problem even
before reaching the target.

---

## Numbers worth pinning

| Quantity | Value |
|---|---|
| Nodes (N) | 200 |
| Sandboxes/node steady (K) | 50 |
| Total sandboxes (T = N×K) | 10,000 |
| Raft voters (today's design) | N = 200 |
| Raft quorum | ⌈(N+1)/2⌉ = 101 |
| Avg create rate (steady) | ~1.7/s |
| Burst create rate (one client) | up to ~50/s |
| Failover blast (one node) | up to K = 50 sandboxes to reassign |
| Failover blast (rack-power loss) | up to 3K = 150 simultaneous |
| FSM in-RAM per node | ~30–40 MB (placements + spec + sealed) |
| Cluster-wide FSM duplication | N × 30 MB ≈ 6 GB across all voters |
| Caddy routes per node (if cross-node) | T = 10,000 |
| Caddy routes cluster-wide (if cross-node) | N × T = 2,000,000 |

## 1. The raft commit hot path

Per raft commit on the leader:

1. Append to local BoltDB log (~1 ms p50, ~10 ms p99 on cheap NVMe).
2. Send AppendEntries to N-1 = 199 followers in parallel.
3. Wait for `quorum - 1 = 100` follower acks (the leader itself counts).
4. Mark committed, apply to FSM locally (cheap, in-RAM).
5. Followers apply on their next tick.

Step 3 is the killer. The leader's commit latency = the
100th-fastest-follower's ack time. The 99th and 100th percentile
followers can be transient stragglers — running gossip-induced GC,
holding a long Caddy admin call, doing a docker pull. **The slowest
quarter of the cluster sets commit latency.**

On a well-tuned LAN with 3-voter raft, p50 commit ≈ 5 ms, p99 ≈ 20 ms.
On 200 voters across a region's AZs (1–2 ms intra-AZ RTT, plus the
slowest-quarter tail), p50 climbs to ~30 ms, p99 to several hundred ms.

### Steady state ≠ problem; bursts = problem.

100 creates + 100 destroys per minute at p50 = 30 ms commit = 6 s of
leader CPU per minute. Fine.

A 1000-sandbox burst from one SDK call, all serialized through one
leader = 1000 × 30 ms = 30 s of pure commit wait, plus the local
docker work behind it. The client's create-loop will time out long
before the cluster catches up. **No batch API; no admission shedding.**

### What needs to change.

- Reduce the voter count to a small fixed control plane (3 or 5). Commit
  latency goes back to p50 ~5 ms.
- Batch raft commits when one originator submits a burst.
- Shed at the API: if `raft.LeaderApplyBacklog()` (a future signal) > X,
  return 503 + Retry-After so clients pace themselves.

## 2. Raft replication fan-out bandwidth

Each commit ships ~200 B–1 KB of log entry to every follower. At 200
followers:

- Steady state: 200 ack/min × 1 KB × 200 followers = 40 MB/min outbound
  on the leader. ~700 KB/s. Trivial.
- Failover burst (50 reassign commits in ~1 s): 50 × 1 KB × 200 = 10 MB
  in one second. Still trivial.
- Snapshot transfer to a fresh joiner: ~30–40 MB of FSM, one-shot. The
  leader streams the snapshot. ~1 s on a 100 Mbps link.

**Bandwidth is not the bottleneck.** The bottleneck is the sequential
ack wait above, not the bytes.

## 3. The FSM memory footprint

Placement row size estimate:

| Field | Bytes |
|---|---|
| SandboxID (UUID string) | ~36 |
| OwnerNodeID, OwnerAPIURL | ~80 |
| Version, timestamps | ~24 |
| Spec (CreateSandboxRequest, with env/mounts) | ~2,000 (typical) |
| SealedSecrets (when registry/mounts used) | ~1,000 |
| ExposedPorts map | ~100 (1–2 entries typical) |
| Map overhead | ~50 |
| **Total** | **~3.3 KB/row** |

At 10K sandboxes: ~33 MB per voter, in steady-state.

Add raft's BoltDB log/stable files on disk: typically 100–300 MB per
voter under churn.

**At 200 voters: 200 × ~33 MB = ~6.6 GB cluster-wide RAM duplicated.**

Not catastrophic, but ~195 copies exist for no good reason — every
worker holds an FSM it could just-as-well fetch on demand. With the
worker/server split:

- Servers (3–5): ~33 MB each ⇒ ~100–165 MB total.
- Workers (195+): each holds only the placements *for sandboxes they
  own* (50 × 3.3 KB = ~165 KB) plus a small LRU cache of recent
  owner-lookups.

That's a 40× reduction in cluster-wide RAM duplication.

## 4. The placement-list scan

`fsm.idsOwnedBy(nodeID)` (`fsm.go:228-238`) is an O(T) scan over the
placement map under a `RLock`. Called by the dead-owner reconciler in
its 5 s tick.

At 10K placements:

- 5 s × 10K iter = nothing meaningful on modern hardware (~100 µs).
- Lock contention: the RLock means concurrent `Apply` writes block while
  this scan runs. At 100 ms scan worst case (unlikely but worth
  bounding), that blocks raft apply for 100 ms.

Not a real problem at 10K. At 100K it would start to matter. Adding a
secondary index `owner → []sandbox_id` would make it O(K), but it's
premature optimization today.

## 5. Gossip at 200 nodes

memberlist SWIM:

- **Probe interval:** 1 s default. Each tick a node picks a random peer
  and pings; if no response, picks another to indirectly probe.
- **Per-node packet rate:** ~3–5 packets/s outbound to randomly chosen
  peers.
- **Cluster-wide packet rate:** N × ~5 = ~1000 packets/s. UDP, small
  payloads (<512 B each). Bandwidth: ~500 KB/s cluster-wide. Trivial.
- **Convergence after death:** memberlist marks suspect after
  ~probe_interval × suspicion_mult (3–5 s), then dead after another
  similar interval. Total dead-detection: ~10 s.

The 5 s metadata refresh loop (`gossip.go:188`) re-publishes
`nodeMeta`. UpdateNode triggers a gossip dissemination wave.

- Per-update bandwidth: 200 nodes × ~500 B nodeMeta = ~100 KB pushed
  every 5 s through gossip. Memberlist's anti-entropy dissipates it in
  O(log N) hops.
- **At 200 nodes that's fine.** memberlist is documented to scale to
  ~1000+ nodes.

**Where gossip starts hurting:** the 5 s refresh tick across 200 nodes
means the *whole-cluster view* of a node's capacity is stale by up to
~5–10 s. Power-of-two scheduling reads that stale view. See A3 in
[`02`](./02-assumptions-challenged.md).

## 6. The TCP host-port pool

Per-node pool: `[22000, 23000]` = **1000 ports per node**. Each
exposed TCP sandbox port consumes one.

- 50 sandboxes × 2 TCP exposures each = 100 ports. Plenty of headroom.
- After failover, the new owner allocates from *its own* pool. The pool
  on the new owner has its own 1000-port capacity.
- The partial unique index on `host_port` (`store.go:256`) enforces no
  double-allocation. Idempotency on retry is the well-tested path.

**This is fine at 200×50.** The single failure mode is "a sandbox uses
50+ TCP exposures" — unlikely in practice.

## 7. Caddy config size

### Status quo (per-node Caddy holds only local routes)

Per node: ~50 sandboxes × ~3 routes each (one for sandbox URL, one per
exposed HTTP port, one per exposed TLS port) = ~150 routes per node.
Caddy handles this in single-digit MB JSON config and reloads in
hundreds of ms.

### If we ship "cross-node Caddy stub routes" (Option 2 in the
existing plan)

Per node: ~10,000 sandboxes × ~3 routes = ~30,000 routes per node.
That's a Caddy JSON config in the tens-of-MB range. Caddy's admin API
reload of a config that large takes seconds, and concurrent reloads
serialize.

**Update fan-out**: every placement change → 200 Caddy admin API
calls (one per node) to keep stub routes in sync. A 50-sandbox failover
generates 50 × 200 = 10,000 Caddy admin calls in seconds, each one
mutating a 30K-route config.

That is the **single worst design choice** if shipped naively. The doc
recommends it in
`plans/fucked-up-design-in-cluster.md` for 3–5 nodes. At 200 it's not
viable.

**This is why the LB tier in [`05`](./05-data-plane-and-load-balancer.md)
is the right answer.** Move the routing decision out of N copies of
Caddy and into a small ingress tier (3–10 nodes) that holds a single
authoritative routing table.

## 8. The clusterListWrap fan-out

Today: any GET `/v1/sandboxes` fans out to *all* alive peers, sequentially
awaiting up to 5 s per peer.

At 200 nodes:

- 199 HTTP requests issued in parallel (`clusterListWrap` does spawn
  goroutines).
- 5 s timeout each — but the *response* waits for all goroutines.
- If even one peer is slow (Caddy admin lock, slow GC), the whole list
  takes 5 s.

This is a denial-of-service vector against the cluster's own API. A
client that polls list every few seconds keeps 199 HTTP connections
warm to peers.

**Fix:** the worker/server split makes list-aggregation a server-only
responsibility. Servers hold the FSM; the FSM has every placement.
Listing becomes a local FSM scan with no fan-out. The local store on
each worker still has runtime state (container ID, ports, etc.), but
the *cluster-wide list* is a server-side operation reading from raft.

This also makes pagination trivial.

## 9. The dead-owner reconcile burst

Scenario: a rack PDU outage takes down 3 adjacent nodes. Each owned ~50
sandboxes. The grace timer expires for all 3 simultaneously (because
they died simultaneously).

The leader's 5 s reconcile tick processes them. `evictDeadOwner` runs
sequentially per dead node (loops in `dead_owner.go:166-201`).

- 150 placements to reassign.
- Each reassign:
  - `pickRecreationTarget(spec)` reads gossip (O(N) scan).
  - `applyCommand(opReassign)` writes a raft entry.
- Raft commit serializes: 150 × ~30 ms = ~4.5 s of pure raft work,
  *if* no other writes are competing (they are).
- Then `RemoveServer` on each dead voter: 3 more raft ConfigChange
  commits.

Total: ~5–10 s for the leader to process the reassign storm. The new
owners then start their owner-watcher recreate work — independently —
in their next 5 s tick.

**The leader is the bottleneck.** With 5 voters instead of 200, raft
commit time drops by ~10x and this becomes <1 s of leader work.

**Image pull storm:** the 150 sandboxes recreate on (say) 30 different
new owners. Each owner does its share of pulls. If 80% of the images
are the same base (typical), the bandwidth cost is paid only once per
owner. But cold-cached owners pay it from scratch. **This is the real
recreate latency tax**, not raft.

## 10. The mTLS hop on every write

Every mutating call from a follower goes:

```
follower handler → leader-forward HTTPS to leader's :7002 → leader raft.Apply
```

That's an extra mTLS HTTPS handshake plus a TCP RTT per write that
doesn't originate on the leader.

At 200 nodes, a uniform write distribution means ~199/200 of writes
need that hop. The mTLS connection is pooled
(`forward.go:54-58`), so steady-state handshake cost is amortized — but
the per-write RTT cost is not.

- LAN RTT: ~0.5 ms.
- Cost: ~0.5 ms per leader-forwarded write.

At ~1.7 writes/s steady state, this is a rounding error. During the
1000-create burst it adds ~0.5 s of total RTT cost. Still small.

**Not a real problem.** Calling it out for completeness.

## 11. Boot time on a fresh node join

When a new worker joins gossip → leader does AddVoter → new voter
catches up on raft log.

At 10K placements + churn, the raft log between snapshots can be
hundreds of MB. The new voter:

1. Downloads the latest snapshot (~30–40 MB FSM serialization).
2. Replays log entries since the snapshot.

On a 100 Mbps link: snapshot transfer ~3 s, log replay ~5 s. Total ~10
s before the new node can take placements.

With 200 voters, this happens for *every* node join. If you autoscale
in 10 nodes at once, the leader serves 10 concurrent snapshots — that's
real outbound bandwidth (300+ MB).

**Worker/server split removes this for the common case.** Workers don't
do raft catch-up; they just register via internal RPC and become
available for placement in <1 s. Only when a *server* node is added —
which is rare — does the full raft catch-up happen, and it's only 3–5
peers receiving it.

## 12. The list of "small enough to ignore at 200×50" items

Worth naming so they're not forgotten:

- BoltDB log file size on each voter (~100–300 MB). Disk space cheap.
- Gossip packet rate (~1000 packets/s cluster-wide). Trivial.
- Capacity admitter math (in-process, ~µs). Trivial.
- mTLS handshake amortization. Pool reuse handles it.
- Caddy DNS-01 wildcard issuance (200 × 1 cert/90 days = ~2/day cluster
  cert renewals). Inside Cloudflare rate limits comfortably.

## What actually breaks first

If you ran this branch as-is and pushed it to 200×50, the failure
order is:

1. **Public sandbox URLs**, immediately. ~99.5% 404 rate. The product
   feature is broken before any scale issue hits.
2. **Raft commit p99**, under burst. A 1000-create burst from one
   client times out before the leader finishes the log.
3. **Failover storm**, on the first 3-node outage. ~10 s leader stall
   while reassigns serialize, then ~60 s of image-pull congestion.
4. **clusterListWrap**, the first time a slow peer holds up a
   monitoring call. UI/dashboard listing times out.
5. **Node-join time**, the first autoscale event. 10–20 s per joiner
   delays the cluster expanding to absorb the load that triggered the
   autoscale.

Notice that #1 and #2 are *design* problems, not load problems —
they'd happen at 200 nodes even with no load. #3 and #4 are
*operational* problems that scale linearly. #5 is the slow drift you'd
notice last but feel most when you most need elasticity.

The fixes are sequenced in [`07`](./07-improvement-proposals.md).
